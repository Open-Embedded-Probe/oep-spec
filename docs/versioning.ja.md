# OEP の版と安定性

状態: **ガイド**（規範ではない）。何が変わらないかの約束をまとめる。規則そのものは [OEP core](oep-core.ja.md)（§2.3、§2.5、§2.8、§7.1、§12）と、core と `registry/oep-v1.toml`
の冒頭にあり、このページと食い違えばそちらが正しい。


## 1. 版を持つもの

| もの | 運ぶ所 | 変わるとき |
|---|---|---|
| **プロトコルの revision** | confirm の revision（u8。v1 = 1）。経路ごとに取り決める（core §7.1） | core の形や既存の契約を壊す振る舞いが変わるとき（core §2.8）。confirm そのもの、その magic、64 byte の決まりは変わらない |
| **インターフェースの revision** | list の fn ごとの revision（u8）と、registry のインターフェースごとの `revision` | 固定部分、必須機能、状態遷移、資源寿命など、既存の契約を壊すとき（core §2.8） |
| **インターフェースの名前** | list | インターフェースの意味が変わるとき（名前が違えば別のインターフェース） |
| **registry の schema** | `[registry] schema`（1） | registry のファイルの形が変わるとき（線の上ではない） |
| **REGISTRY_HASH** | 生成したファイル | registry のどこかの byte が変わるとき。生成したコードが registry と合うかを示すだけで、線の上の互換については何も言わない |
| **仕様のリリース** | このリポジトリの git のタグ（§6） | 規範の文か registry が変わるとき |

## 2. 凍結の前（今）

OEP v1 は凍結前である。凍結までは、壊す変更も **どの revision も上げずに** 入れる。revision 1 だけでは互換性を判定できないため、実装は対応する仕様の commit または tag を明記する。凍結前に削除した番号は再利用してよい。凍結前の版どうしの移行手順は仕様に残さない。

凍結までは日本語の文書（`.ja.md`）を正として保守する。凍結時に英訳を作成し、その後は英語を規範、日本語を対訳として同時に保守する。

### 2.1 コアの暫定確定

正式凍結より先に、coreとtransportsの既存契約を実装の基準として固定する。
範囲はメッセージ/フレーム、fn 0の8操作、発見と識別、TLVと未知値、再送、session/lease、channelと資源の一般規則、通知と拡張の共通契約、
それらに使うregistryの番号・幅・時間条件である。共通部品の採用と個別OEPの機能は、それぞれのインターフェースの範囲に残る。

この範囲へ新しい必須操作・必須宣言・状態表を追加せず、機能は任意のインターフェースで定義する。
既存の意味、幅、番号、必須性、再送や資源の寿命を変える提案は、矛盾または独立実装の成立しない反例と、境界検査を示して暫定基準を更新する。
文言の明確化と、既存契約を保つ任意の追加は許す。各実装は更新後のGit commitを明記する。

暫定確定は、§6のtagを付ける正式凍結や、実装の適合認定ではない。
正式凍結前のrevision 1どうしの互換性は、引き続きcommit/tagで確認する。正式凍結後は§3〜§7のrevisionとリリース規則に従う。

## 3. 凍結が止めるもの

凍結の後、次のものは revision を上げることでしか変わらない:

- フレームの形: COBS + CRC-16、`length(u16)`、HID の report、見出しの順と長さ、confirm の前の 64 byte（core §3）;
- メッセージの形: 要求 / 応答 / 出来事 / データの固定部分、TLV の形と critical の規則、断りの理由、outcome、断り方の順（core §2、§4）;
- 名前が `oep.` で始まるインターフェースの payload: op の表、固定部分、TLV の tag、出来事、status、資源の寿命（`interfaces/oep-if-*.ja.md`）;
- **`registry/oep-v1.toml` のすべての数**: op、tag、reason、status、enum、`timing`、`limits`、`usb`、インターフェースの名前と revision、
  廃止（凍結後に外した値は retired として残し、別の意味に使わない）。参照の firmware の値（max_op_ms、線の時間と回数）は仕様の外;
- core、`oep-if-*` の文書、dmseq の規範の文。

既存の契約を壊すインターフェース変更は revision を上げ、core の形や既存の契約を壊す振る舞いの変更はプロトコルの revision を上げる（core §2.8）。任意から必須への変更も破壊的変更であり、単なる機能追加として扱わない。

凍結の後も自由なもの: ガイドとその中の参考の数字、リリースの前の試験、仕様が probe に選び方を任せる所での仮想ベンチの
動き、各実装の方針と宣言する値。

### 3.1 意図して固定するものと、その理由

既存の契約を保つ境界と、拡張先を示す。固有操作の規則と理由は各インターフェースに置く。

| 境界 | 理由 | 拡張先 |
|---|---|---|
| 1つのロックと再送順序状態 | 所有者と資源の寿命を小さく保つ | 複数hostの共有はbroker。独立した複数sessionはプロトコルの新revision |
| boot内で固定のlist/describe | cacheとページングの一貫性を保つ | 接続や空き容量は状態照会op。公開機能集合の変更は再起動 |
| 固定部分と配列要素の形を伸ばさない | revisionから長さと意味を確定できる | 任意TLV、要素index付きTLV、または新revision |
| op/tagなどの有限の番号空間 | 名前ごとに小さいparserで扱える | 所有者による任意の追加、別名のインターフェース |
| confirm前の64byteと経路ごとのframe | 能力を知る前にも発見できる | 必要な機能は大きいmax_frameを使う。分割可能な新しい一覧は専用照会op |
| 認証・firmware更新の方式をコアへ必須化しない | 製品固有の状態を最小実装へ課さない | 認証済み経路、任意の方針拒否、専用インターフェース |

## 4. revision を変えずに足せるもの

凍結の後の OEP の伸び方はこれだけである（core §12.1）。これらを足しても、どの revision も変わらない。それを知らない host や probe は動き続ける（core §2.8）:

| 道 | 決まり |
|---|---|
| 任意の要求 / 応答 / 出来事の TLV | op の文脈の新しい tag。host は知らない非 critical の tag を読み飛ばし、probe は知らない critical の tag を unsupported で断る（core §2.2、§2.3） |
| 任意の op と出来事 | インターフェースの op 0x10〜0xFF、出来事の kind 0x01〜0x7F。あるかどうかは describe で宣言する（core §2.5、§2.8） |
| 新しい enum の値と予約の bit | 要求では: 定義が使っていなかった値は、それを知らない probe が unsupported で断る（core §2.5、§4.3）。応答、出来事、データでは: どのフィールドのあるなし、長さ、位置もその値に依らず、core §2.4 の知らない値の扱いが安全で、意味がその値に依るフィールドはどれも、その値を知らない読み手が無視するか生のまま見せるときだけ足せる（core §2.5）。そうでなければ新しい TLV、revision、インターフェース |
| インターフェースの断りの理由、unavailableのcauseとstatusの値 | 0x40〜0x7F（core §2.5、common §3） |
| describe の tag | 共通 0x01〜0x3F、インターフェース 0x40〜0x7E。どの固定の形とも同じく、describe の値は延ばさない（core §2.3、§7.4） |
| 名前つきの拡張 TLV | どの文脈でも tag 0x7F、`name_len、name、data`。ほかの者も自分の逆 DNS の名前で足せる。番号は取らない（core §2.2、§12 規則 7） |
| 名前の並び | コンソールの方式、ネットワークの口。標準の名前は registry、ほかの者は逆 DNS の名前。番号は probe の並びの位置（core §7.7） |
| 設定の項目と線の名前 | 本体と `oep.` のインターフェースの新しい項目（registry の settings。名前の意味と形は変えない、core §13.1）。ほかの者は自分の名前のインターフェースに項目を置く。標準の線の名前はregistryとhostガイド §5.3に（hostの慣行） |
| 新しいインターフェース | `oep.` の名前はこのリポジトリを通して。逆 DNS の名前は誰でも登録なしに（core §12） |
| 新しい共通操作 | coreが未割当の0x03〜0x0Fへ割り当て、対応するfnがopsで宣言する（core §12.1） |
| 新しい経路 | フレームの方式と一緒に新しい transport の kind を（transports §1） |

インターフェースの revision を上げる probe は、できれば古い revision も別の fn で出し続ける（core §2.8）。古い host が動き続けるように。

## 5. registry の約束

- 凍結の後、**キーは名前を変えず、消さない**。新しいキーを足す（registry の冒頭）。生成した識別子はキーから作るので、
  それを使うコードはそのまま通る。
- キーの値は変わらない（凍結した数、§3）。凍結後に外した値は retired として残し、別の意味に使わない。何かを試すときは、自分の逆 DNS の名前のインターフェースを使う（core §12）。
- 新しい表の種類や、インターフェースや op の新しいキーは、pull request による registry の変更（CONTRIBUTING）。

## 6. 仕様のリリース

- このリポジトリに **git のタグ `vMAJOR.MINOR.PATCH`** を付け、指す commit と一緒に push する。
  - MAJOR は、正式リリースからはプロトコルの revision（プロトコルの revision 1 は `v1.y.z`）。その前は 0。
  - MINOR は §4 の追加、新しいインターフェースか新しいインターフェースの revision、registry への追加で増える。
  - PATCH は振る舞いを変えない errata で増える: 文言、訳、ガイド、記録、道具。
- **正式リリースの前のタグは `v0.MINOR.PATCH`**（レビューのためでも凍結でも同じ）。凍結は、CHANGELOG が凍結と書く `v0` のタグで、`v1` では
  ない。**`v1.0.0` は正式リリース**で、そこから MAJOR はプロトコルの revision に従う。
- **凍結の前は、revision 1 だけでは形が一つに決まらない**: 壊す変更は revision を上げずに入る（§2）ので、違う commit から作った 2 つの実装が
  どちらも revision 1 と言いながら、つながらないことがある。だから実装は、自分が実装する仕様のタグを示す。
- タグは、`python3 tools/oepgen1.py --check` と `python3 tools/oepvectors1.py --check` が通り、`cd tests && uv run pytest`
  が通る commit にだけ付ける。
- 根の **CHANGELOG.md** にリリースごとの変更（日付、タグ、commit）を並べ、次のタグまでの変更は「Unreleased」の節に集める。規範の文か
  registry の変更はすべて項を持つ。文言だけの変更はまとめてよい。
- 実装は、実装したタグを（README に）、扱うプロトコルとインターフェースの revision と一緒に書く。probe は、
  fn 0 の describe の `firmware`（0x40）の自由な文にもタグを入れてよい。host が食い違いを調べるときに見せられるように。

## 7. 凍結の後の errata

文言だけを直す errata は PATCH。振る舞いを変えるものは規則の変更で、上の revision の決まりと [CONTRIBUTING](../CONTRIBUTING.ja.md) に従う。
