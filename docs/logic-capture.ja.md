# Open Embedded Probe — キャプチャ（ロジック / アナログ / ミックスドシグナル）

状態: **提案**（2026-09-25）。前半はロジアナとしての設計で、OEP から切り離して読める。後半でそれを
`oep.fixture.capture` の操作に落とす。番号と幅は仮の値。根拠の実測は [§7](#7-根拠の実測2026-09-25)。
アナログは実測がまだない。名前、モードの分け方、各モードの要否を含め、§8 のとおり検討と実験が残っている。

## 0. 方針

- **プロトコルはフル機能と拡張の余地を定義する。必須の機能はない。** どのモード、どのトリガ、何本のチャネルを
  持つかは probe が選び、describe で宣言する。
- host は describe で候補を知り、configure の応答で「実際に何が効いたか」を知る。
- 設定の項目は TLV で送る。**critical を立てた項目を probe が持たなければ拒否**し、立てていない項目は無視して
  応答に「効かなかった」と返す。host は「これがなければ意味がない」項目にだけ critical を立てる。
- 番号空間は describe と同じ分け方（[能力の宣言のモデル](capability-declaration-model.ja.md) §2）。
  0x01〜0x3F が共通、0x40〜0x7F がこのインターフェースの標準、それより先を拡張に残す（§5.6）。
- 数の上限はプロトコルでは狭めない。チャネル数、詰めたビット幅、区画の数、トリガの段数は、フィールドの幅が許す限り
  probe が宣言した値まで使える。

## 1. 何を作るか

probe の GPIO や ADC で、target の信号を時系列に取る。単体のロジアナ（Saleae、sigrok の fx2lafw など）や
ミックスドシグナルのオシロと同じ使い方ができる設計にし、そのうえで probe ごとの差を宣言で表す。

- 解析（UART / I2C / SPI のデコード）、表示、保存形式（sigrok の `.sr`、VCD）への変換は host が持つ。
- probe はサンプルを取ってためて渡す。
- 時刻はサンプルの番号から出す。サンプルごとの時刻は持たない（時刻付きの形式は拡張、§3.3）。

## 2. ロジアナとしての設計

### 2.1 構成要素

| 要素 | 決めること |
|---|---|
| トラック | 同じクロックで取るチャネルのまとまり。種類はロジック、アナログ、拡張（§2.2） |
| チャネル | トラックに入る信号。どのピンを使うかは plan で割り当てる |
| クロック | 内部のクロックで取る（タイミング）か、外部のクロックで取る（ステート）か（§2.3） |
| サンプルの形 | トラックごとのビットの詰め方（§3） |
| バッファ | probe の中にためる場所 |
| トリガ | いつ取り始めるか。条件を複数組み合わせる（§2.5） |
| 取得モード | 1 回、繰り返し、取り続ける（§2.4） |
| 転送 | ためたものを host が位置で読む（§2.7） |

### 2.2 トラックとミックスドシグナル

1 回のキャプチャは**トラックの集まり**で、全トラックが 1 本の時間軸（t0 = 取得開始、またはトリガ）を共有する。

- トラックごとに、種類、チャネル、クロック（レート）、サンプルの形、読み出しの位置の空間を持つ。
- **ミックスドシグナル**は、ロジックのトラックとアナログのトラックを同じキャプチャに入れたもの。例えば
  ロジック 8 本を 20 MHz、アナログ 1 本を 48 kHz で同時に取る。トリガは全トラックで共有する。
- probe は各トラックの t0 からのずれ（ns、符号付き）と、その不確かさを返す。同じ開始信号で動く周辺回路なら
  ずれは小さく、別々に開始するなら不確かさが大きくなる。host はそれで並べる。
- 同時に持てるトラックの数と組み合わせ（ロジック 1 個 + アナログ 1 個まで、など）は probe が宣言する。

### 2.3 クロック

**内部クロック（タイミング）**。範囲で表せない機材が多い。

| 実装 | 実際のレート | 刻み | 揺れ |
|---|---|---|---|
| ESP32-P4 PARLIO | 源 ÷（整数 + 分子/分母）。源は 160 MHz / 40 MHz / RC | 範囲内ならほぼ任意 | 分数のとき源 1 周期（160 MHz で 6.25 ns） |
| classic ESP32 のソフトウェア sampler | 240 MHz ÷ 整数 | 240M/n の離散値。上の方ほど粗い | ループの揺れ |
| RP2 の PIO（未実装） | sysclk ÷（整数 + 分数/256） | ほぼ任意 | 分数のとき sysclk 1 周期 |
| ADC の連続変換 | 実装ごと（§2.6） | 実装ごと | 実装ごと |

- **選べるレートは最初から宣言で分かるようにする。** 市販のロジアナの UI は、ちょうどの値を打たせるより、
  粗い一覧（1-2-5 刻み、10 MHz 刻みなど）から選ばせる形が多い。probe は describe で次を宣言し、host は問い合わせ
  なしで UI を作れるようにする。
  - **一覧**: 選べる代表的なレートの並び（例: 1k、2k、5k、……、10M、20M、……、160M）。
  - **ちょうどの値**: 範囲内の任意の値を指定できるか（P4 は可、classic ESP32 は 240M/n のみ）。できるなら、
    範囲と刻みの性質を合わせて宣言する。
  - **条件ごとの上限**: 上限はチャネル数（詰めたビット幅）とモードで変わる（P4 はワンショットなら 2 本 160 Msps、
    ストリーミングは線の速さで決まる）。組み合わせごとの上限を表で宣言する。
  - ストリーミングの上限は probe の中の上限（取り込みと詰め直し）だけを宣言し、線の速さは host が測って掛け合わせる
    （同じ probe でもハブや PC で変わるため。wch-protocols の実測では P4 → PC が 120〜390 Mbps）。
- **host は欲しいレートを言い、probe は実際に使うレートを分数（分子 Hz / 分母）で返す。** 240 MHz / 121 のような
  値を丸めずに表すため。
- **設定せずに問い合わせるだけの形も持つ。** 宣言だけでは表しきれない組み合わせ（ミックスドシグナルで合計の
  上限に当たるかなど）を確かめるため。UI の基本は宣言で作る。
- **範囲外は probe が拒否する。** P4 のドライバは範囲外の要求をエラーにせず、源クロックのまま取る（§7.1）。
- 揺れの種類（なし / 分数分周 / ソフトウェア）と大きさ（ns）を返す。host がエッジの時刻の誤差を見積もるため。
- チャネル数によって上限が変わる実装がある。configure の拒否か、問い合わせで分かる。

**外部クロック（ステート）**。target のクロックの線（SPI の SCK、並列バスのストローブ）のエッジで取る。

- クロックの入力ピンは plan の役割（§5.1）で割り当てる。エッジ（立ち上がり / 立ち下がり / 両方）を指定する。
- 取り込むかどうかを決める**修飾の入力**（並列バスの有効信号など）も持てる。
- レートは target が決めるので、時刻はサンプルの番号からは出ない。時刻が要るなら、別のトラックを内部クロックで
  取って並べる。
- P4 の PARLIO は外部クロックと有効信号の入力を持つ（未確認）。

### 2.4 取得モード

| モード | 動き | バッファの使い方 | あふれたとき |
|---|---|---|---|
| ワンショット | 指定サンプル数を取ったら止まる。転送はあとでゆっくり | 1 回ぶん | —（取り終わるまで読まない） |
| リピート | ワンショットを何度も取る。host が読み終えた区画から再利用する | 区画（セグメント）の並び | **取りこぼさない**。空き区画がなければ待ち、待った時間を記録する |
| ストリーミング | 止めずに取り続ける。host は追いかけて読む | リング | 古いものから上書きし、上書きした量を記録する |

どれも任意。モードの番号には拡張の余地を残す。

**バックグラウンドのフラグ**。取っている間に probe が他の処理をできるかを、**モードごとに**宣言する（同じ probe でも
ワンショットは DMA で取れてストリーミングは CPU が要る、といった差があり得るため）。

- できる（P4 の PARLIO は DMA で取る）: 取っている間も debug の線や UART、コンソールの吸い出しが動き、OEP の
  要求にも答える。
- できない（classic ESP32 の sampler は割り込みを止めて CPU で回す）: 取っている間 probe は何にも答えない。
  host は開始の応答で**止まる時間の見込み**を受け取り、その間は要求を送らない。コンソールの吸い出しも止まるので、
  target が詰まることがある。

**リピートとストリーミングの違いは、あふれたときにどちらを守るか。**

- リピートは取れたものを守る。host が「ここまで読んだ」と返す（ack）まで区画を上書きしない。あふれたら止めて待ち、
  次の区画の開始時刻で空白が分かる。
- ストリーミングは新しいものを守る。読むだけでは probe は host の読んだ位置を知らないので、コンソールと同じく
  古いものから押し出し、押し出した印を残す。
- ストリーミングで「止める」方針を選べるようにする（ack を使う）のは拡張にする。

**区画の間は連続を約束しない**。どの実装でも、区画の間には止まる時間（再開までの時間）がある。各区画は開始時刻と
トリガの位置を持ち、host はそれで並べる。区画の中は連続を約束する。リピートでは、次のトリガを受け付けるまでの
保留時間（holdoff）も指定できる。

### 2.5 トリガ

トリガは**段**の並びで、各段は**条件**の組み合わせ。段 1 が成立したら段 2 を待ち、最後の段が成立したらトリガが立つ。

- 段: 条件の結び方（すべて / どれか）、成立の回数（N 回目で成立）、制限時間（超えたら段 1 からやり直す）。
- 条件の種類:

| 種類 | 対象 | 内容 |
|---|---|---|
| レベル | ロジックのチャネル | High / Low |
| エッジ | ロジックのチャネル | 立ち上がり / 立ち下がり / 両方 |
| パターン | ロジックのトラック | マスクと値（ドントケアを含む）。一致した瞬間、または一致が外れた瞬間 |
| しきい値 | アナログのチャネル | 値を上向き / 下向きに横切る |
| ウィンドウ | アナログのチャネル | 範囲に入る / 出る |
| 外部入力 | トリガ入力の役割 | エッジ |
| host | — | host の要求（force）で立てる |
| 時間 | — | 前の段から一定時間後 |

- トリガの位置: トリガより前に残すサンプル数（プリトリガ）と、後に取るサンプル数。
- **トリガ出力**: トリガが立ったら指定の役割のピンにパルスを出す（オシロに渡すなど）。
- **どの種類を何個、何段まで持つかは probe が宣言する。** 持たない条件に critical が付いていれば拒否する。
- 条件を持たない probe でも、即時に取り始めて host が後から探す使い方ができる。

実装ごとの差の例: P4 の PARLIO はパターンを検出する回路を持たない（ソフトウェアで探すにはリングが要る）。PIO は
`wait` 命令で 1 本のレベル / エッジを待てる。ソフトウェア sampler はループの中で比べられるが、そのぶんレートの
上限が下がる。ESP32 の ADC にはしきい値のモニタ機能がある（使えるかは未確認）。

### 2.6 アナログ

ADC で電圧を時系列に取る。音声の 48 kHz 程度までなら多くのマイコンで取れる。取得モード、区画、転送、トリガの枠組みは
ロジックと同じ。違うのは次の点。

| 項目 | ロジック | アナログ |
|---|---|---|
| 1 サンプル | チャネル数ぶんのビット | チャネルごとの ADC の値 |
| 複数チャネルの取り方 | 同時 | **多くは順番に切り替え**（マルチプレクサ）。チャネル間にずれがある |
| レートの上限 | チャネル数で変わることがある | **全チャネルの合計**で決まることが多い（1 本 48 kHz なら取れても 2 本では超える） |
| 値の意味 | 0 / 1 | ADC の生の値。電圧への換算は宣言から host が行う |

ADC の連続変換（DMA）の範囲。ESP32 系は soc_caps の値、RP2 と CH32 はデータシートの目安で、どれも実測ではない。

| 実装 | 合計のサンプルレート | 分解能 | 備考 |
|---|---|---|---|
| ESP32-P4 / S3 | 611 Hz〜83.3 kHz | 12 ビット | 48 kHz は 1 本まで |
| classic ESP32 | 20 kHz〜2 MHz | 9〜12 ビット | DMA は ADC1 のみ |
| RP2040 / RP2350 | 最大 500 kHz | 12 ビット | 1 個の ADC を順番に切り替える |
| CH32（V003 / X035 など） | 数百 kHz〜1 MHz 級 | 10〜12 ビット | probe として使う場合 |

- **チャネル間のずれを返す。** 順番に切り替える実装では、チャネル k のサンプルは先頭から `k × 変換時間` 遅れる。
  同時サンプリングの実装（ADC を複数使うなど）は 0。
- **値は生のまま送る。** 較正の形は probe によって違う。probe は基準電圧、減衰、測れる電圧の範囲、較正の形
  （2 点の値など）を宣言し、換算は host がする。
- 減衰（ESP32 の 0 / 2.5 / 6 / 11 dB）などのアナログの前段の設定は、チャネルごとに configure で指定する。

### 2.7 転送

- **host が読みに行く。** probe から勝手に送る通知はない（[コンソールのストリーム](console-stream.ja.md)と同じ）。
- **トラックごとに位置で読む。** 読んでも消えない。応答が失われても、同じ位置でもう一度読めば同じデータが返る。
- **複数の読み出しを同時に出してよい。** probe は届いた順にバッファから直接送る。読み出しごとに probe がメモリを
  持つ必要はない。
- **読み出しはロックなし。** 状態を変えないので、他の host のロック中でも読める。
- 速さは「1 回で読める量 × 同時に出せる本数」で決まる（§7.2）。HS では 16 KiB 以上 × 4 本以上で上限に届く。
  そのため 1 回で読める量は、probe が frame に組み立てずに送れる大きさにする（応答の本体はバッファから直接流す）。
- 圧縮（ランレングスなど）は拡張の形式として宣言する（§3.3）。

ストリーミングが続くかどうかは host が計算する。全トラックの `レート × 詰めたビット幅 ÷ 8` の和がリンクの速さを
超えれば、そのうち押し出しが起きる。

| リンク | 実測の上限 |
|---|---|
| UART 115200（classic ESP32） | 約 11 KiB/s |
| USB-Serial/JTAG（P4、FS） | 約 810 KiB/s |
| HS vendor bulk（P4、usbip 経由、ハブ経由） | 約 34.8 MB/s |

### 2.8 PulseView / sigrok との連携

- **`.sr` に保存するだけなら、プロトコルは何でもよい。** host が取ったものを変換する（`.sr` は zip で、中身は
  metadata とチャネルごとのデータ）。wch-protocols の実験では、ストリーミング中は詰めたまま一時ファイルに追記し、
  終わってから変換すると、受け側が律速にならない（E082）。
- **PulseView にリアルタイムで渡す場合は、間に入れるプロトコルで仕様が決まる。** stock の PulseView / libsigrok が
  話せる既存のドライバを host 側で演じて、OEP との間を仲介する形になる。

| 仲介の形 | stock で動くか | 決まってしまう仕様 |
|---|---|---|
| BeagleLogic の TCP（`beaglelogic:conn=tcp-raw/…`） | 動く（wch-protocols E077 / E080 で実機まで通した） | ロジックのみ、16 本まで（1 サンプル 1 or 2 バイト）、レートはドライバの一覧（100 MHz まで）、トリガはほぼ持たない、取り続けて client が止める |
| SUMP（`ols`）を COM ポートで | 動く見込み（未確認） | ロジックのみ、32 本まで、レートは 100 MHz ÷ 整数、サンプル数 24 ビット、4 段のトリガ、ワンショットのみ |
| SUMP を TCP で | libsigrok を git から入れる必要がある | SUMP と同じ |
| 自前の libsigrok ドライバ | 配布が要る | OEP の仕様をそのまま出せる |

- どの形でも、**アナログとミックスドシグナルは stock の経路に載らない**。
- BeagleLogic の形は「client が止めるまで送り続ける」ので、1 回のバッファより長く見るにはストリーミングが要る。
  **ストリーミングの要否（§8）は、この連携を目標にするかで変わる。**
- OEP の仕様は PulseView の経路に合わせて狭めない。仲介する host が、宣言から載せられる部分だけを出す。

## 3. データの形

### 3.1 ロジック

- 1 サンプル = 詰めたビット幅 w。**w はプロトコルでは任意**（u16）。probe は使える w を宣言する
  （P4 の PARLIO なら 1/2/4/8/16、ソフトウェア sampler なら 8 など）。
- チャネル k がサンプルの k ビット目（k は plan の役割の順）。
- バイトの中は LSB が先（サンプル i は、ビット位置 `i × w` から始まる）。使わないビットは 0。

### 3.2 アナログ

- 1 値 = 容器のビット幅（8 / 16 / 32、little endian）に右詰め。有効なビット数は configure の応答で返す。
- 1 サンプル = 有効なチャネルを役割の順に並べたもの（2 本なら a、b、a、b……）。
- 実装が別の形で取る場合（ESP32 の DMA はチャネル番号付きの 4 バイト）は、probe が詰め直す。詰め直せないなら、
  その形を拡張の形式として宣言する。

### 3.3 拡張の形式

形式は番号で指定する。標準はロジックの詰めた形（§3.1）とアナログの容器の形（§3.2）。拡張の例:

- ランレングス（変化がない間を数で表す）。変化の少ない信号で転送量が大きく減る。
- エッジの時刻（変化したときだけ、時刻とチャネルの値を記録する）。PIO やタイマーのキャプチャで作りやすい。
- 実装の生の形（ESP32 の ADC の DMA の 4 バイトなど）。

## 4. 区画と印

リピートとストリーミングは、トラックごとの**位置の付いたバイトの並び**として見せる（[コンソールのストリーム](console-stream.ja.md)
と同じ考え方）。ワンショットは区画が 1 個だけのもの。区画はトラックをまたいで共通。

```text
segment : serial(u32), start_us(u32), trigger_index(u32), flags(u8),
          [track(u8), position(u32), samples(u32)] × トラック数
```

| フィールド | 意味 |
|---|---|
| serial | 取得開始からの区画の通し番号 |
| start_us | 区画の最初のサンプルの時刻（probe の起動からの µs、一周を考慮して比べる） |
| trigger_index | 区画の中でトリガが立ったサンプルの番号（基準のトラックで数える） |
| flags | bit0 待った（空き区画がなく、前の区画との間が再開時間より長い）、bit1 押し出された、bit2 短い |
| position | そのトラックでの区画の先頭のバイト位置（取得開始から通し、一周したら 0 に戻る） |
| samples | そのトラックでの区画のサンプル数 |

- ストリーミングでは、区画は probe の都合の区切り（DMA の 1 回ぶんなど）。区画の間が詰まっていれば連続、
  空いていれば取れなかった時間。
- 区画の情報は本文とは別の小さなリングにためる。

## 5. OEP への落とし込み（`oep.fixture.capture`）

ロジック、アナログ、ミックスドシグナルを 1 つのインターフェースで扱う。ロジックだけの probe はロジックの
トラックだけを宣言する。

### 5.1 役割（plan）

plan の役割は u8 なので、次のように分ける。1 つのインターフェースで使えるのはロジック 128 本、アナログ 64 本まで。
それを超える probe は同じインターフェースを複数（instance 違い）出す。

| role | 意味 |
|---|---|
| 0x00〜0x7F | ロジックのチャネル 0〜127 |
| 0x80〜0xBF | アナログのチャネル 0〜63 |
| 0xC0 | 外部クロック入力（ステート） |
| 0xC1 | 修飾の入力（有効信号） |
| 0xC2 | トリガ入力 |
| 0xC3 | トリガ出力 |
| 0xC4〜0xDF | 標準の予備 |
| 0xE0〜0xFF | 拡張 |

### 5.2 操作

| op | 名前 | 要求 | 応答 | ロック |
|---:|---|---|---|---|
| 0x01 | configure | 設定の TLV の並び（§5.3） | 実際の値の TLV の並び（§5.4） | 必要（問い合わせのみなら不要） |
| 0x02 | start | — | blocking_ms(u32)（0 = 取っている間も答える） | 必要 |
| 0x03 | stop | — | — | 必要 |
| 0x04 | force | — | —（host の条件を成立させる） | 必要 |
| 0x05 | status | — | state(u8)、serial_done(u32)、flags(u8)、[track(u8)、write_pos(u32)] の並び | 不要 |
| 0x06 | read | track(u8)、position(u32)、max(u32) | position(u32)、flags(u8: more、gap)、data | 不要 |
| 0x07 | segments | from_serial(u32) | 区画の情報の並び（§4） | 不要 |
| 0x08 | ack | serial(u32) | —（この区画までを再利用してよい。リピート） | 必要 |

- state: 0 未設定、1 設定済み、2 トリガ待ち、3 取得中、4 完了、5 待機中（空き区画なし）、6 エラー。
- read の max は u32。HS で 1 回 16 KiB 以上読むため。
- read で要求した位置がもう押し出されていれば、応答の position が先に進み、flags の gap が立つ。

### 5.3 configure の TLV

| tag | 名前 | 値 |
|---|---|---|
| 0x40 | mode | u8（1 ワンショット、2 リピート、3 ストリーミング、0x40〜 拡張） |
| 0x41 | query | —（設定せずに実際の値だけ返す） |
| 0x42 | track | track(u8)、kind(u8: 1 ロジック、2 アナログ、0x40〜 拡張)、format(u8)、first_role(u8)、roles(u8) |
| 0x43 | rate | track(u8)、rate_hz(u32)（アナログはチャネルあたり） |
| 0x44 | external_clock | track(u8)、edge(u8)、qualifier(u8: 0 なし / 1 High で有効 / 2 Low で有効) |
| 0x45 | samples | track(u8)、samples(u32)（1 区画あたり。ストリーミングは省略） |
| 0x46 | segments | u32（リピートの区画の数） |
| 0x47 | holdoff_us | u32 |
| 0x48 | trigger_position | pre(u32)、post(u32)（基準のトラックのサンプル数） |
| 0x49 | trigger_stage | stage(u8)、combine(u8: 0 すべて / 1 どれか)、count(u32)、timeout_us(u32) |
| 0x4A | trigger_condition | stage(u8)、type(u8)、target(u8: role か track)、params（type ごと） |
| 0x4B | trigger_out | role(u8)、pulse_us(u32)、polarity(u8) |
| 0x4C | analog_frontend | role(u8)、attenuation(u8)、ほか（実装の値） |

- ロジックのトラックのチャネルは `first_role` から `roles` 本（plan で割り当てた役割）。
- **critical を立てた TLV を probe が持たなければ、configure 全体を拒否する**（どの tag かを応答で示す）。
  立てていなければ無視して、応答の `ignored` に載せる。

### 5.4 configure の応答の TLV

| tag | 名前 | 値 |
|---|---|---|
| 0x50 | actual_rate | track(u8)、num(u32)、den(u32) |
| 0x51 | layout | track(u8)、bits_per_sample(u16)、valid_bits(u8)、format(u8) |
| 0x52 | timing | track(u8)、offset_ns(i32)、uncertainty_ns(u32)、jitter_ns(u32)、channel_skew_ns(u32) |
| 0x53 | actual_samples | track(u8)、samples(u32) |
| 0x54 | blocking_ms | u32（取っている間 probe が答えない時間の見込み。0 なら答える） |
| 0x55 | ignored | tag(u8) の並び（効かなかった項目） |

### 5.5 describe で宣言するもの

| tag | 名前 | 値 |
|---|---|---|
| 0x06 | features | 共通のビット。bit1 問い合わせ、bit2 外部クロック、bit3 トリガ出力、bit4 force |
| 0x40 | modes | mode(u8)、background(u8: 1 = 取っている間も答える) の並び |
| 0x41 | track_kind | kind(u8)、max_tracks(u8)、max_roles(u8)、formats(ビット)、bits_per_sample の候補 |
| 0x42 | track_combination | 同時に使えるトラックの組（kind の並び）。書かなければ 1 トラックのみ |
| 0x43 | rate_range | kind(u8)、min_hz(u32)、max_hz(u32)、steps(u8: 0 ほぼ任意 / 1 源 ÷ 整数 / 2 列挙)。**この間が全部設定できるとは限らない** |
| 0x44 | buffer | kind(u8)、max_samples(u32、ワンショット)、segment_max(u32)、segment_count(u32)、ring_bytes(u32) |
| 0x45 | rearm_us | u32（区画の間に止まる時間の目安） |
| 0x46 | trigger_types | 条件の種類のビット |
| 0x47 | trigger_limits | max_stages(u8)、max_conditions(u8)、max_pre(u32) |
| 0x48 | analog | 基準電圧(mV)、測れる範囲、減衰の候補、較正の形、合計レートの上限、同時サンプリングか |
| 0x03 | max_length | 1 回の read で返せる最大長（共通タグ。ただし u16 なので、超えるなら 0x49 を使う） |
| 0x49 | max_read | u32 |

### 5.6 拡張の余地

- モード、トラックの種類、形式、トリガの条件の種類は、それぞれ 0x40 以降を拡張に残す。
- 役割は 0xE0〜0xFF を拡張に残す。
- configure と describe の TLV は 0x60〜0x7F を拡張に残す。
- 大きく違う取得方式（プロトコルアナライザのように probe がデコードまでするもの）は、このインターフェースを
  広げず、別のインターフェースにする。

### 5.7 使い方の例

```text
ワンショット（P4、ロジック 2 本、20 MHz）
  plan_apply(capture: role0 = GPIO4, role1 = GPIO5)
  configure(mode=1, track(0, logic, first_role=0, roles=2), rate(0, 20 MHz), samples(0, 200000))
    → actual_rate(0, 20000000/1), layout(0, 2 bits), blocking_ms 0
  start → status をポーリング（state = 4 まで）。その間も他の操作ができる
  read(0, 0, 16384) を 4 本同時に出して最後まで読む

リピート（I2C のトランザクションを 1 本ずつ）
  configure(mode=2, track(0, logic, 0, 2), rate(0, 4 MHz), samples(0, 8192), segments(16),
            trigger_stage(0, all, 1, 0), trigger_condition(0, edge-falling, role1), trigger_position(256, 7936))
  start → segments(from) で終わった区画を知る → read で読む → ack(serial)
  ack が遅れると state = 5 になり、次の区画の flags bit0 が立つ

ミックスドシグナル（UART の送信 1 本と電源電圧 1 本）
  plan_apply(capture: role0 = GPIO4, role0x80 = GPIO16)
  configure(mode=1, track(0, logic, 0, 1), rate(0, 1 MHz), samples(0, 100000),
                    track(1, analog, 0x80, 1), rate(1, 48 kHz), samples(1, 4800))
    → timing(1, offset_ns=..., uncertainty_ns=...) で 2 本を並べる

アナログのストリーミング（音声 1 ch、48 kHz × 16 ビット = 96 KB/s）
  configure(mode=3, track(0, analog, 0x80, 1), rate(0, 48000), analog_frontend(0x80, 11 dB))
  start → read(0, pos, max) で追いかける。USB-Serial/JTAG（810 KiB/s）で余裕、UART 115200（11 KiB/s）では続かない
```

## 6. 実装ごとの見込み（どれを選ぶか）

| 実装 | モード | バックグラウンド（モードごと） | トラック | トリガ |
|---|---|---|---|---|
| P4 PARLIO + ADC | ワンショット（1 回の受信は 65,535 バイトまで。partial receive で長く取れる）、リピート、ストリーミング（wch-protocols で 2 本 160 Msps / 8 本 80 Msps を欠損なしで PC へ送った実績。ただし OEP のポーリングで同じ速さが出るかは未確認） | 3 つともあり（DMA）の見込み | ロジック 1 + アナログ 1 の見込み（同時開始のずれは未確認） | host、外部クロック（未確認） |
| classic ESP32 sampler | ワンショットのみ | なし（割り込みを止める） | ロジック 1 | ループ内の比較なら可能（レートが下がる） |
| RP2 PIO + DMA（未実装） | 3 つとも（DMA の連鎖で区画の間も途切れない見込み） | 3 つともあり の見込み | ロジック 1 + アナログ 1 | PIO の `wait` で 1 本のレベル / エッジ |

P4 のストリーミングの実績（wch-protocols）: E078 で 2 本 86 Msps を継ぎ目なく、E113 / E121 で 2 本 160 Msps を
欠損 0、E121 で 8 本 80 Msps（高速 3 本 + 1/64 に間引いた 5 本）をバイト一致。いずれも partial receive のリングを
ISR で吸い出し、PSRAM の FIFO を経て vendor bulk で送る形で、OEP のポーリングではない。

## 7. 根拠の実測（2026-09-25）

### 7.1 P4 PARLIO のレート（80f1、arduino-esp32 3.3.12）

- 分周レジスタを読むと、ドライバは分数分周を使う。範囲内なら PLL 160 MHz 源でも XTAL 40 MHz 源でも要求どおり
  （33 MHz → 4+28/33、7 MHz → 22+6/7）。
- 範囲は源から源 ÷ 256 まで。PLL 源の 625 kHz（ちょうど 256）は失敗した。
- **範囲外はエラー 0 のまま分周 1（源クロック）で取る。** XTAL 源で 100 kHz / 60 MHz を要求すると 40 MHz で
  取っていた（1 MHz の矩形波を同じピンでループバックして確認）。
- RC_FAST 源は較正値を使い、要求から +5.2%。取ったデータにも揺れが見えた。
- 幅 1/2/4/8/16 はどれも 160 MHz まで設定を受け付ける（実際に取れるかは未確認）。

### 7.2 転送（ポーリングの損）

HS vendor bulk（P4 80f1、EspUsbDevice 2.5.1 buffered、usbip / WSL、ハブ経由）。{位置, 長さ} の要求に長さぶん返す
scratch のファームで、1 本の巨大な要求（= ストリーム）と、多数の要求（= ポーリング）を比べた。

| 応答 | 読みの URB 1 本 | 4 本 | 8 本 |
|---:|---|---|---|
| 1 KiB | 4.4 / 4.1 MB/s | 11.6 / 13.0 | 15.8 / 13.6 |
| 4 KiB | 12.3 / 11.3 | 33.0 / 33.4 | 34.7 / 33.9 |
| 16 KiB | 19.2 / 20.8 | 34.8 / 34.1 | 34.8 / 34.0 |
| 64 KiB | 26.2 / 26.8 | 34.7 / 34.5 | 34.8 / 34.7 |

（ストリーム / ポーリング。ポーリングは同時に出す要求の本数を変えた中の最良。全条件で化け 0）

- host が読みの URB を 4 本以上出し、応答が 16 KiB 以上なら、ポーリングはストリームと 2% 以内。
- 遅くなる原因は、URB を 1 本ずつしか出さないこと（usbip で URB あたり約 0.3 ms）と、応答の小ささ。
- USB-Serial/JTAG（FS）では、1 KiB を 2 本以上同時に出して生の 855 KiB/s の 95%（811 KiB/s）。

### 7.3 64 KiB を超える取り方（P4）

1 MHz の矩形波を 20 MHz、1 本で取り、ランの長さが 10 以外になる場所を数えた。

- 1 回の受信（65,408 バイト、内部 SRAM / PSRAM とも）: 途切れなし。
- 65,408 バイトの受信を 2 / 4 / 16 個積む: 区画の境界ごとに 1 か所ずつ途切れる（数サンプル。周期信号なので
  1 µs の端数としてしか分からない）。
- partial_rx（128 KiB のリング、eof 16 KiB）: 止めた後にリングをそのまま読むと、約 7 か所で途切れて見えた。
  **これは partial receive が途切れる根拠にならない。** wch-protocols の E078 / E113 / E121 は、ISR で区切りごとに
  吸い出す形で途切れなしを検証している。今回の読み方（吸い出さずに止めて読む、キャッシュの扱い）が原因の見込み。
- 8 MiB を 1 回で受信しようとすると、ドライバの中でスタック保護フォールトになって落ちる。

## 8. 未決（検討・実験が必要）

この文書の名前、モードの分け方、各モードが要るかどうかは、どれも決まっていない。

設計:

1. 名前（インターフェース名、モード名、「区画」「トラック」などの用語）。
2. ストリーミングが要るか。リピートを区画の間を詰めて回せば代わりになるか、それとも別に要るか（用途と実測で決める）。
   PulseView にリアルタイムで渡すこと（§2.8）を目標にするなら要る。
2a. レートの宣言の形（一覧、ちょうどの値の可否、条件ごとの上限の表）と、一覧の既定（1-2-5 刻みか 10 MHz 刻みか）。
3. リピートとストリーミングを 1 つのモードにまとめ、あふれたときの方針（止める / 上書き）だけを選ぶ形にできるか。
4. ロジック、アナログ、ミックスドシグナルを 1 つのインターフェースにするか、分けるか。
5. レートの問い合わせを configure のフラグにするか、別の op にするか。
6. 区画の開始時刻の分解能（µs で足りるか。区画どうしをサンプル単位で並べたい場面があるか）。
7. トリガの段と条件の表し方（TLV の形、params の中身）。
8. 役割の割り振り（ロジック 128 本、アナログ 64 本の分け方でよいか）。
9. アナログの較正の渡し方（2 点の値で足りるか、ESP32 の曲線の係数をそのまま渡すか）。

実験:

10. P4 の幅 8/16 を高レートで実際に取れるか。
11. classic ESP32 sampler の実際の揺れ。
12. P4 で、取っている間に他の処理（debug の線、UART、OEP の応答）が本当に止まらないか。モードごとに。
13. P4 の PARLIO の外部クロックと有効信号の入力。
14. ADC の連続変換（P4 / classic ESP32 / RP2）: 実際のレートと刻み、チャネル間のずれ、値の揺れ、48 kHz を連続で
    取り続けられるか（DMA の区切りで途切れないか）。
15. ミックスドシグナル: P4 で PARLIO と ADC を同時に始めたときのずれ。
16. ストリーミングを 64 KiB の受信を積む形で回したときの、区画の間の欠けの大きさ（周期でない信号で測る）。
17. **ポーリングで 300 Mbps 級が出るか。** 今日の測定（§7.2）は buffered build で、ストリームもポーリングも 34.8 MB/s
    （278 Mbps）で頭打ちだった。2 本 150 Msps（300 Mbps）は、wch-protocols では zero-copy の vendor bulk で出ている。
    同じ direct 転送の上でポーリングを測る。
