# Open Embedded Probe — キャプチャ（ロジック / アナログ / ミックスドシグナル）

状態: **提案**（2026-09-25）。前半はロジアナとしての設計で、OEP から切り離して読める。後半でそれを
`oep.fixture.capture` の操作に落とす。番号と幅は仮の値。根拠の実測は [§7](#7-根拠の実測2026-09-25)。
アナログは実測がまだない。名前、モードの分け方、各モードの要否を含め、§8 のとおり検討と実験が残っている。

## 0. 方針

- **プロトコルはフル機能と拡張の余地を定義する。必須の機能はない。** どのモード、どのトリガ、何本のチャネルを
  持つかは probe が選び、describe で宣言する。
- host は describe で候補を知り、configure の応答で「実際に何が効いたか」を知る。
- 設定の項目は TLV で送る。**critical を立てた項目を probe が持たなければ拒否**し、立てていない項目は無視して
  応答に「効かなかった」と返す。host は「これがなければ意味がない」項目にだけ critical を立てる。
- 番号空間は describe と同じ分け方（[能力の宣言のモデル](capability-declaration-model.ja.md) §2）。
  0x01〜0x3F が共通、0x40〜0x7F がこのインターフェースの標準、それより先を拡張に残す（§5.6）。
- 数の上限はプロトコルでは狭めない。チャネル数、詰めたビット幅、区画の数、トリガの段数は、フィールドの幅が許す限り
  probe が宣言した値まで使える。

### 0.1 基本と拡張の線引き（案、2026-09-25）

プロトコルは広めに定義して probe が取捨選択する。ただし広げすぎると **host がすべての組み合わせに対応しなければ
ならず辛い**。そこで、基本（BASIC）に入れるものと、別の定義に分けるものを次の基準で分ける。

**基準**

1. **基本に入れるものは、どの host も全部実装できる量にする。** host は基本の中で probe が選んだものに、分岐なしで
   ついていけること。
2. **基本の外のものは、それぞれ独立した定義（別の名前のインターフェース、または独立した features のビットと文書）に
   する。** 知らない host は無視でき、基本の動作は変わらない。
3. 時間軸やデータの意味を変えるもの（外部クロックで時刻がなくなる、複数トラックの時刻合わせ）は基本に入れない。
4. 1 つの実装でしか意味がないもの（P4 の間引き codec、ESP32 の ADC の生のレコード）は基本に入れない。

**案**

| 項目 | 基本 | 別の定義 |
|---|---|---|
| インターフェース | `oep.fixture.capture`（ロジック）と `oep.fixture.analog`（アナログ）。**操作の番号と形は同じ**、1 つのインターフェースは 1 トラック | **ミックスドシグナル**（複数トラックの同時開始と時刻合わせ） |
| モード | ワンショット、リピート、ストリーミング（どれも任意、§2.4 の定義）、モードごとのバックグラウンドのフラグ | 投機的な先行取得（host が頼む前に取っておく） |
| クロック | 内部クロック（タイミング） | **外部クロック（ステート）**、修飾の入力 |
| レート | 方式 C（§2.10）: 宣言は目安、configure の応答が正、問い合わせ | — |
| トリガ | 即時、force、1 本のレベル / エッジ（アナログは 1 本のしきい値の横切り）、プリトリガのサンプル数 | **多段・パターン・ウィンドウ・回数・時間**の組み合わせ、トリガ入力 / 出力のピン |
| データの形 | **§3.0 の規則 1 つ**。幅とチャネルの位置は probe が決めて返す | ランレングス、エッジの時刻、チャネルごとの間引き（E106）、実装の生のレコード（ESP32 の ADC の 4 バイト）、16 ビットを超える ADC |
| 区画と印 | 区画の通し番号、開始時刻（µs）、トリガの位置、待った / 押し出された | — |
| アナログの換算 | 生の値と、1 LSB あたりの電圧とオフセット（1 次式） | 曲線の較正（ESP32 の係数など） |
| チャネル数 | ロジック 128 本、アナログ 64 本まで（1 インターフェース） | それを超える構成 |

**データの形は §3.0 の 1 つの規則**（2026-09-25 の議論）。probe は取れる単位のまま送れるよう、1 サンプルの幅と
各チャネルの位置を probe が決めて返す（詰め替えられない probe を考慮）。

**モードは 3 つとも基本**（2026-09-25 の議論で訂正）。一度「リピートはストリーミングの一種として表せる」として外したが、
それは取りながら送れる probe が前提で、取る → 送るを交互にしかできない probe（classic ESP32 の sampler など）はリピートしか
できない。モードは probe が同時にどこまでできるかで分ける（§2.4）。**投機的な先行取得はしない**（probe は host が頼んだ
区画だけを取る）。ワンショットは、リピートの詰め替えや転送が間に合わない probe が選ぶもので、**基本はリピートか
ストリーミングになる**見込み。ストリーミングは probe から送る通知の仕組み（core、別途決める）を使う。

- 基本の形で送れない probe（ESP32 の ADC は 4 バイトのレコードで取る）は、probe が基本の形（16 ビット）に詰め直して
  送る。遅い ADC なら詰め直しは軽い（83 kHz × 4 バイト = 333 KB/s）。高速のロジック（PARLIO）は、取得した形が
  そのまま基本の形になる。§3.4 の「取得した形のまま送る」は、基本の形と一致する場合、または拡張の形式を host が選んだ
  場合に当てはまる。
- ロジックとアナログを別のインターフェースにするのは、[開発の指針](development-guidelines.ja.md)の「service は単体で
  意味が閉じる最小単位で切る」とも合う。同時に動かしたときに開始がそろわない、という指針に書かれた弱点は、plan の
  `start_together`（0x91、[能力の宣言のモデル](capability-declaration-model.ja.md)）で一緒に開始する形が既にある。
  ミックスドシグナルの定義は、その上に「トラック間のずれと不確かさを返す」を足すだけで済む見込み。
- 別の定義の文書は、必要になったときに 1 つずつ書く（名前だけ先に作らない）。候補の順は、ミックスドシグナル、
  多段トリガ、外部クロック。

## 1. 何を作るか

probe の GPIO や ADC で、target の信号を時系列に取る。単体のロジアナ（Saleae、sigrok の fx2lafw など）や
ミックスドシグナルのオシロと同じ使い方ができる設計にし、そのうえで probe ごとの差を宣言で表す。

- 解析（UART / I2C / SPI のデコード）、表示、保存形式（sigrok の `.sr`、VCD）への変換は host が持つ。
- probe はサンプルを取ってためて渡す。
- 時刻はサンプルの番号から出す。サンプルごとの時刻は持たない（時刻付きの形式は拡張、§3.3）。

## 2. ロジアナとしての設計

### 2.1 構成要素

| 要素 | 決めること |
|---|---|
| トラック | 同じクロックで取るチャネルのまとまり。種類はロジック、アナログ、拡張（§2.2） |
| チャネル | トラックに入る信号。どのピンを使うかは plan で割り当てる |
| クロック | 内部のクロックで取る（タイミング）か、外部のクロックで取る（ステート）か（§2.3） |
| サンプルの形 | トラックごとのビットの詰め方（§3） |
| バッファ | probe の中にためる場所 |
| トリガ | いつ取り始めるか。条件を複数組み合わせる（§2.5） |
| 取得モード | 1 回、繰り返し、取り続ける（§2.4） |
| 転送 | ためたものを host が位置で読む（§2.7） |

### 2.2 トラックとミックスドシグナル

1 回のキャプチャは**トラックの集まり**で、全トラックが 1 本の時間軸（t0 = 取得開始、またはトリガ）を共有する。

- トラックごとに、種類、チャネル、クロック（レート）、サンプルの形、読み出しの位置の空間を持つ。
- **ミックスドシグナル**は、ロジックのトラックとアナログのトラックを同じキャプチャに入れたもの。例えば
  ロジック 8 本を 20 MHz、アナログ 1 本を 48 kHz で同時に取る。トリガは全トラックで共有する。
- probe は各トラックの t0 からのずれ（ns、符号付き）と、その不確かさを返す。同じ開始信号で動く周辺回路なら
  ずれは小さく、別々に開始するなら不確かさが大きくなる。host はそれで並べる。
- 同時に持てるトラックの数と組み合わせ（ロジック 1 個 + アナログ 1 個まで、など）は probe が宣言する。

### 2.3 クロック

**内部クロック（タイミング）**。範囲で表せない機材が多い。

| 実装 | 実際のレート | 刻み | 揺れ |
|---|---|---|---|
| ESP32-P4 PARLIO | 源 ÷（整数 + 分子/分母）。源は 160 MHz / 40 MHz / RC | 範囲内ならほぼ任意 | 分数のとき源 1 周期（160 MHz で 6.25 ns） |
| classic ESP32 のソフトウェア sampler | 240 MHz ÷ 整数 | 240M/n の離散値。上の方ほど粗い | ループの揺れ |
| RP2 の PIO（未実装） | sysclk ÷（整数 + 分数/256） | ほぼ任意 | 分数のとき sysclk 1 周期 |
| ADC の連続変換 | 実装ごと（§2.6） | 実装ごと | 実装ごと |

- **選べるレートは最初から宣言で分かるようにする。** 市販のロジアナの UI は、ちょうどの値を打たせるより、
  粗い一覧（1-2-5 刻み、10 MHz 刻みなど）から選ばせる形が多い。probe は describe で次を宣言し、host は問い合わせ
  なしで UI を作れるようにする。
  - **一覧**: 選べる代表的なレートの並び（例: 1k、2k、5k、……、10M、20M、……、160M）。市販品と sigrok の慣習
    （調査、2026-09-25）: libsigrok のドライバはレートを「固定の一覧」か「最小・最大・刻み」で出し、PulseView は
    刻み 1 のとき 1-2-5 のドロップダウン、それ以外は数値入力にする。fx2lafw は 48 MHz の約数の一覧（20k〜48M）、
    DSLogic や Kingst は 1-2-5、Saleae Logic 8 は 100/50/40/25/20/10/8/5/4/2/1 MS/s（100/50/40 はチャネル数の制限付き）、
    Pro 16 は 500 MS/s（4 本以下）から。**チャネル数を増やすと上限が下がる**のは市販品も同じ。
  - **ちょうどの値**: 範囲内の任意の値を指定できるか（P4 は可、classic ESP32 は 240M/n のみ）。できるなら、
    範囲と刻みの性質を合わせて宣言する。
  - **条件ごとの上限**: 上限はチャネル数（詰めたビット幅）とモードで変わる（P4 はワンショットなら 2 本 160 Msps、
    ストリーミングは線の速さで決まる）。組み合わせごとの上限を表で宣言する。
  - ストリーミングの上限は probe の中の上限（取り込みと詰め直し）だけを宣言し、線の速さは host が測って掛け合わせる
    （同じ probe でもハブや PC で変わるため。wch-protocols の実測では P4 → PC が 120〜390 Mbps）。
- **host は欲しいレートを言い、probe は実際に使うレートを分数（分子 Hz / 分母）で返す。** 240 MHz / 121 のような
  値を丸めずに表すため。
- **設定せずに問い合わせるだけの形も持つ。** 宣言だけでは表しきれない組み合わせ（ミックスドシグナルで合計の
  上限に当たるかなど）を確かめるため。UI の基本は宣言で作る。
- **範囲外は probe が拒否する。** P4 のドライバは範囲外の要求をエラーにせず、源クロックのまま取る（§7.1）。
- 揺れの種類（なし / 分数分周 / ソフトウェア）と大きさ（ns）を返す。host がエッジの時刻の誤差を見積もるため。
- チャネル数によって上限が変わる実装がある。configure の拒否か、問い合わせで分かる。

**外部クロック（ステート）**。target のクロックの線（SPI の SCK、並列バスのストローブ）のエッジで取る。

- クロックの入力ピンは plan の役割（§5.1）で割り当てる。エッジ（立ち上がり / 立ち下がり / 両方）を指定する。
- 取り込むかどうかを決める**修飾の入力**（並列バスの有効信号など）も持てる。
- レートは target が決めるので、時刻はサンプルの番号からは出ない。時刻が要るなら、別のトラックを内部クロックで
  取って並べる。
- P4 の PARLIO は外部クロックと有効信号の入力を持つ（未確認）。

### 2.4 取得モード

モードは、probe が同時にどこまでできるかで分ける。どれも任意で、probe が持つものを宣言し、host は 3 つすべてに対応する。

| モード | probe ができること | 動き | 取ったデータ |
|---|---|---|---|
| ワンショット | 取る領域が 1 つ。取りながら詰め替えや転送ができない | host が開始を頼むと N サンプル取って止まる | 次の開始で消える。host は読み終えてから次を頼む |
| リピート | 取る領域（区画）が 2 つ以上 | host が区画を 1 つ頼むたびに、その 1 区画だけ取る（トリガがあれば待つ）。区画の数の範囲で、前の区画を読んでいる間に次を取れる | host が解放するまで読める |
| ストリーミング | 取りながら同時に送れる | 止めずに取り続け、host が与えたクレジットの範囲で probe から送る | 送ったもの。クレジットが足りなければ取得を止め、空白を印で示す |

- **投機的な先行取得はしない。** probe が取り始めるのは host が頼んだときだけ。リピートで空いている区画があっても、
  頼まれていない区画は取らない。ストリーミングも、クレジットの範囲を超えて先に取りためない。
- 区画の解放は、区画を使い回すための管理（先取りのためではない）。解放していない区画の数が上限に達したら、次の区画の
  依頼は rejected（busy）。
- ワンショットは、リピートの詰め替えや転送が間に合わない probe が選ぶ。基本はリピートかストリーミングになる見込み。
- ストリーミングは probe から送る通知の仕組み（core）を使う。その仕組みを v1 に入れるかは別に決める（§8）。

**バックグラウンドのフラグ**。取っている間に probe が他の処理をできるかを、**モードごとに**宣言する。

- できる（P4 の PARLIO は DMA で取る。classic ESP32 の sampler は core 0 で取り、OEP は core 1 で動く。§7.5）: 取っている間も
  debug の線や UART、コンソールの吸い出しが動き、OEP の要求にも答える。
- できない実装（CPU を占有して取り、ほかの処理を同じ CPU で回すもの）: 取っている間 probe は何にも答えない。host は開始の
  応答で**止まる時間の見込み**を受け取り、その間は要求を送らない。

**区画の間は連続を約束しない**。各区画は開始時刻とトリガの位置を持ち、host はそれで並べる。区画の中は連続を約束する。
ストリーミングの連続は、クレジットが足りている間だけ約束する（足りなくなれば印を付けて空白を作る）。

### 2.5 トリガ

トリガは**段**の並びで、各段は**条件**の組み合わせ。段 1 が成立したら段 2 を待ち、最後の段が成立したらトリガが立つ。

- 段: 条件の結び方（すべて / どれか）、成立の回数（N 回目で成立）、制限時間（超えたら段 1 からやり直す）。
- 条件の種類:

| 種類 | 対象 | 内容 |
|---|---|---|
| レベル | ロジックのチャネル | High / Low |
| エッジ | ロジックのチャネル | 立ち上がり / 立ち下がり / 両方 |
| パターン | ロジックのトラック | マスクと値（ドントケアを含む）。一致した瞬間、または一致が外れた瞬間 |
| しきい値 | アナログのチャネル | 値を上向き / 下向きに横切る |
| ウィンドウ | アナログのチャネル | 範囲に入る / 出る |
| 外部入力 | トリガ入力の役割 | エッジ |
| host | — | host の要求（force）で立てる |
| 時間 | — | 前の段から一定時間後 |

- トリガの位置: トリガより前に残すサンプル数（プリトリガ）と、後に取るサンプル数。
- **トリガ出力**: トリガが立ったら指定の役割のピンにパルスを出す（オシロに渡すなど）。
- **どの種類を何個、何段まで持つかは probe が宣言する。** 持たない条件に critical が付いていれば拒否する。
- 条件を持たない probe でも、即時に取り始めて host が後から探す使い方ができる。

実装ごとの差の例: P4 の PARLIO はパターンを検出する回路を持たない（ソフトウェアで探すにはリングが要る）。PIO は
`wait` 命令で 1 本のレベル / エッジを待てる。ソフトウェア sampler はループの中で比べられるが、そのぶんレートの
上限が下がる。ESP32 の ADC にはしきい値のモニタ機能がある（使えるかは未確認）。

### 2.6 アナログ

ADC で電圧を時系列に取る。音声の 48 kHz 程度までなら多くのマイコンで取れる。取得モード、区画、転送、トリガの枠組みは
ロジックと同じ。違うのは次の点。

| 項目 | ロジック | アナログ |
|---|---|---|
| 1 サンプル | チャネル数ぶんのビット | チャネルごとの ADC の値 |
| 複数チャネルの取り方 | 同時 | **多くは順番に切り替え**（マルチプレクサ）。チャネル間にずれがある |
| レートの上限 | チャネル数で変わることがある | **全チャネルの合計**で決まることが多い（1 本 48 kHz なら取れても 2 本では超える） |
| 値の意味 | 0 / 1 | ADC の生の値。電圧への換算は宣言から host が行う |

ADC の連続変換（DMA）の範囲。ESP32 系は soc_caps の値、RP2 と CH32 はデータシートの目安。P4 の実測は §7.4。

| 実装 | 合計のサンプルレート | 分解能 | 備考 |
|---|---|---|---|
| ESP32-P4 / S3 | 611 Hz〜83.3 kHz（設定できる範囲） | 12 ビット | **P4 は 48 kHz 以上で各サンプルが 2 回ずつ出る**（§7.4。実質の上限は 46 kHz 前後） |
| classic ESP32 | 20 kHz〜2 MHz | 9〜12 ビット | DMA は ADC1 のみ |
| RP2040 / RP2350 | 最大 500 kHz（48 MHz、96 サイクル / 変換） | 12 ビット | 1 個の ADC を順番に切り替え、合計で 500 kS/s を分け合う。FIFO 8 段 → DMA |
| CH32（V003 / X035 など） | 数百 kHz〜1 MHz 級 | 10〜12 ビット | probe として使う場合 |

- **チャネル間のずれを返す。** 順番に切り替える実装では、チャネル k のサンプルは先頭から `k × 変換時間` 遅れる。
  同時サンプリングの実装（ADC を複数使うなど）は 0。
- **値は生のまま送る。** 較正の形は probe によって違う。probe は基準電圧、減衰、測れる電圧の範囲、較正の形
  （2 点の値など）を宣言し、換算は host がする。
- 減衰（ESP32 の 0 / 2.5 / 6 / 11 dB）などのアナログの前段の設定は、チャネルごとに configure で指定する。

### 2.7 転送

- **host が読みに行く。** probe から勝手に送る通知はない（[コンソールのストリーム](console-stream.ja.md)と同じ）。
- **トラックごとに位置で読む。** 読んでも消えない。応答が失われても、同じ位置でもう一度読めば同じデータが返る。
- **複数の読み出しを同時に出してよい。** probe は届いた順にバッファから直接送る。読み出しごとに probe がメモリを
  持つ必要はない。
- **読み出しはロックなし。** 状態を変えないので、他の host のロック中でも読める。
- 速さは「1 回で読める量 × 同時に出せる本数」で決まる（§7.2）。HS では 16 KiB 以上 × 4 本以上で上限に届く。
  そのため 1 回で読める量は、probe が frame に組み立てずに送れる大きさにする（応答の本体はバッファから直接流す）。
- 圧縮（ランレングスなど）は拡張の形式として宣言する（§3.3）。
- **ストリーミングでは、まだ取れていない位置を先に要求する。** host は線を空けないよう、取り込みより先の位置の
  読み出しを何本も出しておく。probe はその要求を、データがそろうまで（または制限時間まで）保留して答える。
  すぐに空の応答を返す方式だと、host が空振りの要求を繰り返して線と probe の時間を使う。保留できる本数と
  制限時間は宣言する。
- probe のバッファは、同時に出されている読み出しの合計と、host の遅れの揺れを吸収できる深さが要る
  （37.5 MB/s で 64 KiB × 8 本なら 512 KiB が常に予約され、その上に揺れのぶん）。

ストリーミングが続くかどうかは host が計算する。全トラックの `レート × 詰めたビット幅 ÷ 8` の和がリンクの速さを
超えれば、そのうち押し出しが起きる。

| リンク | 実測の上限 |
|---|---|
| UART 115200（classic ESP32） | 約 11 KiB/s |
| USB-Serial/JTAG（P4、FS） | 約 810 KiB/s |
| HS vendor bulk（P4、usbip 経由、ハブ経由） | 約 34.8 MB/s |

### 2.8 PulseView / sigrok との連携

- **`.sr` に保存するだけなら、プロトコルは何でもよい。** host が取ったものを変換する（`.sr` は zip で、中身は
  metadata とチャネルごとのデータ）。wch-protocols の実験では、ストリーミング中は詰めたまま一時ファイルに追記し、
  終わってから変換すると、受け側が律速にならない（E082）。
- **PulseView にリアルタイムで渡す場合は、間に入れるプロトコルで仕様が決まる。** stock の PulseView / libsigrok が
  話せる既存のドライバを host 側で演じて、OEP との間を仲介する形になる。

| 仲介の形 | stock で動くか | 決まってしまう仕様 |
|---|---|---|
| BeagleLogic の TCP（`beaglelogic:conn=tcp-raw/…`） | 動く（wch-protocols E077 / E080 で実機まで通した） | ロジックのみ、16 本まで（1 サンプル 1 or 2 バイト）、レートはドライバの一覧（100 MHz まで）、トリガはほぼ持たない、取り続けて client が止める |
| SUMP（`ols`）を COM ポートで | 動く見込み（未確認） | ロジックのみ、32 本まで、レートは 100 MHz ÷ 整数、サンプル数 24 ビット、4 段のトリガ、ワンショットのみ |
| SUMP を TCP で | libsigrok を git から入れる必要がある | SUMP と同じ |
| hameg-hmo（SCPI のオシロ、tcp-raw / VXI） | 0.5.2 と git の両方にある（実機未確認） | オシロのモデル表に合わせる（HMO1202 ならアナログ 2 + ロジック 8、ほかに 4 + 16 まで）。**アナログとロジックを同時に載せられる**。取得はフレーム単位（ドライバは RUN / SINGLE を送らず、今あるフレームを取るだけ）。**レートは読み取りのみ**（`:ACQ:SRAT?`）で、PulseView にレートの選択は出ない。電圧レンジと時間軸は 1-2-5 の表の値でないと開けない |
| raspberrypi-pico（テキスト、serial） | git のみ（2022〜）。TCP は git の `serial_tcpraw` 経由 | アナログ 8 + ロジック 32 まで、**ストリーミング**、RLE、レートは設定可 |
| 自前の libsigrok ドライバ | 配布が要る | OEP の仕様をそのまま出せる |

- BeagleLogic と SUMP の形では、**アナログとミックスドシグナルは載らない**。載るのは hameg-hmo（フレーム単位、
  レートは読み取りのみ）と raspberrypi-pico（ストリーミング、git の libsigrok が要る）。
- 調査の詳細（コマンド、なりすましに要ること、他のドライバ）: [キャプチャの机上調査](capture-survey.ja.md)。
- BeagleLogic の形は「client が止めるまで送り続ける」ので、1 回のバッファより長く見るにはストリーミングが要る。
  **ストリーミングの要否（§8）は、この連携を目標にするかで変わる。**
- **ここは「どう見せるか」の段で決める**（ロジアナ自体の設計を先に済ませる）。選択肢は、基本の機能をどれかの
  経路（hameg-hmo など）で実現できる範囲に合わせるか、もっと自由に作って経路への変換は別の機能（host の仲介）に
  するか。

### 2.9 host のユースケース

| ユースケース | host がしたいこと | モード | 要るもの |
|---|---|---|---|
| テストの自動判定（CI / HIL） | sketch の UART の中身とボーレート、PWM の周期と duty、I2C の応答を判定する | ワンショット（即時かエッジ） | **正確な実際のレート**、短い往復（書き込みからキャプチャまで数秒）、デコーダ |
| プロトコルのデコード | UART / I2C / SPI を読む（sigrok のデコーダ、手元に 298 個） | ワンショット、リピート | `.sr` か sigrok の形への変換 |
| タイミングの測定 | パルス幅、周期、エッジ間の時間 | ワンショット | 実際のレート（分数）、揺れの大きさ |
| 対話的に見る | PulseView などで波形を見る | リピート、ストリーミング | 粗い一覧のレート、仲介（§2.8） |
| 保存 | `.sr` に残して後で見る | どれでも | 変換（取得した形 → `.sr`） |
| イベントを待って取る | 特定の条件の前後を取る、何度も | リピート + トリガ | トリガ、プリトリガ、区画の時刻 |
| 長時間の監視 | グリッチや異常を数える | ストリーミング | 押し出しの印、帯域の見積もり |
| アナログ | 音声、電源電圧の変化、DAC / PWM の出力 | どれでも | 実際のレート、較正、値の重複がないこと（§7.4） |
| ミックスドシグナル | GPIO の変化と電圧の変化を並べる | ワンショット | トラック間のずれと不確かさ |

この repo（ArduinoCore-CH32）の用途では、**テストの自動判定が中心**になる。§7.7 の H3 はその形で、sketch の
書き込みから UART の中身とボーレートの判定までを OEP だけで通した。

### 2.10 サンプルレートを誰が刻むか

| 方式 | 内容 | 良い点 | 弱い点 |
|---|---|---|---|
| A. probe が刻む | host は欲しい値を送り、probe が実際の値を返す（configure、問い合わせ） | 実装の癖（P4 の ADC の重複、範囲外で黙って源クロックになる PARLIO）を probe が知っている | 候補を作るのに往復が要る |
| B. host が刻む | probe はレートの作り方（基準クロック、分周の範囲、分数の有無、一覧）を宣言し、host が計算する | 往復なしで UI を作れる | 宣言で表しきれない癖（重複、チャネル数や幅による上限、揺れ）を host が知らない |
| C. 両方 | 宣言は UI の候補を作るための目安、configure の応答が正（probe が刻んだ実際の値） | A と B の良い点 | 宣言と実際が食い違う可能性は残る（応答で分かる） |

- 問い合わせの往復のコスト（§7.7 の H1）: USB の probe は 1 件 0.3〜0.5 ms、UART の probe は 1 件 4.9 ms（まとめても
  速くならない）。一覧 40 件を問い合わせで確かめると、USB で 20 ms、UART で 200 ms。細かく 1000 件なら USB で 0.3 s、
  UART で 4.9 s。**数十件の確認は無駄でも困らない。細かい走査は UART の probe では遅い。**
- ESP32 の ADC の例（§7.4）のように、ドライバが受け付けても中身が正しくない場合がある。host が作り方から計算した
  値だけでは気づけないので、**実際の値と上限は probe が持つべき**。
- **提案: C。** 宣言には粗い一覧、範囲、ちょうどの値を指定できるか、条件ごとの上限を入れる（§2.3）。configure は
  常に実際の値（分数）を返し、テストの判定やタイミングの測定はそれを使う。問い合わせは、宣言で表しきれない組み合わせを
  確かめるためにあり、host が必要なら何度使ってもよい。

## 3. データの形

### 3.0 基本のデータの形（厳密、案）

用語: **ストリーム**は、1 回のキャプチャ（1 区画）で probe が返すバイトの並び。バイト位置 0 から始まる。
**ストリームのビット j** は、バイト `floor(j / 8)` のビット `j mod 8`（ビット 0 = LSB）と定める。

#### ロジック

configure の応答で probe が返す値:

| 値 | 範囲 | 意味 |
|---|---|---|
| `w` | 1, 2, 4, 8, 16, 32 のどれか | 1 サンプルのビット数。probe が選ぶ（チャネル数より大きくてよい） |
| `C` | 1 以上 | チャネル数（plan で割り当てたロジックの役割の数） |
| `pos[k]`（k = 0 … C−1） | 0 ≤ pos[k] < w、互いに異なる | チャネル k（役割の番号の小さい順）の、サンプルの中のビット位置 |
| `N` | 1 以上 | 区画のサンプル数 |

規則:

1. サンプル i（i = 0 … N−1）は、ストリームのビット `i·w` から `i·w + w − 1` まで。
2. サンプル i のチャネル k の値は、ストリームのビット `i·w + pos[k]`。
3. どの `pos[k]` にも当たらないビットの値は**未定義**。host は読まずに無視する（probe は 0 にしなくてよい）。
4. 区画の長さは `ceil(N·w / 8)` バイト。最後のバイトの、`N·w` を超えるビットは未定義。
5. w ≥ 8 のとき、サンプルは `w/8` バイトの little endian の整数と同じになる。w < 8 のとき、1 バイトに `8/w` サンプルが
   入り、若い番号のサンプルが下位ビットに来る。

例:

| 構成 | w | pos | 1 バイトの中身 |
|---|---|---|---|
| P4 PARLIO、1 本 | 1 | [0] | サンプル 0〜7 がビット 0〜7 |
| 1 バイト単位でしか取れない probe、1 本 | 8 | [0] | 1 バイトが 1 サンプル。ビット 1〜7 は未定義 |
| GPIO のポートの 1 バイトをそのまま取る probe、ピンがビット 5 | 8 | [5] | ビット 5 だけが意味を持つ |
| P4 PARLIO、**3 本** | 4 | [0, 1, 2] | ビット 0〜2 = サンプル 2m の ch0〜2、ビット 3 未定義、ビット 4〜6 = サンプル 2m+1 の ch0〜2、ビット 7 未定義 |
| classic ESP32 の sampler、**3 本** | 8 | [0, 1, 2] | 1 バイト 1 サンプル、ビット 3〜7 未定義 |
| P4 PARLIO、9 本 | 16 | [0 … 8] | 2 バイトで 1 サンプル（little endian）、ビット 9〜15 未定義 |

この規則に入らない取り方（RP2 の PIO の自動 push は、32 ビットのワードにサンプルを左詰めする）は、probe が詰め直すか、
別の定義の形式を使う。

#### アナログ

configure の応答で probe が返す値:

| 値 | 範囲 | 意味 |
|---|---|---|
| `s` | 8, 16, 32 のどれか | 1 つの値を入れる枠のビット数 |
| `o`, `b` | 0 ≤ o、1 ≤ b、o + b ≤ s | 枠の中の値の位置（ビット o から b ビット、符号なし） |
| `C` | 1 以上 | チャネル数 |
| `order[m]`（m = 0 … C−1） | チャネルの番号の並べ替え | サンプルの中の m 番目の枠が、どのチャネルか |
| `N` | 1 以上 | 区画のサンプル数 |

規則:

1. 枠は `s/8` バイトの little endian の整数。枠の値の `o` から `o+b−1` ビットが変換の結果（符号なし）。それ以外の
   ビットは未定義（host は無視する）。
2. サンプル i は、枠 `i·C` から `i·C + C − 1` まで。m 番目の枠がチャネル `order[m]`。
3. 区画の長さは `N·C·s/8` バイト。
4. 電圧 = （値 − `zero`）× `scale`。`zero`（値）と `scale`（µV / 1 値）は configure の応答で返す（1 次式。曲線の較正は
   別の定義）。
5. チャネル m の時刻は、サンプルの時刻から `skew[m]` ns 遅れる（順番に切り替える ADC の場合）。

例:

| 構成 | s | o | b | 備考 |
|---|---|---|---|---|
| ESP32-S3 / P4 の ADC（DMA の 4 バイトのレコードのまま） | 32 | 0 | 12 | ビット 13〜16 のチャネル番号などは未定義として無視される。チャネルの順番がパターンどおりであることが条件（崩れる場合は probe が並べ直すか、そのレートを宣言から外す） |
| classic ESP32 の ADC（2 バイトのレコードのまま） | 16 | 0 | 12 | 上位 4 ビット（チャネル番号）は未定義 |
| RP2 の ADC（FIFO の 16 ビット） | 16 | 0 | 12 | |
| RP2 の ADC（8 ビットに縮めたもの） | 8 | 0 | 8 | |



### 3.1 ロジック

- 1 サンプル = 詰めたビット幅 w。**w はプロトコルでは任意**（u16）。probe は使える w を宣言する
  （P4 の PARLIO なら 1/2/4/8/16、ソフトウェア sampler なら 8 など）。
- チャネル k がサンプルの k ビット目（k は plan の役割の順）。
- バイトの中は LSB が先（サンプル i は、ビット位置 `i × w` から始まる）。使わないビットは 0。

### 3.2 アナログ

- 1 値 = 容器のビット幅（8 / 16 / 32、little endian）に右詰め。有効なビット数は configure の応答で返す。
- 1 サンプル = 有効なチャネルを役割の順に並べたもの（2 本なら a、b、a、b……）。
- 実装が別の形で取る場合（ESP32 の DMA はチャネル番号付きの 4 バイト）は、probe が詰め直す。詰め直せないなら、
  その形を拡張の形式として宣言する。

### 3.3 拡張の形式

形式は番号で指定する。標準はロジックの詰めた形（§3.1）とアナログの容器の形（§3.2）。拡張の例:

- ランレングス（変化がない間を数で表す）。変化の少ない信号で転送量が大きく減る。
- エッジの時刻（変化したときだけ、時刻とチャネルの値を記録する）。PIO やタイマーのキャプチャで作りやすい。
- 実装の生の形（ESP32 の ADC の DMA の 4 バイトなど）。

### 3.4 データの持ち方の宣言（取得した形のまま送る）

実装によって、取ったときのデータの並びが違う。

| 実装 | 取ったときの並び |
|---|---|
| P4 PARLIO | 複数チャネルを同時に取り、サンプルごとに並ぶ（interleaved、1 サンプル = w ビット） |
| ESP32 の ADC（DMA） | 変換 1 回ごとに 4 バイト（チャネル番号と 12 ビットの値）。パターンの順に並ぶ |
| wch-protocols E106 の間引き codec | ブロックごとに、全速のチャネルと間引いたチャネルを別々に詰める（ブロックの中は planar） |
| RP2 の PIO（未実装） | PIO のシフトレジスタの詰め方（連続ピンの interleaved） |
| エッジの時刻を記録する形 | 変化ごとに時刻とチャネルの値 |

**提案: probe は取得したときの形のまま送り、詰め替えは host がする。** そのかわり、その形を宣言で正確に表す。

- 理由 1: 高速時は probe に詰め替える余力がない。2 本 160 Msps は DMA のバッファを zero-copy で送ってやっと
  間に合った（§7.2）。wch-protocols でも、codec の処理が律速になった（E106 / E111）。
- 理由 2: probe の実装が単純になり、実装ごとの差を宣言だけで吸収できる。
- 理由 3: host は PC なので、チャネルごと（planar）とサンプルごと（interleaved）の持ち替えは安い。`.sr` も
  PulseView への仲介も、host がどちらの形にでも作り直せる。

例外として、probe が形を変えた方がよい場面もある。

- **線が細いとき**: ESP32 の ADC の 4 バイトの結果は、12 ビットの値に対して 2.7 倍の量になる。UART の probe では、
  probe 側で 16 ビットに詰める方がよい。
- **帯域に収めるための間引き**（E106 のように、一部のチャネルだけ時間分解能を落とす）: これは詰め替えではなく
  取得の設定なので、形式の 1 つとして宣言する。

これらは、probe が選べる形式を複数宣言し、host が configure で選ぶ形にする（既定は取得したときの形）。

宣言に要る項目（案）:

| 項目 | 内容 |
|---|---|
| 並び | interleaved / planar（ブロックの長さ）/ レコード（1 件の大きさとフィールド） |
| サンプルのビット幅 | interleaved のときの w、チャネル k のビット位置 |
| ビットの順 | バイトの中の LSB 先 / MSB 先、バイト順 |
| レコードのフィールド | 値のビット位置と幅、チャネル番号のビット位置と幅、そのほか（ADC の unit など） |
| チャネルの順 | パターンの順（ADC）、最大レートで順番が乱れる場合があること（E034） |
| ブロック | planar のときのブロックあたりのサンプル数、チャネルごとの間引き率 |

## 4. 区画と印

リピートとストリーミングは、トラックごとの**位置の付いたバイトの並び**として見せる（[コンソールのストリーム](console-stream.ja.md)
と同じ考え方）。ワンショットは区画が 1 個だけのもの。区画はトラックをまたいで共通。

```text
segment : serial(u32), start_us(u32), trigger_index(u32), flags(u8),
          [track(u8), position(u32), samples(u32)] × トラック数
```

| フィールド | 意味 |
|---|---|
| serial | 取得開始からの区画の通し番号 |
| start_us | 区画の最初のサンプルの時刻（probe の起動からの µs、一周を考慮して比べる） |
| trigger_index | 区画の中でトリガが立ったサンプルの番号（基準のトラックで数える） |
| flags | bit0 待った（空き区画がなく、前の区画との間が再開時間より長い）、bit1 押し出された、bit2 短い |
| position | そのトラックでの区画の先頭のバイト位置（取得開始から通し、一周したら 0 に戻る） |
| samples | そのトラックでの区画のサンプル数 |

- ストリーミングでは、区画は probe の都合の区切り（DMA の 1 回ぶんなど）。区画の間が詰まっていれば連続、
  空いていれば取れなかった時間。
- 区画の情報は本文とは別の小さなリングにためる。

## 5. OEP への落とし込み（`oep.fixture.capture`）

ロジック、アナログ、ミックスドシグナルを 1 つのインターフェースで扱う。ロジックだけの probe はロジックの
トラックだけを宣言する。

### 5.1 役割（plan）

plan の役割は u8 なので、次のように分ける。1 つのインターフェースで使えるのはロジック 128 本、アナログ 64 本まで。
それを超える probe は同じインターフェースを複数（instance 違い）出す。

| role | 意味 |
|---|---|
| 0x00〜0x7F | ロジックのチャネル 0〜127 |
| 0x80〜0xBF | アナログのチャネル 0〜63 |
| 0xC0 | 外部クロック入力（ステート） |
| 0xC1 | 修飾の入力（有効信号） |
| 0xC2 | トリガ入力 |
| 0xC3 | トリガ出力 |
| 0xC4〜0xDF | 標準の予備 |
| 0xE0〜0xFF | 拡張 |

### 5.2 操作

| op | 名前 | 要求 | 応答 | ロック |
|---:|---|---|---|---|
| 0x01 | configure | 設定の TLV の並び（§5.3） | 実際の値の TLV の並び（§5.4） | 必要（問い合わせのみなら不要） |
| 0x02 | start | — | blocking_ms(u32)（0 = 取っている間も答える） | 必要 |
| 0x03 | stop | — | — | 必要 |
| 0x04 | force | — | —（host の条件を成立させる） | 必要 |
| 0x05 | status | — | state(u8)、serial_done(u32)、flags(u8)、[track(u8)、write_pos(u32)] の並び | 不要 |
| 0x06 | read | track(u8)、position(u32)、max(u32) | position(u32)、flags(u8: more、gap)、data | 不要 |
| 0x07 | segments | from_serial(u32) | 区画の情報の並び（§4） | 不要 |
| 0x08 | ack | serial(u32) | —（この区画までを再利用してよい。リピート） | 必要 |

- state: 0 未設定、1 設定済み、2 トリガ待ち、3 取得中、4 完了、5 待機中（空き区画なし）、6 エラー。
- read の max は u32。HS で 1 回 16 KiB 以上読むため。
- read で要求した位置がもう押し出されていれば、応答の position が先に進み、flags の gap が立つ。

### 5.3 configure の TLV

| tag | 名前 | 値 |
|---|---|---|
| 0x40 | mode | u8（1 ワンショット、2 リピート、3 ストリーミング、0x40〜 拡張） |
| 0x41 | query | —（設定せずに実際の値だけ返す） |
| 0x42 | track | track(u8)、kind(u8: 1 ロジック、2 アナログ、0x40〜 拡張)、format(u8)、first_role(u8)、roles(u8) |
| 0x43 | rate | track(u8)、rate_hz(u32)（アナログはチャネルあたり） |
| 0x44 | external_clock | track(u8)、edge(u8)、qualifier(u8: 0 なし / 1 High で有効 / 2 Low で有効) |
| 0x45 | samples | track(u8)、samples(u32)（1 区画あたり。ストリーミングは省略） |
| 0x46 | segments | u32（リピートの区画の数） |
| 0x47 | holdoff_us | u32 |
| 0x48 | trigger_position | pre(u32)、post(u32)（基準のトラックのサンプル数） |
| 0x49 | trigger_stage | stage(u8)、combine(u8: 0 すべて / 1 どれか)、count(u32)、timeout_us(u32) |
| 0x4A | trigger_condition | stage(u8)、type(u8)、target(u8: role か track)、params（type ごと） |
| 0x4B | trigger_out | role(u8)、pulse_us(u32)、polarity(u8) |
| 0x4C | analog_frontend | role(u8)、attenuation(u8)、ほか（実装の値） |

- ロジックのトラックのチャネルは `first_role` から `roles` 本（plan で割り当てた役割）。
- **critical を立てた TLV を probe が持たなければ、configure 全体を拒否する**（どの tag かを応答で示す）。
  立てていなければ無視して、応答の `ignored` に載せる。

### 5.4 configure の応答の TLV

| tag | 名前 | 値 |
|---|---|---|
| 0x50 | actual_rate | track(u8)、num(u32)、den(u32) |
| 0x51 | layout | track(u8)、bits_per_sample(u16)、valid_bits(u8)、format(u8) |
| 0x52 | timing | track(u8)、offset_ns(i32)、uncertainty_ns(u32)、jitter_ns(u32)、channel_skew_ns(u32) |
| 0x53 | actual_samples | track(u8)、samples(u32) |
| 0x54 | blocking_ms | u32（取っている間 probe が答えない時間の見込み。0 なら答える） |
| 0x55 | ignored | tag(u8) の並び（効かなかった項目） |

### 5.5 describe で宣言するもの

| tag | 名前 | 値 |
|---|---|---|
| 0x06 | features | 共通のビット。bit1 問い合わせ、bit2 外部クロック、bit3 トリガ出力、bit4 force |
| 0x40 | modes | mode(u8)、background(u8: 1 = 取っている間も答える) の並び |
| 0x41 | track_kind | kind(u8)、max_tracks(u8)、max_roles(u8)、formats(ビット)、bits_per_sample の候補 |
| 0x42 | track_combination | 同時に使えるトラックの組（kind の並び）。書かなければ 1 トラックのみ |
| 0x43 | rate_range | kind(u8)、min_hz(u32)、max_hz(u32)、steps(u8: 0 ほぼ任意 / 1 源 ÷ 整数 / 2 列挙)。**この間が全部設定できるとは限らない** |
| 0x44 | buffer | kind(u8)、max_samples(u32、ワンショット)、segment_max(u32)、segment_count(u32)、ring_bytes(u32) |
| 0x45 | rearm_us | u32（区画の間に止まる時間の目安） |
| 0x46 | trigger_types | 条件の種類のビット |
| 0x47 | trigger_limits | max_stages(u8)、max_conditions(u8)、max_pre(u32) |
| 0x48 | analog | 基準電圧(mV)、測れる範囲、減衰の候補、較正の形、合計レートの上限、同時サンプリングか |
| 0x03 | max_length | 1 回の read で返せる最大長（共通タグ。ただし u16 なので、超えるなら 0x49 を使う） |
| 0x49 | max_read | u32 |

### 5.6 拡張の余地

- モード、トラックの種類、形式、トリガの条件の種類は、それぞれ 0x40 以降を拡張に残す。
- 役割は 0xE0〜0xFF を拡張に残す。
- configure と describe の TLV は 0x60〜0x7F を拡張に残す。
- 大きく違う取得方式（プロトコルアナライザのように probe がデコードまでするもの）は、このインターフェースを
  広げず、別のインターフェースにする。

### 5.7 使い方の例

```text
ワンショット（P4、ロジック 2 本、20 MHz）
  plan_apply(capture: role0 = GPIO4, role1 = GPIO5)
  configure(mode=1, track(0, logic, first_role=0, roles=2), rate(0, 20 MHz), samples(0, 200000))
    → actual_rate(0, 20000000/1), layout(0, 2 bits), blocking_ms 0
  start → status をポーリング（state = 4 まで）。その間も他の操作ができる
  read(0, 0, 16384) を 4 本同時に出して最後まで読む

リピート（I2C のトランザクションを 1 本ずつ）
  configure(mode=2, track(0, logic, 0, 2), rate(0, 4 MHz), samples(0, 8192), segments(16),
            trigger_stage(0, all, 1, 0), trigger_condition(0, edge-falling, role1), trigger_position(256, 7936))
  start → segments(from) で終わった区画を知る → read で読む → ack(serial)
  ack が遅れると state = 5 になり、次の区画の flags bit0 が立つ

ミックスドシグナル（UART の送信 1 本と電源電圧 1 本）
  plan_apply(capture: role0 = GPIO4, role0x80 = GPIO16)
  configure(mode=1, track(0, logic, 0, 1), rate(0, 1 MHz), samples(0, 100000),
                    track(1, analog, 0x80, 1), rate(1, 48 kHz), samples(1, 4800))
    → timing(1, offset_ns=..., uncertainty_ns=...) で 2 本を並べる

アナログのストリーミング（音声 1 ch、48 kHz × 16 ビット = 96 KB/s）
  configure(mode=3, track(0, analog, 0x80, 1), rate(0, 48000), analog_frontend(0x80, 11 dB))
  start → read(0, pos, max) で追いかける。USB-Serial/JTAG（810 KiB/s）で余裕、UART 115200（11 KiB/s）では続かない
```

## 6. 実装ごとの見込み（どれを選ぶか）

| 実装 | モード | バックグラウンド（モードごと） | トラック | トリガ |
|---|---|---|---|---|
| P4 PARLIO + ADC | ワンショット（1 回の受信は 65,535 バイトまで。partial receive で長く取れる）、リピート、ストリーミング（wch-protocols で 2 本 160 Msps / 8 本 80 Msps を欠損なしで PC へ送った実績。ただし OEP のポーリングで同じ速さが出るかは未確認） | 3 つともあり（DMA）の見込み | ロジック 1 + アナログ 1 の見込み（同時開始のずれは未確認） | host、外部クロック（未確認） |
| classic ESP32 sampler | ワンショットのみ | あり（core 0 で取り、OEP は core 1。§7.5） | ロジック 1 | ループ内の比較なら可能（レートが下がる） |
| RP2 PIO + DMA（未実装） | 3 つとも（DMA のリング（最大 32 KiB）と 2 チャネルの連鎖で途切れない見込み。RP2350 は ENDLESS の転送モードもある） | 3 つともあり の見込み | ロジック 1（連続ピン 1〜32 本、sysclk まで）+ アナログ 1 | PIO の `wait` で 1 本のレベル / エッジ（プリトリガなし） |

P4 のストリーミングの実績（wch-protocols）: E078 で 2 本 86 Msps を継ぎ目なく、E113 / E121 で 2 本 160 Msps を
欠損 0、E121 で 8 本 80 Msps（高速 3 本 + 1/64 に間引いた 5 本）をバイト一致。いずれも partial receive のリングを
ISR で吸い出し、PSRAM の FIFO を経て vendor bulk で送る形で、OEP のポーリングではない。

## 7. 根拠の実測（2026-09-25）

### 7.1 P4 PARLIO のレート（80f1、arduino-esp32 3.3.12）

- 分周レジスタを読むと、ドライバは分数分周を使う。範囲内なら PLL 160 MHz 源でも XTAL 40 MHz 源でも要求どおり
  （33 MHz → 4+28/33、7 MHz → 22+6/7）。
- 範囲は源から源 ÷ 256 まで。PLL 源の 625 kHz（ちょうど 256）は失敗した。
- **範囲外はエラー 0 のまま分周 1（源クロック）で取る。** XTAL 源で 100 kHz / 60 MHz を要求すると 40 MHz で
  取っていた（1 MHz の矩形波を同じピンでループバックして確認）。
- RC_FAST 源は較正値を使い、要求から +5.2%。取ったデータにも揺れが見えた。
- 幅 1/2/4/8/16 はどれも 160 MHz まで設定を受け付ける（実際に取れるかは未確認）。

### 7.2 転送（ポーリングの損）

HS vendor bulk（P4 80f1、EspUsbDevice 2.5.1 buffered、usbip / WSL、ハブ経由）。{位置, 長さ} の要求に長さぶん返す
scratch のファームで、1 本の巨大な要求（= ストリーム）と、多数の要求（= ポーリング）を比べた。

| 応答 | 読みの URB 1 本 | 4 本 | 8 本 |
|---:|---|---|---|
| 1 KiB | 4.4 / 4.1 MB/s | 11.6 / 13.0 | 15.8 / 13.6 |
| 4 KiB | 12.3 / 11.3 | 33.0 / 33.4 | 34.7 / 33.9 |
| 16 KiB | 19.2 / 20.8 | 34.8 / 34.1 | 34.8 / 34.0 |
| 64 KiB | 26.2 / 26.8 | 34.7 / 34.5 | 34.8 / 34.7 |

（ストリーム / ポーリング。ポーリングは同時に出す要求の本数を変えた中の最良。全条件で化け 0）

- host が読みの URB を 4 本以上出し、応答が 16 KiB 以上なら、ポーリングはストリームと 2% 以内。
- 遅くなる原因は、URB を 1 本ずつしか出さないこと（usbip で URB あたり約 0.3 ms）と、応答の小ささ。
- USB-Serial/JTAG（FS）では、1 KiB を 2 本以上同時に出して生の 855 KiB/s の 95%（811 KiB/s）。

**direct（zero-copy）転送の上で同じ比較**（EspUsbDevice 2.5.1、`CFG_TUD_VENDOR_TXRX_BUFFERED=0`、`writeDirect`
48 KiB 区切り、完了コールバックで次を積む。同じ P4 80f1、ハブ経由）:

| 応答 | 読みの URB 2 本 | 4 本 | 8 本 |
|---:|---|---|---|
| 4 KiB | 22.7 / 22.1 MB/s | 39.4 / 34.4 | 42.7 / 34.5 |
| 16 KiB | 43.2 / 43.3 | 46.5 / 44.0 | 46.3 / 44.1 |
| 64 KiB | 46.4 / 46.2 | 46.6 / 46.1 | 46.6 / 46.1 |
| 256 KiB | 46.4 / 46.4 | 46.5 / 46.5 | 46.6 / 46.6 |

（ストリーム / ポーリングの最良。全条件で化け 0）

- 上限は約 46.6 MB/s（373 Mbps）。ポーリングは 64 KiB 以上の応答で 99%、16 KiB で 95%、4 KiB で 74〜81%。
- **2 本 150 Msps（詰めて 37.5 MB/s = 300 Mbps）は、転送の上ではポーリングで間に合う**（16 KiB 以上 × 2 本以上で
  44 MB/s）。160 Msps（40 MB/s）も 64 KiB 以上なら入る。

**取り込みと同時に: 2 本 160 Msps（320 Mbps）をポーリングで運ぶ**（wch-protocols E121 のファームを scratch で改造。
EspUsbDevice 2.5.0、arduino-esp32 3.3.12。host が「G バイトの読み出し」をクレジットとして先に W バイトぶん出し、
device はクレジットの範囲でだけ送る。検証は内部ループバックのバイト比較、1 回 41.9 MB）:

| 条件 | 3 回の結果 |
|---|---|
| ストリーム | 3/3 バイト一致、host 343.0 Mbps、PSRAM への退避 0 |
| ポーリング G = 64 KiB、W = 256 KiB | **3/3 バイト一致、341.6 Mbps、退避 0**（ストリームと同等） |
| ポーリング G = 32 KiB、W = 64 KiB | 3/3 失敗。先行が足りずに PSRAM へ退避し（30 MB）、取り込み側のキューがあふれた |
| ポーリング G = 256 KiB、W = 2 MiB | 3/3 失敗。最初から全量が退避に回った（原因は未特定） |

- **ポーリングでも 320 Mbps の連続取得は成立する。** 条件は、host が先に出しておく量が十分で、かつ多すぎないこと。
- 先行が足りないと、probe の中でデータが滞って遅い経路（PSRAM への退避）に回り、そこから戻れずに破綻する。
  これは E121 のファームの構造（退避中は全部を退避に回す）による面もある。
- 150 Msps は、ストリームでも検証用ループバックの開始位相が合わず、判定できなかった（治具の問題とみて除外）。

### 7.3 64 KiB を超える取り方（P4）

1 MHz の矩形波を 20 MHz、1 本で取り、ランの長さが 10 以外になる場所を数えた。

- 1 回の受信（65,408 バイト、内部 SRAM / PSRAM とも）: 途切れなし。
- 65,408 バイトの受信を 2 / 4 / 16 個積む: 区画の境界ごとに 1 か所ずつ途切れる（数サンプル。周期信号なので
  1 µs の端数としてしか分からない）。
- partial_rx（128 KiB のリング、eof 16 KiB）: 止めた後にリングをそのまま読むと、約 7 か所で途切れて見えた。
  **これは partial receive が途切れる根拠にならない。** wch-protocols の E078 / E113 / E121 は、ISR で区切りごとに
  吸い出す形で途切れなしを検証している。今回の読み方（吸い出さずに止めて読む、キャッシュの扱い）が原因の見込み。
- 8 MiB を 1 回で受信しようとすると、ドライバの中でスタック保護フォールトになって落ちる。

### 7.4 外部クロック（ステート）と ADC（P4 80f1、2026-09-25）

**外部クロック**: PARLIO TX が GPIO 2〜9 に 8 ビットのカウンタ、GPIO 10 にクロックを出し、RX がそのクロックで同じ
パッドを取る（チップ内のループバック）。TX はクロックの立ち下がりでデータを変える。

| クロック | RX 立ち上がりで取る | RX 立ち下がりで取る |
|---|---|---|
| 1 / 10 / 20 / 32 / 40 / 53.3 / 80 / 160 MHz | すべて 16,384 サンプル中 誤り 0 | 16 サンプルに 1 回ずれる（160 MHz では 548 / 16,384） |

- ステートモードは 160 MHz まで成立する（チップ内。外部の信号品質は未確認）。取るエッジの選択は必要。
- RX の構成体では `ext_clk_freq_hz` の指定が要る（ないと作成に失敗する）。
- P4 の PARLIO TX は 1 ユニットで、解放の戻り値が成功でも同じ起動の中で作り直せなかった（1 起動 1 条件で測った）。

**ADC の連続変換**（ADC1、12 dB、TYPE2 の形式）:

| 要求 | 実際（最初の変換フレームが欠ける分を補正） | overflow |
|---|---|---|
| 8 kHz | 約 8,012 /s（+0.15%） | 0 |
| 16 kHz | 約 16,024 /s（+0.15%） | 0 |
| 22.05 kHz | 約 22,122 /s（+0.3%） | 0 |
| 32 kHz | 約 32,049 /s（+0.15%） | 0 |
| 44.1 kHz | 約 44,642 /s（**+1.2%**） | 0 |
| 48 kHz（1 本） | 約 48,076 /s（+0.16%） | 0 |
| 48 kHz（2 本、各 24 kHz） | 各約 24,038 /s | 0 |
| 83.333 kHz | 約 83,332 /s | 0 |

- 10 秒（一部 3 秒）読み続けて数えた。最初の変換フレーム（後述）が出てこない分を足して補正した（256 バイトの
  フレームで測り直した 8 kHz は 7,991 + 21 = 8,012 /s で一致）。
- **ADC のレートも要求どおりにはならない。** 多くは +0.15% 前後、音声の 44.1 kHz は 1.2% ずれる。実際のレートを
  返す必要がある。
- **48 kHz 以上では各サンプルが 2 回ずつ出る**（esp-idf #17792 の報告を再現）。ADC のピンにレートの 1/8.7 の矩形波を
  出し、High / Low が続くサンプル数を数えた:

| 要求 | 続く長さ | 隣と同じ値の割合 |
|---|---|---|
| 20 / 30 / 38 / 40 / 41 / 42 / 44.1 / 46 kHz | 4 と 5（正常） | 13〜16% |
| 48 / 60 / 83.333 kHz | **4 と 6 だけ（偶数）** | 53〜54% |

  つまり 48 kHz を指定すると中身は実質 24 kHz、83.333 kHz は実質 41.7 kHz になる。**結果の個数は要求どおり出るので、
  数えるだけでは気づかない。** 2 チャネル（合計 48 kHz）でも起きるかは未確認。probe は、宣言するレートの上限を
  実質の値（P4 では 46 kHz 前後）にする必要がある。
- LEDC で出力しているパッドを、そのまま ADC で読めた（0 と約 3476）。
- **ADC と PARLIO を続けて開始したとき**（同じパッドを 1 回だけ立ち上げ、それぞれの開始時刻からの位置で比べた。10 回）:
  - PARLIO: エッジの位置は GPIO を書いた時刻と 5 µs 以内で一致した。開始時刻がそのまま時間軸の基準になる。
  - ADC: エッジが 5.20〜5.25 ms 早く見えた。これは変換フレーム 1 つ分（1 KiB = 256 結果 = 48 kHz で 5.33 ms）で、
    最初のフレームが読み出しに出てこない（または開始より前に始まる）とみられる。フレームを 256 バイト（64 結果 =
    1.33 ms）にすると、ずれは 1.22〜1.27 ms に縮んだので、フレーム 1 つ分で確定。回ごとの差の変化（-5254 → -5200 µs）は、
    実際のレート 48,050 /s を 48,000 として計算した誤差で説明がつく。
  - したがって **ADC の時間軸は「開始時刻 + 番号 ÷ 要求レート」では合わない。** probe は実際のレートと、最初のサンプルの
    時刻（ドライバの挙動を含めた補正後の値）を返す必要がある。補正後の残りの誤差は未確認。
  - 初めに 1 kHz の矩形波で測ったときは 306 µs と読んだが、周期で折り返した値だった（5.25 ms − 5 × 1 ms 付近）。

### 7.5 取っている間に他の操作ができるか（OEP の probe、2026-09-25）

キャプチャ（v1 の `oep.fixture.capture`、v0 の形の操作）を始め、終わるまで riscv-dm の DMSTATUS の読み出しを繰り返した。

| probe | DM 読み出し（普段） | 取っている間 | キャプチャ |
|---|---|---|---|
| X035 jig の P4（PARLIO、1 MHz / 20 MHz、50 万サンプル） | 中央値 0.49 ms、p95 0.65 ms | 中央値 0.50 ms、p95 0.66〜0.67 ms | 完了、全量読めた |
| V003 jig の classic ESP32（sampler、0.4 / 2 MHz、6.5 万サンプル） | 中央値 5.7〜6.3 ms | 中央値 5.5〜6.6 ms | 完了、全量読めた |

- どちらも、取っている間に DM の操作は遅くならなかった。
- classic ESP32 で読み出しが 36,704 / 65,000 サンプルで止まったのは client の不具合だった（1 回 900 バイトを要求し、
  probe の frame 512 バイトに収まらず短く返っていた）。oep-client-python で修正済み。
- 今回はモードがワンショットだけ（今の probe の実装）。リピートとストリーミングは実装がないので未確認。

### 7.6 机上調査（2026-09-25、esp-idf master と TRM / データシート、libsigrok。詳細は [キャプチャの机上調査](capture-survey.ja.md)）

**P4 PARLIO**
- RX ユニットは 1 つ、幅は 1/2/4/8/16。分周は整数（〜256）+ 分数。
- **データシートの IO クロックの上限は 40 MHz**（P4 datasheet v0.7 §4.2.2.18、TRM 61.3）。ドライバはこれを検査しない。
  §7.4 の外部クロック 160 MHz はチップ内のループバックでの結果で、外部の信号でどこまで使えるかは別に確かめる。
- 有効信号（valid）はドライバの中で 1 本のデータ線を使う扱いで、レベル / パルスの区切りではデータは 8 ビットまで
  （wch-protocols E041 は GPIO を共有して 8 本 + valid で成立）。
- partial receive（`partial_rx_en`）は DMA の記述子をリングにつなぐ正式な機能で、esp-idf の logic analyzer の例もこれを
  使う（P4 の持続帯域の公式な数字はない。wch-protocols の E078 / E113 / E121 が実測）。

**ESP32 の ADC（DMA）**
- `sample_freq_hz` は**全チャネル合計**の変換レート（HAL のコードから。ドキュメントには明記がない）。
- 結果の形: classic ESP32 は 2 バイト（値 12 + チャネル 4）、S3 / P4 は 4 バイト（値 12、チャネル 4、unit 1）。
- P4 は ADC2 も DMA で使える（classic ESP32 は ADC1 のみ、S3 は ADC2 にエラッタ）。
- しきい値のモニタ: S3 は esp-idf にドライバがある（割り込み経由、サンプル位置は分からない）。**P4 はハードウェアに
  あり ETM のイベントも出ているが、esp-idf では無効**。ハードウェアトリガに使えるかは未確認。
- 既知の問題: classic ESP32 の実レートが 18〜22% 低い（esp-idf #16768 ほか）。**P4 は 83,333 Hz で各サンプルが
  2 回ずつ出て実質 40 kHz 前後になるという報告がある（#17792、未回答）**。§7.4 の 83.333 kHz は結果の個数だけを
  数えたので、重複していないかは確かめていない。wch-protocols E034 の「最大レートでチャネルの順番が乱れる」とも
  関係するかもしれない。

**libsigrok / 市販品**: §2.3 と §2.8 に反映した。

### 7.7 host 側の実験（2026-09-25）

**H1: 小さな問い合わせの往復のコスト**（core の `lock_state`、ロックなし。問い合わせ 1 件の代わり）

| probe | 1 件ずつ | 100 件まとめて | 1000 件まとめて |
|---|---|---|---|
| X035 jig の P4（USB-Serial/JTAG） | 0.46 ms / 件 | 44 ms | 332 ms |
| V003 jig の classic ESP32（UART） | 4.88 ms / 件 | 485 ms | 4.87 s |

UART の probe は、まとめて送っても 1 件ずつと変わらない。

**H2: host での詰め替えのコスト**（numpy、1 スレッド、WSL。入力 40 MB）

| 詰め替え | 入力の速さ |
|---|---|
| PARLIO 2 ビットの interleaved → sigrok の 1 バイト / サンプル | 112 MB/s |
| PARLIO 2 ビットの interleaved → チャネルごとのビット列（planar） | 72 MB/s |
| PARLIO 8 ビットの interleaved → チャネルごとのビット列（planar） | 55 MB/s |
| PARLIO 8 / 16 ビット → sigrok（unitsize 1 / 2、そのまま） | 変換なし |
| ADC TYPE2 の 4 バイト（2 チャネル）→ チャネルごとの uint16 | 531 MB/s |
| ADC TYPE2 → チャネルごとの float32 の電圧（hameg-hmo の形） | 589 MB/s |

HS の上限（46 MB/s）より速いので、**取得した形のまま送って host で詰め替える方針（§3.4）で、host が律速にならない。**

**H3: テストの自動判定の通し**（X035 jig）

X035 に USART4 で `OEP capture line N` を出し続ける sketch を書き込み、TX の線を P4 の capture（4 MHz、50 万サンプル）で
取り、`.sr` にして `sigrok-cli -P uart` でデコードした。

- ビルド 1.6 s、OEP 経由の書き込み 0.6 s、キャプチャと読み出し 0.7 s。
- 888 文字、41 行をデコードし、行番号は連続していた。サンプルから見積もったボーレートは約 117 kbps（見積もり方が粗い）。
- 今の capture は 1 本でも 1 サンプル 1 バイトで送る（PARLIO が取った形は 1 サンプル 1 ビット）。**8 倍の量を送っており、
  読み出しの 0.7 s の大半はこれ。** 取得した形のまま送れば 1/8 になる。
