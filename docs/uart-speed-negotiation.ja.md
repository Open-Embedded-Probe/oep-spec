# UART の速さ（再検討）

状態: **保留・実験中**（2026-10-01。実験 1 の結果は §3a）。V003 ジグ（classic ESP32 + CP2102、115200）で、fixture UART の連続受信が約 2.9 KB/s で
頭打ちになり、1 KB の答えが線の上で 1 byte 落ちるとフレームごと無駄になる件（bench、2026-10-01）から始まった。

最初の案（セッションの間は交渉して上げ、黙りが続けば戻す）は**採らない**。理由と、代わりの進め方を下に書く。

## 1. 前提（ユーザーの指摘、2026-10-01）

- **速さを変えると壊れやすい**。変換チップ、ボードの配線、ケーブル、usbipd の経路、チップの UART の分周で、安定して使える速さが
  違う。上げられるかどうかは実際に流してみないと分からない。
- **ビルド済みのバイナリの既定を前提にできない**。M5Stack ATOM のように、決まった（特殊な）速さでしか通信できない device がある。
  そういう device では、115200 の「既定」自体が通らない。
- **esptool の流儀**: ESP32 のシリアル書き込みは途中で速さを上げる（メガ単位）が、決め打ちで交渉は無い。上げた後に通らなければ
  失敗するだけで、利用者が `--baud` を下げてやり直す。

## 2. 本当に速さが要るか

UART の経路で OEP がしていることごとに、115200（約 11 KB/s、往復 約 5 ms）で足りるかを見る。

| 使い方 | 量 | 115200 で | 速さが要るか |
|---|---|---|---|
| 制御（halt、resume、attach、設定） | 1 要求 数十 byte | 往復 5 ms | 要らない |
| 小さな target の書き込み（V003 16 KB、L103 64 KB） | 16〜64 KB | 1.5〜6 s（理論） | 要らない（ESP32 の書き込みとは量が 2 桁違う） |
| target のコンソール（bind、console の read） | 人が読む量 | 足りる | 要らない |
| **fixture UART の連続受信**（target の UART を 115200 で受け続ける） | 11.5 KB/s を続けて | **追いつかない**（実測 2.9 KB/s） | 線の速さより、往復の作りの問題 |
| キャプチャ（logic / analog）を UART で読む | 大きい | 足りない | UART の経路は向かない（USB の口を使う） |

- **速さが足りないのは fixture UART の連続受信だけ**で、それも線の上限（11 KB/s）の 4 分の 1 しか出ていない。原因は線の速さ
  ではなく、1 回の read の量（classic ESP32 は max_frame 512、max_inflight 1）と往復の待ち。線の速さを上げても、同じ作りなら
  往復の待ちが残る。
- 同じ線の上で、相手（target の UART）と OEP の口が同じ 115200 なら、**OEP が相手の全量を運ぶことは原理的にできない**（見出しと
  往復の分だけ足りない）。これは速さの交渉ではなく、「target の UART を probe の UART の口で全量中継する」使い方自体の限界で、
  USB の口を持つ probe を使うか、target の UART を遅くするのが正しい。

**bench の測定（2026-10-01、V003、broker 経由、950 回の read を記録）**: probe は DUT の 64 KB を全部受けていた（リングの位置が
毎秒 10.2〜11.1 KB 進む、mark の lost なし）。host の取り込みは 480 byte の答えが 約 61 ms ごと（線の上 42 ms + 往復）で最大 約 7.9 KB/s。
約 3 秒でリングに追い越されて gap になり、DUT が送り終えた後は空の read が続いた（「88% が空」はこの待ちの分）。読み位置の誤りも、
broker の取り違えも無かった。往復は直結で keepalive 5.3 ms、空の read 7.1 ms（線の上は 1〜2 ms、残りは CP2102 と usbipd）。

**結論**: 2.9 KB/s は host の読みが遅いのではなく、DUT の送信が終わった後も 64 KB を待ち続けた平均。受信中の取り込みは 7.9 KB/s で、
往復の待ちを消しても（max_inflight 2）線の上の 480 / 500 の効率で約 11 KB/s が上限になり、115200 の UART の全量（11.5 KB/s）には
届かない。§2 のとおり、同じ速さの UART を probe の UART の口で全量中継するのは原理的にできない。

## 3. 進め方

1. **115200 のまま効率を上げる**（仕様の変更なし、すぐできる）:
   - fixture UART の read を、往復ごとに 1 フレーム目一杯（約 490 byte）返す。今の 2.9 KB/s がどこで決まっているか（probe の
     max_read、host の待ち、poll の間隔）を測って直す。
   - 必要なら classic ESP32 の max_inflight を 2 にして、読みを 2 本重ねる（線を休ませない）。
   - 目標: 線の上限の 8 割（約 9 KB/s）。それで bench の long（64 KB / 20 s = 3.2 KB/s 以上）は通る。
2. **実験**（仕様を決める前に、何が壊れるかを測る）:
   - 変換チップ（CP2102、CH340、CH9102、FTDI、M5Stack ATOM の変換）× 速さ（115200、230400、460800、921600、1.5M、2M）×
     経路（直結、usbipd）で、link_source / link_sink を流し、CRC 不一致と落ちた byte を数える。
   - 速さを切り替える手順（応答を送り終えてから切り替える、切り替えの後の最初のフレームが落ちるか）を測る。
   - 結果は wch-protocols / oep-spec の実験の記録に置く。
3. **速さを変える機能が要ると分かったら**、次の制約で仕様にする（今は決めない）:
   - **既定の速さは probe の firmware（ボードの profile）が決め、利用者が host に渡す**（ATOM のような device のため。host は開く前に
     速さを知る手段が無いので、口を選ぶのと同じく利用者が指定する。参照の firmware の既定は 115200）。
   - **上げる範囲を最小にする**: セッションの間ずっとではなく、host が頼んだ**大きな転送の間だけ**（書き込み、キャプチャの読み出し）
     上げて、終わったら戻す。上げる op と戻す op を対にし、戻し忘れても probe が短い時間（秒単位）で戻る。
   - **上げた後に確かめる**: 切り替えた後、host は link_source / link_sink で両方向に max_frame 近くの大きさを数回流し、1 つでも
     壊れれば元の速さに戻して、その速さを使わない。使っている間も、壊れたフレームの数が閾値を超えたら 1 段下げる。
   - **交渉しない選択肢も残す**: esptool のように host が決め打ちで速さを指定し、通らなければ失敗として利用者に返す。

## 3a. 実験 1: M5Stack ATOM（ESP32-PICO-D4 + FTDI、2026-10-01）

> **注（ユーザーのメモ、2026-10-01）**: ATOM の変換は本物の FTDI ではなく、**CH552 が FTDI 互換（0403:6001 "M5stack"）を
> 名乗っている**もの。整数分周の速さしか通らないこと、両方向同時に壊れること、115200 でも 0.1〜0.3 % 壊れることは、この
> ソフトウェア実装の性能の限界で、FTDI 系の一般の性質ではない。以下「FTDI」とあるのはこの CH552 のこと。

**やり方**: 実験用の op（fn 0 の 0xF0 `port_speed`、実験用の番号の範囲。oep-probe-arduino の `exp-port-speed` ブランチ、
`-DOEP_EXPERIMENT_PORT_SPEED`）を classic ESP32 の OepProbe に足して ATOM に焼いた。**probe は速さの候補を宣言しない**。host が頼み、
probe は応答を今の速さで送り終えてから UART0 の baud を変え、confirm_ms（500 ms）の間に正しいフレームが来なければ 115200 に戻る。
上げた後は idle_ms の黙りで戻り、セッションの終わりでも戻る。host は頼んだ後に自分の baud を変え、confirm を送り、通れば
link_source / link_sink（496 byte）を 100 回ずつ流して壊れ方を数え、115200 に戻す。スクリプトは scratchpad の speed_probe.py
（oep_client 0.0.22）。

**準備で分かったこと**: 参照の classic ESP32 の firmware はそのままでは ATOM で起動しない（TG1WDT のリセットを繰り返す）。
ESP32-PICO-D4 は GPIO16 / 17 を内蔵の flash に使うのに、firmware がそれを channel として Hi-Z にするため。ビルド済みのバイナリが
ボードによって動かない例そのもので、PICO-D4 向けの profile（channel から 16 / 17 を外す）が要る（実験では `-DOEP_BOARD_PICO_D4`）。

**結果**（115200 で開始、各速さで confirm → 100 回の検証 → 115200 に戻る）:

| 速さ | 切り替え | 壊れたフレーム | probe → host / host → probe |
|---|---|---|---|
| 115200（開始） | — | 0 | 9.5 / 9.0 KB/s |
| 230400、460800、600000、921600、1000000、1200000、2000000、3000000 | **通らない**（confirm が返らない） | — | — |
| 250000、300000、375000 | 通る | 0 / 200 | 14.3 / 14.3 KB/s |
| 500000、750000、1500000 | 通る | 0 / 200 | 28.2〜29.0 / 28.2〜29.0 KB/s |

- **通るのは 3 MHz ÷ 整数の速さだけ**（250000 = 3M/12、300000 = /10、375000 = /8、500000 = /6、750000 = /4、1500000 = /2）。921600 も
  230400 / 460800 も通らない。変換チップ（FTDI 0403:6001 "M5stack"）の分周の都合で、ユーザーの見立てどおり「普通の速さ」は通らない。
- **通らなかった速さは、すべて probe が 500 ms で 115200 に戻り、host も 115200 で confirm し直せた**（一度も probe を見失わなかった）。
  黙りでの戻り（idle_ms 1500 ms）も確かめた。
- **速さを上げても 29 KB/s で頭打ち**: 往復が FTDI の latency timer（Linux の既定 16 ms）に合わせて量子化され、1 往復が 16 ms（500000
  以上）か 32 ms（250000〜375000）になる。496 byte ÷ 16 ms ≈ 30 KB/s。線の速さではなく、host の側の設定
  （`/sys/bus/usb-serial/devices/ttyUSBn/latency_timer`、root が要る）が律速。max_inflight 1 のままでは、これ以上は出ない。
- **probe が候補を宣言する形は合わない**: 通る速さは変換チップが決め、probe の firmware は知らない（ESP32 の UART はどの速さも出す）。
  host が頼んで、試して、確かめる形（ユーザーの案）が正しい。

**ここから言えること**:
- 交渉は「host が頼み、probe は応答の後に切り替え、確かめが来なければ自分で戻る」で安全に試せる。宣言は要らない。
- 試す候補は host が持つ（変換チップの VID:PID で 3 MHz ÷ 整数の FTDI 系、CP2102 系の表、など）か、順に試す。
- 速さの効果は latency timer に大きく左右される。速さを上げるより先に、host が latency timer を下げる（または max_inflight を上げる）
  方が効く場面がある。次の実験で latency timer 1 ms と max_inflight 2 を試す。

## 3b. 実験 2〜4: 同じ ATOM で、latency timer、切り替えの繰り返し、長時間、max_inflight（2026-10-01）

- **latency timer**: pyserial の `set_low_latency_mode(True)`（root 不要、ftdi_sio の latency_timer が 16 → 1 ms）で、link_source が
  500000 で 33 KB/s、750000 で 47 KB/s、1500000 で 77 KB/s（16 ms のときは どれも 29 KB/s で頭打ち）。
- **切り替えの繰り返し**: 115200 ↔ 1500000 を 50 回（上げる → confirm → link_source → 下げる → confirm）。失敗 0、1 回 44 ms。
- **長時間**（link_source 496 byte を 3000 回、壊れたら同じ corr で 1 回送り直す）:

| 速さ | max_inflight | 速度 | 壊れて送り直したフレーム |
|---|---|---|---|
| 115200 | 1 | 9.3 KB/s | 3 / 1500（0.2%） |
| 115200 | 2 | 9.5 KB/s | 2 / 1500 |
| 750000 | 1 | 35.5 KB/s | 10 / 3000（0.3%） |
| 1500000 | 1 | 57.8〜65.5 KB/s | 3〜6 / 3000（0.1〜0.2%） |
| 1500000 | 2 | **77.7 KB/s** | 2 / 1500（0.1%） |

- **壊れ方は速さに依らない**: 115200 でも同じ割合（0.1〜0.3%）でフレームが壊れる。この ATOM の FTDI / USB の経路の性質で、上げた
  速さのせいではない。どれも同じ corr の送り直し（送り直しの表、1 KiB × 8）で取り戻せ、データの誤り（bad）は 0。壊れたフレームは
  1 秒の待ちで見つかるので、速度の値はその待ちを含む（1500000 / inflight 1 の幅はそのため）。
- **max_inflight 2** は線の速いときだけ効く（1500000 で 58〜65 → 78 KB/s、115200 では変わらない）。

**ここまでの結論**: この ATOM では、「host が頼む → probe が応答の後に切り替える → 500 ms の確かめ → 通らなければ probe が戻る」で、
試した 17 通りの速さの切り替え（通る 6、通らない 11）と 50 回の往復がすべて安全に済んだ。上げた後の壊れ方は 115200 と同じ。
115200 の 9.5 KB/s に対して、1500000 + latency timer 1 ms + max_inflight 2 で 77.7 KB/s（8 倍）。次は CP2102 / CH340 の板で同じことを
確かめる（V003 のジグは bench の了解が要る）。

## 3b-2. 実験 5: V003 のジグ（classic ESP32 + **CH340**、usbipd、2026-10-01）

bench の了解を取って使い、終わってから release の firmware（0.0.22）と設定（prepare.py、hash 0x146c090e、ready）に戻した。変換チップは
bench の記録にあった CP2102 ではなく CH340（1a86:7523、ch341）だった。max_inflight 2 の実験の firmware。各速さで新しいセッションから
confirm → link_source / link_sink 496 byte を 20〜100 回ずつ。

| 速さ | confirm | probe → host | host → probe | 速度（in / out） |
|---|---|---|---|---|
| 115200 | — | 0 / 100 壊れ | 0 / 100 | 9.5 / 9.3 KB/s |
| 230400 | **通る** | **全部壊れる** | **全部壊れる** | — |
| 250000 | 通る | 0 | 0 | 18.9 / 18.7 |
| 460800 | 通る | 0（1 回の送り直し） | 0 | 7.2 / 28.4（送り直しの待ちを含む） |
| 500000 | 通る | 0 | 0 | 30.8 / 30.3 |
| 921600 | 通る | 0 | 0 | 47.7 / 44.1 |
| 1000000 | 通る | 2 / 20 壊れ | 0 | 1.3 / 38.2 |
| 1500000 | 通る | 12 / 20 壊れ | 0 | 0.4 / 39.7 |
| 2000000 | **通る** | **全部壊れる** | **全部壊れる** | — |

- 921600 の長時間（1500 フレーム、max_inflight 2）: 37.5 KB/s、送り直し 7 回（0.5%）、データの誤り 0。切り替えの往復 20 回で失敗 0。
- set_low_latency_mode は ch341 にも効いたように見えるが（エラーにならない）、latency timer の sysfs は無い。
- **危ない落とし穴**: 230400 と 2000000 では、**小さな confirm は通るのに、大きなフレームは両方向とも全部壊れる**。confirm が通ったので
  probe は戻らず、host は 1 秒ずつ待って送り直し続け、lease が切れた（expired）。probe が戻ったのは idle_ms（5 s）の黙りの後だった。
  1000000 / 1500000 では **片方向だけ**（probe → host）が壊れる。
- **ここから言えること**: (1) 切り替えの確かめは、**両方向に max_frame 近くの大きさのフレーム**で行い、その結果で probe が戻るか
  どうかを決める（小さな confirm では足りない）。(2) probe は、新しい速さで**壊れたフレームを受けたら**（CRC が合わない候補）すぐ戻ってよい
  （probe → host だけが壊れる場合は probe には見えないので、host の確かめが要る）。(3) 通る速さは変換チップとドライバの組で決まり、
  ESP32 側（ATOM の FTDI とこの CH340 で、同じ ESP32 の UART）からは分からない。

## 3c. peer の意見（2026-10-01）

- **bench（ArduinoCore-CH32RV）**: 強い反対なし。今 115200 で足りないのは V003 のジグの fixture UART の連続受信だけで、「あれば
  全量で回せる」程度。使うなら bench のコードに手が要らない形（broker か client の link が自動で上げ下げ）。速さを決める所は
  「既定の速さ（profile か利用者の指定）」と「broker の交渉」の 2 か所に限り、既定の速さ（ATOM のような device の値）は 1 か所に
  書けるように（port の設定か board-identify の id ごと）。broker のセッションは長いので、上げたまま壊れ続けたら 1 段下げる処理が
  要る。気になるのは、候補表を誰が持つか、書き込みの途中で壊れたときの 500 ms の待ちと再送の兼ね合い。順は §3-1 を先に、交渉は
  optional・host の opt-in で。V003 のジグでの実験は可（1〜2 時間、始めと終わりに連絡、終わったら release の firmware と設定に戻す）。
- **ch32rv**: 「あれば使う、無くても困らない」。serial の口を持つのは常にブローカーなので、ブローカーの責任でよい（大きな転送の間だけ
  上げる、セッションの終わりと lease 切れで probe が戻るのを当てにする、boot_id が変われば既定に戻ったものとして扱う）。試す速さは
  利用者が明示したときだけ（自動で順に試さない。試すこと自体が口を揺らす）。VID:PID ごとの候補表はヒントにとどめ、必ず
  link_source / link_sink で確かめてから使う。応答に実際に掛かる速さを返す。戻る契機に lease 切れと force（持ち主の交代）も。支持の
  宣言は describe の feature か unknown_operation で足りる。先に §3-1 と host の low latency を、の意見（ただし 115200 では
  max_inflight 2 と latency 1 ms でも 9.5 KB/s で、線の上限 11 KB/s を超えないので、long の全量には速さが要る: §3b）。
- **WireSkein**: 使いたい、賛成。UART の probe ではキャプチャの読み出しが長く（32 KB に数秒）、lease にも気を遣っていた。交渉は
  クライアントの中で済ませ、止めたいときの引数があれば `oep:/dev/ttyUSB0?fast=0` のように渡す。失敗したら必ず 115200 に戻ること
  （CH340 など 1.5 Mbaud を出せない変換チップ、長いケーブル）。

## 4. 今の決定

- 921600 への単純な変更はしない。速さの交渉も、実験の結果が出るまで仕様に入れない。
- まず §3-1（115200 のまま効率を上げる）を probe と client で行い、bench の long で確かめる。
- §3-2 の実験は、bench のジグを使う前に bench（arduinocore-ch32rv-3c）の了解を取る。

## 5. 仕様の案（2026-10-01、実験 1〜5 の後。**採用**: core §3.5 に入れた。確かめは大きめの転送でスループットとエラー率を測る、をユーザーの指示で足した）

位置付け: **probe と host の間のリンクを、target の UART より速くするための任意の機能**（V003 のジグの long のように、同じ速さの
リンクでは target の UART の全量を運べない。今後の ESP32 の大きな書き込み、ロジアナ、JTAG / SWD のデバッグも見込む）。probe の UART
（fixture UART、target との間）の速さは、これとは別に `oep.fixture.uart` の configure と設定の uart 項目で決める（9600、31250 の MIDI、
115200 など）。

- **probe は ON / OFF を持つ**: 機能を持つ probe（firmware のビルドで ON にしたもの）だけが fn 0 の describe に `port_speed`（u8 1）を
  宣言し、op を受ける。OFF の probe は op を unknown_operation で断る。速さの候補は宣言しない（通る速さは変換チップとドライバが決め、
  probe には分からない: ATOM の FTDI と V003 の CH340 で全く違った）。
- **host が使うかは host が決める**。仕様は既定を決めない。試す速さは host が持つ（利用者の明示、または host が知っている変換チップ
  の候補）。
- **形**（fn 0、ロックが要る。番号は 0x14、セッションの範囲）:

```text
port_speed  要求: port(u8)、baud(u32)、step(u8: 0 試す、1 決める、2 戻す)、verify_ms(u16)、idle_ms(u32)、[TLV]
            応答: baud(u32: 実際に掛かる速さ)、[TLV]
```

- **手順**:
  1. host が 起動時の速さ（既定。ボードの profile が決め、利用者が host の 1 か所に書く）で confirm と describe を済ませ、`port_speed(試す)` を頼む。
  2. probe は応答を今の速さで送り終えてから切り替え、**試しの状態**になる。
  3. host も切り替え、**両方向に max_frame 近くの大きさ**で確かめる（link_source を 2 回、link_sink を 2 回、どれも壊れずに返ること）。
     小さな confirm では足りない（実験 5: CH340 の 230400 で、confirm は通り、大きなフレームは全部壊れた）。
  4. 通れば `port_speed(決める)` を新しい速さで送る。probe は決めた状態になる。
  5. **probe が戻る**（起動時の速さへ）: 試しの状態で verify_ms が過ぎた、試しの状態で壊れた候補（CRC が合わない）を受けた、決めた後に
     idle_ms の間正しいフレームが来ない、決めた後に短い間に壊れた候補が続いた（目安 1 秒に 3 つ）、セッションが終わった（end、
     lease の期限切れ、force で持ち主が替わった）、`port_speed(戻す)` を受けた。どの場合も応答は無く、host は時間切れの後、起動時の
     速さで confirm し直す。
  6. 戻った後の速さは起動時の速さ。boot_id が変わっていれば probe は再起動していて、やはり起動時の速さ。
- **host の義務**: 試したが確かめが通らなかった速さは使わない。決めた後も、送り直しが続くなら `port_speed(戻す)` か切断で起動時の
  速さに戻る。ブローカーが口を持つ構成ではブローカーの責任（client は知らない）。

決めること: この案で core に入れてよいか。入れるなら spec → fake → probe（classic ESP32 の参照 firmware は ON、ほかは UART bridge が
無いので無し）→ oep-client-python（`open_host(..., port_speed=[候補])` の opt-in）→ 実際の書き込み・キャプチャで使ってみる（ドッグ
フーディング）の順で進める。

## 6. ドッグフーディング（2026-10-01、仕様と実装の後）

M5Stack ATOM（main の firmware、`oep speed`、`raise_speed`）で使って見つかったことと直したこと:

1. **切り替えの残り**: 両端が切り替わる間に流れていたバイトが、切り替えのたびに 1 つ壊れた候補になった。最初の実装は試しの状態でそれを
   見て戻り、どの速さも断られた。→ probe は新しい速さで正しいフレームを受けるまで壊れた候補を数えない（oep-probe-arduino e6b8106）。
   host は切り替えの後 20 ms 待ち、confirm で新しい速さを確かめてから測る（oep-client-python 1e2b8e4）。core §3.5 にも書いた。
2. **両方向の同時**: この FTDI は 500 kbaud 以上で、応答を受けている間に次の要求を書くと応答が壊れる（max_inflight 2 で並べると
   壊れ、1 つずつなら壊れない）。→ host は実際に使う並べ方で確かめ、壊れたら 1 つずつで確かめ直し、通った上限を link に残す。
   ATOM は 1.5 Mbaud を同時 1 で 79 / 59 KB/s で決める。
3. **壊れたフレームの待ち**: 壊れたフレームのたびに 1 秒の時間切れを待っていた。→ セッションが口を持つ間は、probe はその口に
   生のバイトを送らないので、壊れた候補は応答そのもの。すぐ送り直す（probe の送り直しの表が答える）（oep-client-python be4b451）。
4. **実際の使い方**: 60 KB のロジックのキャプチャ（3 チャネル、1 MHz、60000 サンプル）の読み出し: 115200 で 15.0 s（4.0 KB/s）→
   上の 3 の後 7.3 s（8.3 KB/s）、1.5 Mbaud で 0.79 s（76 KB/s）。セッションの終わりで link も probe も 115200 に戻った。

## 7. 使い方の方針（2026-10-01、ユーザー）

- 入れた機能は使う（使われない機能は壊れる）。**長いセッションを持つ host は既定で試す**: ch32rv のブローカー、WireSkein の capture。
  1 回ごとに開く CLI は試さない（確かめのコストで元が取れない）。CDC / USB-Serial/JTAG は対象外。
- 候補はまず固定の 921600、750000、500000（WireSkein は 1500000、921600、500000）。止める設定は残す。
- 候補の列の決め方、結果を unit_id ごとに覚えるか、試す時間の上限は、使ってみた結果（ブローカーのログ: 速さごとの通った / 壊れた、
  KB/s、重ねられた要求の数、かかった時間）を見てから決める。

## 8. 使ってみた結果（2026-10-01）

- **bench（V003、CH340、firmware 0.0.24、oep-client-python 0.0.24）**: `oep speed … 921600,500000,250000` が 921600 で決まった（67.6 / 44.7 KB/s、
  同時 2、壊れ 0）。bench の一通り（max_inflight 2）で新しい問題なし。
- **ch32rv のブローカー（4462abf、既定 ON、候補 921600 → 750000 → 500000）**: V003 で 4 回とも 921600 が 1 回目で通った（actual 922190、
  69 / 65 KB/s、同時 2、壊れ 0、試すのに 600 ms）。flash（11 KB）が 4.8 s → 2.4 s、dmseq の monitor と並行でも 2.6 s で 6/6。並行中に
  壊れたフレームが 1 つ出たが、すぐの送り直しで回復。上げた後に 115200 へ戻る場面は無かった。
- **黙りの上限 3 秒と、開く host の再試行（core §3.5 の probe が戻る条件 3 と host の義務 7、ch32rv の提案）**: ATOM（main の firmware）で、1 つめの host が lease 60 s で
  速さを上げたまま end せずに落ち、2 つめの host がすぐ開いた。2 つめは 3.6 s 後に 115200 で開けた（probe が 3 秒の黙りで戻り、host の
  confirm の繰り返しが拾った）。上限の前は、lease の 60 s が切れるまで開けなかった。

## 9. 限界の測り方（2026-10-01、ユーザーの指摘の後）

決め打ちの速さと回数だけで確かめるのではなく、**host が条件を変えながら測れる道具**にした: `oep linktest`（oep-client-python の
`oep_client.linktest`）。速さ（今の速さ、または port_speed で切り替える速さの並び）、流し方（in = probe → host、out = host → probe、
duplex = 交互）、同時に出す要求の数、フレームの大きさ、回数か時間、待ち、low latency の ON / OFF をすべて引数で渡し、条件ごとに
ok / broken（答えは来たが中身が違う）/ lost（答えが来ない）と KB/s を出す。

**ATOM（ESP32-PICO-D4 + FTDI "M5stack"）で分かったこと**（main の firmware、low latency ON）:

| 条件 | 115200 | 1500000 |
|---|---|---|
| in / out / duplex、同時 1 | 壊れ 0〜0.5 % | 壊れ 0〜0.5 %、82 / 63 / 75 KB/s |
| in、同時 2 | 壊れ 5 % | 27〜64 % |
| out、同時 2 | 7 % | 55〜86 % |
| duplex、同時 2 | 23〜69 % | 86〜100 % |

- **host が送っている間に probe の答えを受けると、その答えが壊れる**。115200 でも同じ。実験で切り分けた: 496 byte の答え（線の上 45 ms）
  の途中で host が小さな confirm を書くと 100 回中 3〜6 回答えが壊れ、書かなければ 1 回。probe 側の壊れた候補と生のバイトの数は 0
  （実験用のビルドで confirm に載せて確かめた）ので、壊れるのは probe → host の向き、host の変換チップ（かその経路）の性質。
- したがってこの ATOM では、**要求を重ねずに 1 つずつ**（同時 1）なら 1.5 Mbaud で 75〜82 KB/s が安定し、重ねると速さに関係なく壊れる。
  client の「重ねて壊れたら 1 つずつで確かめ直し、通った上限で使う」はこのためのもので、正しく働く。
- bench の V003（CH340）は同時 2 で 921600 が通る（§8）。限界は変換チップごとに違い、measure してから決める、を続ける。
- 偽の probe（pty）では同じ測り方で壊れが 0、同時 4 で 290 KB/s（線が無い分の上限）。道具の側に壊れる原因が無いことの確かめ。


## 10. 規範から移した記録（2026-10-02）

core §3.5 を、数と分岐だけで書いた手順に書き直した（ボード名・チップ名・実験の逸話は規範に置かない）。旧 §3.5 にあった次の事実と理由を
ここに残す。

- **参照の firmware の起動時の速さは 115200**（ボードの profile が決める。規範は数を決めない）。
- **切り替えの後に host が 20 ms 待つ理由**: 両端が切り替わる間に流れていたバイトが、新しい速さで 1 つ壊れた候補になる（M5Stack ATOM の
  FTDI 互換の変換（CH552）で切り替えのたびに 1 つ、§6-1）。probe が試しの状態で「新しい速さで正常なフレームを受けるまでの壊れ」を
  数えないのも同じ理由。
- **小さな confirm だけでは足りない理由**: 壊れる速さでも小さなフレームは通ることがある（V003 の CH340、230400 で confirm は通り、大きな
  フレームは全部壊れた、§3b-2）。確かめは max_frame − 16 byte の payload で行う。
- **並べて壊れたら 1 つずつ（n = 1）で確かめ直す規則の由来**: M5Stack ATOM の変換（CH552 の FTDI 互換。整数分周の速さしか作れない）は
  500 kbaud 以上で、応答を受けている間に要求を書くと応答が壊れた（§6-2、§9）。
- **両方向を交互に流す確かめ (c) の由来**: V003 の CH340 は 921600 で、片方向ずつなら通り、受信を流し続けながら要求を送ると 0.5 秒おきに
  壊れた（2026-10-01）。
- **旧 §3.5 の目安と、新しい数**: probe の自分での戻り「決めた後に壊れた候補が続いた（目安 1 秒に 3 つ）」→「正常なフレームを挟まず
  壊れが 3 つ続いた」。host の戻し「上げた速さで壊れたフレームが続いたら（目安 5 秒に 3 つ）」→「直近 100 フレームの割合が
  閾値 = max(基準 × 2, 1 %) を超えたら」（この判定は 2026-10-02 の後半に規範から外し、host 開発ガイド §7 の参考の手順になった。
  床と窓は §11 の計測で 10 % と 3 秒に変えた）。口を開く host の待ち「port_speed_idle_max_ms と少し（目安 4 秒）」→
  「port_speed_idle_max_ms + 1000 ms」。確かめの量「合わせて 1 秒か 32 KiB 以上」→「(a)(b)(c) それぞれ 16 フレーム以上、全体で 1 秒程度」。
  今の参照の firmware（oep-probe-arduino）は戻りの条件 4 を「1000 ms の間に壊れが 3 つ」で数えており、規範の「正常なフレームを挟まず
  3 つ」とは違う（直すのは probe の側）。
- **probe の自分での戻りの位置付け**: host が落ちたときのための最後の手段で、host がそれより先に気づいて揃えて下げるのが本来の形。
  速さを上げた host が落ちても、黙りが port_speed_idle_max_ms 続けば probe は戻る（lease が長くても待たない。§8 の ATOM の 3.6 s）。
- **生の転送との関係**: 生の転送（core §3.4）はセッションの間止まっているので、速さを変えている間に OEP を知らない相手（IDE の
  シリアルモニター）がその口を読むことは無い。

## 11. §3.5 の手順そのものを繰り返した計測（2026-10-02）

core §3.5 の確かめの手順（基準 60 フレーム → 候補ごとに流し方 16 フレーム以上 → 決める → 使用中の割合）を、**手順どおりに各 12 回**
回した。閾値の床、使用中の窓、基準の取り方を決めるための計測。この結果を受けて、§3.5 からは
候補・基準・閾値・使用中の判定を外して握手だけを残し、選び方と数字は [host 開発ガイド](host-development-guide.ja.md) §7 に参考として
置いた（床は確かめ 5 %、使用中 10 %。旧 §3.5 の【決める】の案 1 % は、CH340 の基準が 0〜10 % で揺れるので成り立たなかった）。

### 11.1 CH340（V003 治具、classic ESP32）

payload max_frame − 16 byte、probe → host（in）の流し方。使用中は 100 フレームの窓（合わせて 48 窓）と 3 秒の平均の両方で数えた。

| 速さ | 基準 / 確かめ | 使用中: 100 フレーム窓の割合（48 窓） | 使用中: 3 秒平均（12 回） |
|---|---|---|---|
| 115200（基準、60 フレーム） | 0〜10 %（12 回中 4 回が 0 以外。数秒まとめて落ちる） | — | — |
| 500000 | 確かめ 10/12 通る | 10 % 超 2/48 | 0〜6 % |
| 921600 | 確かめ 11/12 通る（48 フレーム合算、5 %） | 2 % 超 26/48、10 % 超 11/48、20 % 超 4/48 | 0〜19 %（10 % 超 3/12） |
| 1500000 | 確かめ 3/12 通る | — | 5〜16 %（12 回すべて 5 % 超） |

- host → probe（out）の向きは 1.5 M まで壊れが 0（§1.4 の [リンクの計測](link-measurements.ja.md) と同じ）。
- 115200 の基準が 0 と 10 % の間で揺れるので、基準 × 2 だけでは閾値が 0 になる回がある。床が要る。

### 11.2 CH552 の FTDI 互換（M5Stack ATOM、ESP32-PICO-D4）

| 速さ | n | 基準 / 確かめ | 使用中: 3 秒平均（12 回） |
|---|---|---|---|
| 115200（基準） | 1 | 0/720 フレーム | — |
| 115200（基準） | 2 | 17〜45 %（両方向同時で壊れる） | — |
| 500000 | 1 | 確かめ 12/12 通る | 0〜3 % |
| 921600 | — | confirm が返らない（整数分周で作れない） | — |
| 1500000 | 1 | 確かめ 12/12 通る | 0〜1.3 % |

### 11.3 結論

1. **使用中の窓は時間（3 秒）で取る**。100 フレームの窓は 921600 では 0.7 s しかなく、まとめて落ちる線（CH340）では 1 回の落ちで
   割合が 10〜20 % に跳ねる（11/48 が 10 % 超）。3 秒の平均なら同じ線で 10 % 超は 3/12 に落ち着く。50 フレーム未満では判定しない。
2. **基準は使う n で測る**。CH552 は n = 1 では 0/720 だが n = 2 では 17〜45 % 壊れる。n = 1 の基準で n = 2 の候補を判定すると、
   変換チップの性質（重ねると壊れる）を候補の速さのせいにしてしまう。基準が大きい流し方は n = 1 で測り直す。
3. 床: 確かめは 5 %（CH340 の 1.5 M をすべて落とし、500000 / 921600 を通す）、使用中は 10 %（CH340 の基準の上限と同じ）。
   どちらも規範ではなく、host 開発ガイド §7 の参考の値。
