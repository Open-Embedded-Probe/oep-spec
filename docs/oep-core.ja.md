# Open Embedded Probe — プロトコル本体（OEP core）v1

状態: **規範**（v1）。凍結状態と言語・互換性の方針は[版と安定性](versioning.ja.md)を参照。この文書は OEP のプロトコル本体だけを定める。インターフェースは
それぞれの文書が定める（名前が `oep.` で始まるものの一覧は [インターフェース](../interfaces/README.ja.md)）。この文書はそれだけで完結する: 読む人が規則の
理由を必要とする所では、理由を規則と一緒に書く。ガイド（§14）は実務を足すもので、規則は足さない。この文書と、規範ではない文書が食い違えば、この文書が正しい。

番号（op、tag、reject reason、status、enum）の唯一の定義は `registry/oep-v1.toml` で、この文書の表はその写しである。
食い違えば registry が正しく、文書を直す。registry は、名前が `oep.` で始まるインターフェースの名前と番号も持つ。
probe と host が適合するために何をするか、それをどう確かめるかは [適合](conformance.ja.md)（ガイド）に並べてある。

## 0. 範囲と層

OEP は 2 つの層からなる。

| 層 | 中身 | 名前 | 版 |
|---|---|---|---|
| **本体（この文書）** | どの probe と host も、機能に関係なく実装するもの: 経路とフレーム（[OEP の経路](oep-transports.ja.md)）、メッセージ、セッションと排他、発見（confirm / list / describe）、probe の時刻（clock）、channel と資源の寿命と取り合いの一般の規則、通知の仕組み、拡張の規則、任意の設定の仕組み（§13） | 持たない（fn 0 で話す。list に載らない） | プロトコルの revision（confirm） |
| **インターフェース** | 本体の仕組みだけで定義した、名前つきの機能。本体が必須としない機能は、すべてインターフェースにある | 逆 DNS の名前。project 自身のものは短い `oep.` の名前（§12） | インターフェースごとの revision |

インターフェースどうしの関係（あるインターフェースが別のインターフェースの資源を使う、など）は、関係するインターフェースの
文書が定める。

本体の対象外: probe自身のfirmware更新の手順（DFU、Mass Storageなど）、USBの記述子の細部。
自己更新や認証の固有機能は、§12に従って任意のインターフェースとして定義できる。本体へ更新操作や認証の必須機能は追加しない。

**外部の仕様**: OEP のプロトコルは、これらの文書だけで定まる。target、バス、経路を動かすには、それぞれの文書が「参照する仕様」の節に並べる
外部の仕様も要る（経路のものは [経路](oep-transports.ja.md) §8）。

## 1. 用語

| 用語 | 意味 |
|---|---|
| probe | OEP を話す装置（デバッガ、治具、ロジアナなど） |
| host | probe を使うソフトウェア |
| target | 操作・観測の対象（開発中のマイコンなど）。probe自身を対象としてよい。その場合もOEP端点としての役割はprobe |
| 経路（transport） | OEP のフレームを運ぶもの（UART bridge、USB CDC、内蔵の USB シリアル、USB の vendor bulk、HID、TCP） |
| シリアルの口（serial port） | 経路のうち OS からシリアルデバイスに見えるもの（UART bridge、USB CDC、内蔵の USB シリアル）。OEP のフレームだけを運ぶ（[経路](oep-transports.ja.md) §4） |
| インターフェース | probe が名前で出す機能。list で見つけ、fn で呼ぶ |
| fn | 同じ boot_id の間、インターフェースを指す番号（u16、§7.2）。fn 0 は本体（名前を持たず、list に載らない） |
| op | インターフェースの中の操作の番号（u8） |
| セッション | ロックを持って状態を変える権利。host が選ぶ session_id（u32）で識別する |
| lease | ロックの期限。keepalive などの要求で延びる |
| channel | probe のピン。名前（チップのデータシートのピンの名前、§7.5）で識別し、wire では同じ boot_id の間の番号（u16）で指す |
| 設定 | probe が起動を越えて保つ値。本体が取りまとめ、項目の持ち主（本体かインターフェース）が決める（§13） |

### 1.1 規範の語

大文字の MUST、MUST NOT、SHOULD、SHOULD NOT、MAY は RFC 2119 と RFC 8174 のとおりに使う。probe や host がすることを現在形で述べた文（「probe は〜を返す」）は要件（MUST）である。「できれば」は SHOULD。（参考）と記した文、例、注は規範ではない。日本語の訳では、「〜する／〜しない」が MUST / MUST NOT、「〜してよい」が MAY、「できれば〜する」が SHOULD にあたる。

### 1.2 適合

probe が実装しなければならない（MUST）もの:
- §3 の経路の少なくとも 1 つと、そのフレーム;
- §4〜§6;
- fn 0 の confirm、list、describe、clock、open、end、keepalive、lock_state;
- fn 0 の describe の unit_id、transport、max_op_ms（§7.5）;
- fn 0 と、list に載せるすべての fn の describe の、共通の tag ops（§7.4）;
- channel を持つなら、fn 0 の describe の channels（§7.5）と §8 の channel の空きの状態;
- 通知を送り出すインターフェースを持つなら、§10.3 と §10.4;
- 設定を持つなら、§13（save は任意）。

任意: すべてのインターフェース。あるインターフェースを出す probe が、ほかにどのインターフェースを出さなければならないかは、そのインターフェースの文書が定める（§0）。

**最小の実装**: probe は経路を 1 つだけ持ち、`max_frame = 64`、`window = 64`、`max_inflight = 1` としてよい。
要求を 1 つずつ処理し、名前付きインターフェース、通知、ピン、インターフェースの資源を持たなくてよい。
複数経路、複数の未解決要求、通知の送信は、それを提供する場合の義務であり、最小の実装へ要求しない。
要求・応答の再送用の保持量は §5.1 のとおり制限でき、再送の byte 記録を持たず最後の番号だけで旧要求を断ってもよい。
動的なメモリ確保、スレッド、ハードウェアの 64 bit タイマーを実装方法として要求しない。

**必ず持つ op と任意の op。** インターフェースの op の表（fn 0 は §11、ほかはそのインターフェースの文書の op の表）の op は、そのインターフェースを list に載せる probe が必ず持つ。文書が任意と書いた op は除く。**すべての fn は、持つ op を 1 か所で宣言する: describe の共通の tag ops（0x07、§7.4）。** 必須の op はすべてそこに立てる。任意の op は、probe がそれを持つときに限り立てる。

probe は、その fn の ops が立てない op（インターフェースが定義しない op、または持たない任意の op）の要求に rejected unknown_operation で答える（§4.3）。持つ op に、宣言しない任意の機能（mode、format、値、critical の TLV、ピンの組み合わせ）を求める要求には rejected unsupported で答える（§4.3）。

## 2. 共通の規則

### 2.1 byte order と文字列

数値はすべて little endian。文字列は UTF-8 のバイト列で、長さは別に持つ（終端の 0 は付けない）。
**bitmap** は byte の並びで、bit i は byte ⌊i/8⌋ の bit (i mod 8) である（bit 0 は最下位の bit）。bitmap は、それを含む値の終わりまで続く。

- 真偽値の u8 は、送る側が 0（偽）か 1（真）を置き、読む側は 0 でない値をすべて真と読む。
- host は、応答の text を見せる前に、C0 の制御文字（0x00〜0x1F）、0x7F と正しくない UTF-8 を置き換える。

### 2.2 TLV

```text
tag(u8) | len(u16) | value(len byte)
```

- **すべての TLV が 1 つの形**で、値の長さ（0〜65535 byte）によらない。len がそれを含む message の終わりを越える TLV は、
  要求では malformed。応答、出来事、データの中にあれば、その応答、出来事、データは壊れている。
- **tag の番号は下位 7 bit（0x01〜0x7F）。** bit 7 は critical の印。要求の中でだけ使い、番号には含めない: 0x10 と 0x90 は同じ TLV を、印なしと印ありで送ったもの。応答、出来事、データでは bit 7 は 0 で、そこで bit 7 の立った TLV に会った読む側は、知らない tag として読み飛ばす。
- TLV の番号 0（critical bit の有無を問わない）は要求では malformed、応答・通知では壊れた TLV。unsupported の固定部分の印 0 は TLV ではない。
- rejected unsupported の payload は、受け取ったままの tag の byte（bit 7 を含む）を持つ。
- tagの空間は、そのpayloadの定義の文脈ごとである。要求・応答では(fn, op)と応答のresolution/reason、describeでは宣言対象のfn、
  データではfn、出来事では(fn, kind)が文脈を決める。同じ番号でも文脈が違えば別物である。
- 同じ tag の繰り返しは、繰り返すと定義が言う tag で、並びを表す（§2.3）。
- **名前つきの拡張 TLV（tag 0x7F）**: どの文脈でも、tag 0x7F は名前つきの拡張に予約する。値は
  `name_len(u8)、name、data`。name は §12 規則 1 のインターフェースの名前と同じ形の逆 DNS の名前で、data の形と意味は
  その名前を持つ者が決める（§12 規則 7）。どの定義も tag 0x7F に別の意味を与えない。
  - 名前は revision を持たない。同じ名前の data は、どの文脈、どの probe でも同じ形と意味を持つ。形か意味を変えるときは、新しい名前にする。
  - 繰り返してよい。同じ名前を 2 つ置けるかは、その名前の定義が決める。
  - 要求で、知らない名前の拡張は、critical（0xFF）なら rejected unsupported（payload の tag は 0xFF）、そうでなければ無視する。
    name_len が値に収まらない拡張は malformed。
  - 応答、出来事、データ、describe で、読む側は知らない名前の拡張を読み飛ばす。

### 2.3 固定の形と TLV

- **容器は自分の長さを知る**: フレーム、TLV、並び、バイト列（data）のどれも、読む側が要求や外の知識なしに終わりが分かる。
  可変の部分（並び、バイト列、文字列）には前に数か長さを置く。
- **固定の形はどれも (名前, revision) で決まる**（fn 0 ではプロトコルの revision、§2.8）: 要求、応答、出来事、データの payload の固定部分、TLV の値、並びの
  要素、設定データの項目。固定の形は後ろに伸ばさない。その中の可変の部分（名前、要素の中の一覧）は前に数か長さを
  置くので、固定の形も自分の長さを知る。
- **並び**: `count、count × 要素`。要求でも応答でも同じ。要素は自分の長さを持たない。要素の形は revision で決まり、読む側は
  フィールドを 1 つずつ読む。
- **応答**: 各 op の応答の固定部分（と、前に数か長さを置いた並び）の後ろは TLV の並び。後から足すものはすべてここに TLV で足す。
  host は知らない tag を読み飛ばす。固定部分より短い応答は壊れた応答として扱う。応答、出来事、データの TLV で、値が定義の
  決める長さ（可変の部分を持つ値なら、その数と長さが決める長さ）を持たないものは壊れている: host はそれを使わない。
  **応答の固定部分の形は (op, resolution, outcome) ごとに
  op の定義が決める**（成功と失敗で形が違ってよい。インターフェースの共通部品 §3）。
- **出来事とデータ**（§10.2）も応答と同じ: 固定部分の後ろは TLV の並び。
- **要求**: 要求の後ろに足せるのは TLV の並びだけ。host は、効かなければ要求に意味が無いか、害があるTLV（attachのreset、scanのmax_speedなど）に
  **critical の bit を付ける**。
- **知らない TLV**（この probe が実装しない tag）: critical なら、probe は要求を rejected unsupported（payload に受け取ったままの tag）で断る。
  critical でなければ無視する。
- **実装する TLV** は、bit 7 によらず同じに扱う: 値の長さが定義と違う（可変の部分を持つ値なら、その数と長さが決める長さと違う）か、定義が除く値を
  持てば rejected malformed。定義が使わずに残した値と、この probe が扱わない値は rejected unsupported（受け取ったままの tag）。
- **要求の TLV の値は後ろに伸ばさない。** 新しいフィールドは新しい tag に置く。
- 繰り返すと定義が言わない tag が 2 つ以上あれば、読む側は最初のものを使う。後続の同じtagも上の検証対象である。
  例えば、正常な既知TLVの後に同じtagで不正な長さの値があれば、要求全体をmalformedで断る。
- 固定部分より短い要求は rejected malformed。
- **可変の並びは前に数を置く**（後ろに TLV を付けられるように）。
- 固定部分に省略できるフィールドを置かない（省略したい値は TLV にする）。

### 2.4 知らない値

- 知らない role のフレームは捨てる。
- probe は、role が要求の role（0x01）でない message と、見出し（10 byte）より短い要求を、答えずに捨てる。host は、role が要求の role の message を捨てる。
- host は、5 byte より短い応答と、見出しより短い出来事やデータのフレームを、壊れたフレームとして扱う（§5.1、[経路](oep-transports.ja.md) §5）。
- 知らない resolution、completed の知らない outcome は失敗として扱う。
- インターフェースの status や reason の知らない値は失敗として扱う。
- 知らない出来事の kind は捨てる（seq は数える）。
- host は応答の flags の予約のビットを無視する。応答の enum の知らない値で失敗を知らせないもの（cause、scan の entry の kind）は、知らない値として見せる。status と reason の知らない値は失敗のまま。

### 2.5 番号の空間

| 空間 | 範囲 |
|---|---|
| role | 0x01 要求、0x02 応答、0x03 出来事、0x04 データ。0x00 は無効、ほかは未割当 |
| 本体（fn 0）の op | 0x01〜0x0F 発見、0x10〜0x1F セッション、0x20〜0x2F 設定（§13、経路の network）、0x30〜0xFF 未割当 |
| インターフェースの op | 0x01〜0x0F は共通操作専用（0x01 subscribe、0x02 unsubscribe）。0x10〜0xFF は各インターフェースの操作 |
| reject reason | 0x01〜0x3F 本体（全インターフェース共通）、0x40〜0x7F インターフェース、0x80〜0xFF 未割当 |
| unavailableのcause | 0x01〜0x3F 本体、0x40〜0x7F 要求先fnのインターフェース、0x80〜0xFF 未割当。fn 0は固有範囲を使わない |
| outcome | 0 success、1 failed、2 partial。ほかは予約 |
| 出来事の kind | fn ごとの空間。0x01〜0x7F はインターフェースが決める、0x80〜0xFF は未割当（fn 0 は通知を送らない、§10.2） |
| TLV の tag | payloadの文脈ごと（§2.2）。番号は下位 7 bit で、bit 7 は critical の印（§2.2）。0x00 は全文脈で無効、0x7F は全文脈で名前つきの拡張 |
| describe の tag | 0x01〜0x3F 本体の共通タグ（§7.4）、0x40〜0x7E インターフェース、0x7F 名前つきの拡張（§2.2） |
| 資源の番号 | u32（1〜0xFFFFFFFF、0 は割り当てない）、probe で 1 つの空間（§9） |

未割当は、まだ意味を定めていない番号。共通操作専用の範囲は、その所有者だけが割り当てられる。
無効な番号（role / op / TLV の 0）は構造上使わない。凍結後に廃止した番号は retired として記録し、再利用しない。
凍結前に削除した番号は再整理して再利用してよい。将来の用途を推測して個別の番号を予約しない。

**番号の振り方**（本体とすべてのインターフェース）:

1. 番号を振るのは、その空間の持ち主（本体は project、インターフェースはその名前の持ち主）だけである。ほかの者は番号を取らず、
   名前で識別する（名前つきの拡張 TLV、§2.2、名前の並び、§7.7、自分のインターフェース、§12）。だから、ほかの者のための番号の範囲は置かない。
2. 範囲に意味を持たせるのは、(a) 1 つの空間を複数の持ち主が振るとき（本体・共通部品とインターフェース。上の表の範囲）と、
   (b) 読む側が知らない値の扱いを番号から決めるとき（tag の bit 7）だけである。
3. それ以外は、持ち主の範囲の先頭から定義の順に連番で振る。凍結前は欠番を作らない（reject reason 0x05 は、本体の基準を保つため退いた番号として残す）。
4. 複数のインターフェースが同じ意味で使う値（同じ一族の TLV、role、enum）は、一族の共有の空間として 1 か所で定義し、
   各インターフェースはその一部を同じ番号で使う。一部が飛び飛びになってよい。
5. 外の仕様が決める値（protocol の応答の値、ビットの位置）は、その値のまま使う。ビットの集合はビットの位置で表す。

定義が別に言わない限り、enum の使っていない値と要求の予約のビットは、どれも後から定義されうる（§2.8）。probe はそれらを rejected unsupported で断る。

### 2.6 一周する値

corr（u16）の循環と再送の比較は §4.1、§5.1 の半周規則に従う。下の保持範囲の規則は corr には適用しない。

seq（u16）と、インターフェースが定める通し番号や時刻のうち一周すると定めたものは、差を同じ幅 w の符号付きとして
比べる（serial number arithmetic）。そうした 1 つの空間の値のうち、probe が同時に持つもの（例: まだ読める記録、まだ解放していないデータ）では、
いちばん新しいものからいちばん古いものを引いた差は 2^(w−2)（幅の 4 分の 1）未満。一周させないストリームの位置と時刻は u64 にする
（インターフェースが定めるストリームの位置、時刻など）。資源の番号（§9）は等しいかどうかだけを比べ、同じ boot_id の間は使い回さない。

### 2.7 時計

probe の時計は 1 つ: **起動からの ns（u64）**。時計は、同じ boot_id の間、減らず、一周しない。probe自身の時刻として返す値（clockのuptime_nsなど）はすべてこの値で、
「まだ無い」は全ビット 1。
hostは時計の今の値をclock（§7.6）で読む。別の時計の値を運ぶインターフェースは、その時計の主体・起点・単位を自分の定義で明記し、probeの時計と暗黙に混ぜない。

**ns は表す単位であり、分解能の要求ではない。** probe は自分の時計の tick を ns へ換算してよい。同じ tick の間に読んだ値は同じでよい。
短いハードウェアカウンターをソフトウェアで延長してよい。延長する場合は、カウンターの一周で時刻を失わず、同じ boot_id の間の単調性を保つ。
インターフェースが特定の精度や分解能を必要とするときは、そのインターフェースが能力と条件を定める。

### 2.8 名前と revision

- インターフェースのどの**固定の形**（§2.3: 固定部分、TLV の値、並びの要素、項目）も、形と意味は **(名前, revision) で決まる**（list の revision、u8）。
- **revision を上げるのは、既存の契約を壊すとき**。固定の形の意味か長さ、必須操作、状態遷移、資源の寿命などを変え、既存の host または probe が従来の契約で動けなくなる変更を含む。任意の操作や機能を必須にする変更も含む。host は知らない revision のインターフェースを使わない。
- 既存の形と振る舞いの契約を保ち、任意の request TLV、response TLV、任意の op、任意の event を足すときは、revision を変えない。知らない
  host はそれらを使わない。任意の op の有無は ops（§1.2、§7.4）で、op でない任意の機能（モード、format など）の有無は describe（features など）で宣言する。
- 本体の形または既存の契約を壊す振る舞いを変えるときは、プロトコルの revision（confirm）を上げる。この文書の形は revision 1。

## 3. 経路

メッセージは経路のフレームで運ぶ。経路は [OEP の経路](oep-transports.ja.md) が定める。その文書は本体の一部である。

## 4. メッセージ

### 4.1 要求

```text
role=0x01 | corr(u16) | fn(u16) | op(u8) | session_id(u32) | payload    見出し 10 byte
```

- `corr`: 0 を使わない u16。host は **session_id ごと**に、新しい要求の番号を循環して前へ進める（通常は 1 ずつ、65535 の次は 1）。
  前進距離 `d = (new − previous) mod 65536` は 1〜32767（`corr_half_range` 未満）。初回の非zero番号は host が選ぶ。
  host は、そのセッションの最古の未解決要求からの前進距離が 32768 以上になる新しい要求を送らない。解決するか、§5.1 に従って回復する。
  session_id 0 の要求の番号はセッションの順序に影響しない。大量の session_id 0 の照会で、セッションの番号を半周以上飛ばさない。
  同じ経路では、session_id が違っても未解決要求の corr と、古い応答が残りうる corr を再使用しない。必要ならその番号を飛ばす。
  最後の再送コピーより後に送った別番号の要求への応答を受け取れば、順序を保つ経路でそれより前の応答を読み終えたと確認できる。
  排出を確認できなければ経路を立て直す。新規セッションの開始や session_id 0 の番号の周回も、この再使用規則を守る。
  送り直しは番号を含む要求全体を byte 単位で同じにする。解決済みの要求を後から送り直さない。
- `session_id`: 要求が属するセッション、または **0 = セッションなし**。どの要求もこれを持つ。
  - ロックが要る op（§6.3）の要求は、ロックを持つセッションの id を持つ。0 なら rejected session_required。
  - ロックなしの op の要求は 0 を持ってよい: そのときはセッションの確かめ（§5.1、§6.2）なしに処理し、lease に触れない。0 でない id なら、
    ロックが要る要求と同じくそれらを通り、lease を数え直す（§6.1）。
  - open は、開くセッションの id を持つ（§6.4）。0 なら rejected malformed。

### 4.2 応答

```text
role=0x02 | corr(u16) | resolution(u8) | detail(u8) | payload           見出し 5 byte
```

| resolution | 値 | detail | payload |
|---|---:|---|---|
| rejected | 0x00 | reject reason（§4.3） | reason が定める補助の情報 |
| completed | 0x01 | outcome（0 success、1 failed、2 partial） | op が定める |

- 要求ごとに応答はちょうど 1 つ。応答はその要求の来た経路に、同じ corr で返す。fn と op は返さない。
  未完了要求の再送コピーを§4.4に従って捨てる場合は、元の要求の応答1つをそのコピーにも共通の結果とする。
- **rejected は「要求を受け付けなかった」ときだけ**（書式、番号、セッション、今の状態で受けられない）。受け付けて実行した
  結果うまくいかなかったものは completed の failed か partial にし、payload でどこまで進んだかと理由を返す。
- completedの進捗の計測点はopが定める。外部targetへの書き込みでは、failedや進捗0でも作用が無かった保証にはならない。
  インターフェースは、送信済み・完了確認済みなどの計測点と、結果不明時の扱いを定める。hostは失敗だけを根拠に状態変更を自動再実行しない。

### 4.3 reject reason（本体）

| 値 | 名前 | 意味 | payload |
|---:|---|---|---|
| 0x01 | unknown_function | その fn は無い（見出しの fn、または payload で指す fn） | — |
| 0x02 | unknown_operation | その fn にその op は無い | — |
| 0x03 | malformed | 長さ・値域の誤り | — |
| 0x04 | unavailable | 今の状態・資源・方針では受けられない | TLV の並び（任意、下） |
| 0x06 | window_exceeded | window / max_inflight を超えた | — |
| 0x07 | no_session | 要求は session_id を持つが、どのセッションもロックを持っていない（セッションが終わった、または初めから無い）。host はセッションを開き直す | — |
| 0x08 | locked | 他のセッションがロックを持つ | 残り時間 ms（u32）、[TLV owner（§6.4）] |
| 0x09 | session_required | ロックが要る op の要求が session_id 0 を持つ | — |
| 0x0A | no_resource | 要求の資源（connection、stream など、番号で指すもの）を probe が知らない。host は作り直す。どのインターフェースでも、知らない番号にはこれを使う | — |
| 0x0B | unsupported | 定義にはあるが、この probe が扱えない（critical の TLV、固定部分の値、この probe が持つ op の任意の機能） | `tag(u8)`、[TLV]。tag は critical の TLV なら受け取ったままの値、固定部分の値なら 0x00。どの要素かを示すときは後ろに TLV（unavailable と同じ tag の空間: channel、index） |
| 0x0C | result_lost | 送り直された要求の結果を覚えていない（§5.1） | — |

rejected の detail は reason で、そのほかの情報は payload に置く。表の `—` は固定部分のフィールドが無いことを表す。応答の固定部分の後ろへ TLV を足す §2.3 の規則は、固定部分が空の成功応答と rejected にも掛かる。知らない応答 TLV は読み飛ばす。

**断り方の順**: probe は次の順に見て、最初に当たったもので答える。

1. 見出し: corr 0 は malformed。そのほかは unknown_function → unknown_operation（その fn の ops が立てない op、§1.2）→ session_required。その後、下の任意の方針判定。
2. 送り直し: 未完了のコピーは§4.4に従って捨ててよい。処理済みなら§5.1の表でresult_lost / 覚えた応答。
3. セッション（§6.2）: no_session / locked。
4. そのほか: probe は、書式（malformed: 長さ、中身と合わない数、TLV の符号化、フィールドどうしの矛盾、定義が除く値）、対応（unknown_function: payload で指す fn が無い。
   unsupported: 定義が使わずに残した値、この probe が宣言しない値、知らない critical の TLV、宣言が許さないピンの組）、状態（window_exceeded、unavailable: 今の状態や資源で受けられない。
   no_resource: 番号で指す資源を知らない）を、何も変える前にすべて確かめ、当たった理由のどれか 1 つで断る。

**任意の方針判定**: probeは、経路、経路で認証した相手、物理的な在席確認、製品のmodeなどの方針で要求を拒否してよい。
その場合はrejected unavailableにcause 7のTLVを付ける。fn 0のconfirm / list / describe / clock / lock_stateは、この方針では拒否しない。
方針を持たないprobeは、この判定を省ける。認証方式、認証用の操作や宣言、権限状態の保持は本体の必須機能ではない。
判定は見出し確認後、再送のコピーの処理・保存済み応答の返却・session判定より前に行う。
方針で拒否した要求は実行せず、再送履歴、lease、所有者、資源を変更しない。保存済みの元の応答も置き換えない。
これは要求を処理するときの判定であり、受理済み操作の取消しや送信中の応答・通知の停止を保証しない。
権限の失効と受理済み操作・出力の扱いは、その方針を提供する経路または拡張が定める。
方針はロックの条件を免除しない。session_idやowner文字列だけを本人・権限の証明にしない（§6）。

unsupported の payload の tag は、固定部分の値なら 0x00、TLV についての断りならその TLV の受け取ったままの tag。

**unavailable の payload**（任意の TLV の並び。host は知らない tag を飛ばし、無くても扱えるようにする。probe は分かる範囲で付ける）:

| tag | 名前 | 値 |
|---:|---|---|
| 0x01 | cause | u8: 1 ピンが使われている、2 数・処理能力の上限、3 保存先が足りない、4 ほかの fn に束ねられている、5 設定が使用を制限している、6 状態が違う、7 方針で許されない |
| 0x02 | channel | u16。ぶつかった channel（繰り返してよい） |
| 0x03 | item | u8。断りの対象の、要求の中の並びの位置（0 から。設定の set と unset の値、§13.5） |
| 0x05 | fn | u16。断りの対象の fn |

インターフェースは 0x40 以降に自分の tag を足せる。rejected unsupported の payload の後ろの TLV も同じ空間（channel 0x02、fn 0x05、
インターフェースの index など）。ただしそこでは 0x01 は supported で、confirm の断りに使う（§7.1）。item（0x03）も同じ空間にある。
causeの0x40〜0x7Fは、要求先fnのインターフェースが自分の定義で使える。診断のfn TLVが指す別fnの値へ読み替えない。

### 4.4 パイプライン

- confirm（§7.1）で probe は `max_frame`（受け取る最大の message 長）、`window`（未解決の要求の message 長の合計の上限）、
  `max_inflight`（未解決の要求の数の上限）を返す。message 長は見出し（role から）を含み、フレームの包み（COBS、CRC、length）は含まない。
- host はこれらの上限を守る。超えた要求を probe は rejected window_exceeded で断ってよいが、バッファを超えて失われた要求には
  応答も返らない。守るのは host の責任である。
- probeは、各経路のwindow / max_inflightを守る新規要求を、先行要求の処理中も失わずに受ける。
  受信処理を止める方式は、受信の保持や経路の流量制御などでこの条件を保てる場合だけ使う。
  1経路・max_inflight=1では、hostは応答まで次の新規要求を送らない。未完了の再送コピーは下の規則に従って捨ててよい。
- window / max_inflightは、その経路の異なる未解決要求について数える。同じ経路・session_id・corrの再送コピーは、新たな未解決要求として数えない。
  元の要求が処理待ち・実行中・応答送信前または送信中なら、probeはそのコピーを別に保持せず、内容を照合せずに捨ててよい。
  元の要求を再実行せず、そのコピーだけを理由にleaseや処理期限を更新しない。応答を送り終えた後の再送は§5.1に従う。
  この未完了コピーの扱いはsession_id 0にも適用する。hostは再送でも要求全体を同じbyte列にする（§4.1）。
- 要求が収まっても、要求の引数から必要となる固定結果がその経路のmax_frameへ収まらない場合は、probeは実行前にrejected unsupported（固定部分の印0）で断る。
  結果の短縮・prefix・ページングをインターフェースが定める場合は、その規則で収める。成功に必要な結果を捨ててsuccessにしない。
- probe は要求を受け取った順に処理し、その要求の順に応答を返す。
- confirm の max_frame、window、max_inflight は、**その confirm が来た経路の**上限である。経路ごとに別々に数え、ある経路で未解決の要求は、ほかの経路の受けの余地を使わない。§5.1 の表は probe に 1 つのまま（セッションの要求は 1 つの経路で送る、[経路](oep-transports.ja.md) §3）。
- **host の待ち時間**: 応答が来ないことは時間切れだけで判断する。host は要求ごとに**少なくとも**次を待つ: 要求全体の処理時間の上限
  + 1000 ms（`host_wait_add_ms`）+ 転送の時間（[経路](oep-transports.ja.md) §6）。処理時間の上限は max_op_ms（§7.5）。操作の定義が、
  検証・内部の再試行・実行・後始末を含む要求全体について、それより短い上限を定める場合だけ、その上限を使ってよい。
  fn 0のconfirm / list / describe / clock / keepalive / lock_stateの要求全体の処理上限は、max_op_msと `core_quick_op_max_ms`（1000 ms）の小さい方である。
  この上限には検証と応答の組立ても含み、経路の転送時間と、同じ経路・別の経路の先行要求の処理が終わるのを待つ時間は含まない（§7.5 と同じ）。
  起算はその要求自身の検証を始める時点で、検証後の内部待ちや後始末は含む。別経路の要求に割り込む処理や並列処理は要求しない。
  別経路の先行要求待ちがある場合、送信から応答までがこの処理上限に収まる保証ではない。
  open / end の後始末にはこの短い上限を課さない。
  引数の待ち時間だけを要求全体の上限として使わない。host は状態を変える要求の前に fn 0 の describe で max_op_ms を取得する。
  max_op_msをまだ取得していない間は、これらの処理上限にcore_quick_op_max_msを使う（待ちの下限は2000 msと転送の時間）。
  待ちは、要求を書き終えた時から始める。同じ経路に先の要求が未解決の間は、その 1 つ前の要求の応答が届いた時から始める（probe は順に答える）。
  この下限より長く待つことはいつでも許される。待ちが過ぎたら §5.1 の送り直しに進む。
- **この下限はすべての要求に当てはまる**。インターフェースの文書が要求と要求の間に置く待ちは、応答を待つ時間ではなく、この下限を縮めない。
  [経路](oep-transports.ja.md) §4 が、任意の port_speed を扱う host に許す confirm の繰り返しは、それぞれ新しい corr の新しい要求で、§5.1 の送り直しではない: host は、前の confirm の下限が過ぎる前に次を送ってよく、後から届いた前の corr への応答は受けるか読み飛ばす。通常の探りは同 §3 に従う。ほかの要求はこのように繰り返さない。

## 5. 立て直しと送り直し

### 5.1 再送と結果の保持

- 応答が来ないか壊れたとき、host は同一の要求を送り直してよい。実行済みか分からない要求を、新しい corr で自動的に再実行しない。
- probe は最後に成功した新規セッションについて、最後に受けた新しい要求の corr を持つ。この順序状態は必須。
  要求・応答の再送用の記録は任意で、件数と byte 数に上限を置いてよく、0 件でもよい。max_inflight は未解決要求の受け付け数で、再送記録の件数を定めない。
  記録を持つ場合、キーは (session_id, corr)、要求の同一性は見出しと payload の全 byte。open も同じ規則で扱う。
  半周以上過去の記録は捨て、照合に使わない。
- §4.3の見出し・方針判定を通った後、順 2 で、記録した要求と同じ corr が来たら、要求の全 byte を保持していない場合は rejected result_lost。
  保持していれば内容を比較し、違えば rejected malformed。同じ場合は記録した応答を返す。応答を保持していなければ rejected result_lost。
  いずれも再実行せず、lease や通知の送り先を変えない。任意の方針で拒否された要求にはこの記録を返さない（§4.3）。
- 同じセッションの記録に無い番号は、最後の番号との差 `d = (corr − last) mod 65536` で判定する。
  `0 < d < 32768` なら新しい要求、それ以外（同じ番号と半周ちょうどを含む）は rejected result_lost。
  要求・応答の保持に大きさの上限を置いてよい。保持していない旧要求も最後の番号とこの比較で再実行を防ぐ。
  この判定は §4.1 の host と経路の順序規則を前提とする。半周より古い要求を再投入しても世代を区別する保証はない。
- 最後に成功した新規セッションの新しい要求で §4.3 の順 2 を通ったものは、後で rejected となるものも含めて最後の corr を更新する。
  byte 記録を持つ場合はその保持上限の範囲で記録する。要求を直すときは新しい corr を使う。
- end と期限切れでも順序状態を残す。保持中の byte 記録も、その保持上限と半周の規則に従って残す。同じ ID の open で再送状態を初期化しない。
  **異なる ID の新規セッションの open が成功したときだけ**、前の再送状態を捨て、その open から新しい状態を始める。
  hostは終了したidでsessionを再開せず、idを意図的に循環・再利用しない。新しいsessionには乱数を新しく選ぶ。偶然の衝突については§6.1。
- session_id 0の処理済み要求は重複排除しない。未完了コピーは§4.4に従って捨ててよい。corr 0 の要求は rejected malformed。
- この再送状態は probe に 1 つで、すべての経路で共有する。OEP の要求へ自分で答える broker もこの規則に従う。
- 再送を諦めたら、その経路の未解決の要求は結果不明となる。host は TCP では接続を閉じて開き直し、ほかの経路では
  [経路](oep-transports.ja.md) §5 に従って立て直す。boot_id を確認し、状態を読んでから次の状態変更を判断する。
- 再接続後の同一要求の再送にも半周の範囲を守る。番号の進行や古い queue の排出を確定できなければ、新しい session_id で回復する。
  host と broker は、旧経路に残った要求・応答を新しい経路へ自動的に再投入しない。新しいセッションによる資源解放は §9 のとおり。


## 6. セッションと排他

### 6.1 ロック

- probe は**ロックを 1 つ**持つ。ロックを持つセッションだけが状態を変える要求を実行できる。
- host はセッションごとの session_id を、予測できない 32 bit の乱数で選ぶ。決まった値や 0 は使わない。session_id 0 の open は rejected malformed。probe は最後にロックを持った session_id を覚えている。
  乱数の偶然の一致は起こりうる。hostに過去の全idの履歴保持は要求しない。
  idが一致する要求は同じsessionとして扱われ、通信だけで衝突を識別できる保証はない。session_idをhostの身元や権限の証明には使わない。
- leaseはopenで決まる。ロックの持ち主の新規要求で§4.3の順3を通ったものは、検証・実行・後始末・応答生成の間だけleaseを止める。
  応答を生成した時点からlease_msを数え直す（rejectedの応答も含む）。この起算は応答の送信待ち・送信完了によらず、経路が閉じて応答を捨てる場合も同じ。
  endで終了した旧sessionのleaseは更新しない。新規openは新しい所有者の応答生成からleaseを始める。
  処理済み要求の再送、未完了の再送コピー、session_id 0や他sessionの要求、通信の送受信待ちは、所有者のleaseを止めず、更新もしない。
  長い所有者のopはleaseより長くてもsessionが切れない。処理時間の上限はmax_op_ms（§7.5）。
  期限を過ぎたsessionの資源は§9に従って解放する。逐次処理のprobeは他session/session_id 0の要求を処理した後に期限切れの後始末を行ってよいが、
  次の要求の処理（再送判定も含む）や、新しい通知・資源操作より前に行う。割込みや別threadでピンを期限ちょうどに戻すことは要求しない。

### 6.2 要求を受けたときの判定

probe は、ロックの有無、ロックを持つ、または最後に持った session_id（以下 S。§5.1 の再送状態はこれに結びつく）、ロックが持たれている間の
owner（表示を実装する場合）を覚えている。§5.1 の判定（送り直し）はこの表より先。session_id 0 のロックなしの op の要求はここに来ない（§4.1）。

| ロック | 要求 | 結果 |
|---|---|---|
| 空き | open（session_id ≠ 0、最後に終了した ID と異なる。force の有無を問わない） | ロックを立てる: S をこの id にし、lease を lease_ms から始め、owner は open の示すとおり |
| 空き | 終了した最後の ID の新しい open、または session_id ≠ 0 のほかの要求 | rejected no_session |
| S が持つ | session_id S の open（force の有無を問わない） | 新しい corr の open: lease_ms を更新する。資源と再送履歴を残す。購読の送り先は変えない（同一要求の再送は §5.1） |
| S が持つ | 別の id の open、force なし | rejected locked と残り時間（と owner） |
| S が持つ | 別の id の open、force あり | 奪う（§6.4）: S の資源を解放し（§9）、それから新しい id のロックを立てる |
| S が持つ | session_id S のほかの要求 | 処理する |
| S が持つ | 別の id のほかの要求 | rejected locked と残り時間（と owner） |

### 6.3 ロックの要る要求

targetの状態、ピンの駆動、設定、実行時の資源、購読、保持データの消費を要求の作用として変える操作はすべてロックが要る（セッションのidを持つ、§4.1）。
ロックなしで使えるのは、それらを変えない読むだけの要求に限る
（confirm、list、describe、clock、lock_state、インターフェースが定める読むだけの op）。インターフェース
がロックなしとするopは、それらの状態を変えてはならない。confirmの経路ごとのrevision選択と、フレーム受信・時間経過による経路のtimer/復帰、
非同期の取得・受信の進行は、この操作の作用とは区別する。session_id 0の要求で所有者のleaseを止めたり更新したりしない（§6.1）。

### 6.4 open、end、keepalive、force

- **open**（lease_ms、force。session_id は見出しのもの、§4.1）: ロックを取る。応答は lease_ms（probe が決めた値）と boot_id。**再開は
  無い**: 終わったセッションは、どの要求でも続かない。host は新しいセッションを開く。異なる ID の新規セッションの open が成功したときだけ §5.1 の再送状態を置き換える。end と期限切れでは順序状態を残す。
- **lease_ms**: 0 は「probe の既定」。probe は 1000〜60000 ms の要求をそのまま受け、範囲の外は範囲の中に丸める（既定は
  probe が決める）。応答の lease_ms は lease_min_ms〜lease_max_ms（1000〜60000）の中にある。host は応答の lease_ms を正とする。
- **end**: ロックと、セッションが作ったものすべてを解放する（§9）。lease の期限切れと force も同じ。
- **keepalive**: lease を延ばすだけ。
- **lock_state**: ロックの有無と残り時間（ロックが空いていれば 0）。locked は「どのセッションであれロックが持たれている」（lock_state はセッションを
  持たずに送れるので、probe には誰が聞いたかは分からない。自分が持っているかは host が自分の状態で知る）。
- **owner（任意の表示機能）**: open の TLV 0x01 owner（text、1〜32 byte、非 critical）で、host は持ち主の名前（例 "flash-tool pid 1234"）を
  付けてよい。probe は owner の保持と表示を実装しなくてよい。実装しない probe は、owner を知らない TLV として §2.3 に従って扱い、非 critical の owner は無視する。
  owner はロック取得の成否やセッションの識別には使わず、host は返らないことを失敗とみなさない。実装する probe は owner をロックを立てる open から取り、ロックが持たれている間覚え（持つ側の id の open では変えない）、ロックが
  終わると忘れる。ロックが持たれている間、lock_state の応答と rejected locked の payload の後ろに
  TLV 0x01 owner で付ける（owner が無ければ付けない）。owner は表示のためだけのもので、
  probe は解釈しない。（参考）owner は lock_state でどの host からも読めるので、host は秘密を入れない。
- **force**: 他のセッションがロックを持っていても奪う。probe は、前のセッションの資源をその終わりと同じく解放してから（§9）
  ロックを渡す。force は認証ではなく、取り違えを防ぐだけのものである。

### 6.5 boot_id

boot_idはprobeが起動ごとに変わるように選ぶu32で、confirm（§7.1）、clock（§7.6）とopenの応答に同じ値を入れる。
生成方法はprobeが決め、hardware RNGや不揮発記憶を必須にしない。起動ごとに異なる入力を使い、起動の決まった位置でのtimerだけなど、同じ値を繰り返す決定的な生成にしない。
衝突は起こりうるため、hostはその可能性を受け入れる。0も普通の値。hostはboot_idが変わった
とき、そのセッションの資源（インターフェースの資源）と、覚えた fn の対応、資源の番号、ストリームの位置がすべて無効になったとみなす。
ロックを持たない host（監視、発見）は confirm か clock で再起動を知る。
この文書が「同じboot_idの間」と書く不変性・単調性・番号の非再利用は、1回の起動の範囲での契約である。
起動をまたいで偶然boot_idが一致しても、同じ起動や資源の継続を保証しない。

open の応答も boot_id を持つ: 知っていた boot_id と比べる host は、open のときに再起動を知り、覚えた fn の対応を使う前に list をやり直す（§7.2）。

## 7. 発見

### 7.1 confirm

```text
要求: "OEP?"、min_rev(u8)、max_rev(u8)、[TLV]
応答: "OEP!"、revision(u8)、max_frame(u16)、window(u32)、max_inflight(u8)、boot_id(u32)、[TLV]
```

- TLV 0x01 transport（u8）: この confirm が来た経路の index（§7.5）。probe は必ず付ける。同じ接続で返す fn 0 の describe の entry を指す。

host は扱えるプロトコルの revision の範囲を送り、probe はその中で扱える最大の revision を返す。範囲に扱えるものが無ければ
rejected unsupported（下）。max_frame は 64 以上（[経路](oep-transports.ja.md) §3）、window は max_frame 以上、max_inflight は 1 以上。boot_id は §6.5（ロックなしで再起動を知るための置き場）。要求も応答も 64 byte に収まる
（[経路](oep-transports.ja.md) §3）。

- confirm の要求と応答の見出し（§4.1、§4.2）と固定部分、magic の `OEP?` / `OEP!`、confirm の前の規則（64 byte、[経路](oep-transports.ja.md) §1 のフレーム、[経路](oep-transports.ja.md) §3）は、どのプロトコルの revision でも同じ。
- probe が選んだ revision は、**その confirm が来た経路**の、両方向のすべての message に、その経路の次の confirm まで掛かる。経路ごとに違う revision で動いてよい。TCP では、経路は受けた接続ごとである（[経路](oep-transports.ja.md) §1）。
- ある経路で最初の confirm をした後、host はそこでの後の confirm（立て直し、探り直し）ではすべて、`min_rev = max_rev =` 使っている revision を送る。
- 範囲の中に扱える revision が無いとき: rejected unsupported で、payload は tag 0x00 の後に TLV 0x01 supported（min(u8)、max(u8): probe が扱える範囲）。`min_rev > max_rev` は rejected malformed。

### 7.2 list

```text
要求: first(u16)
応答: total(u16)、count(u8)、count × entry
entry: fn(u16)、instance(u16)、revision(u8)、name_len(u8)、name
```

- probe のインターフェースを、first 番目から 1 フレームに入る分だけ返す。total はインターフェースの数。本体（fn 0）は名前を持たないので
  list に載らない: entry の fn は 0 でない。
- 名前は 1〜48 byte、使える文字は `a-z 0-9 - .`（§12）。項目 1 つの応答は、名前が 48 byte でも 62 byte（見出し 5、total と count 3、項目の固定部分 6、名前 48）で、どの max_frame（64 以上）にも収まる。
- instance は、同じ (名前, revision) のインターフェースを見分ける **u16 の識別子**。その組の中で重複しない。0 を使ってよく、欠番もよい。fn の順や list の位置から計算しない。
  同じ製品の firmware 更新では、同じ論理インターフェースの instance を保つ。削除したものの番号を別の論理インターフェースへ振り直さない（保存した設定がカテゴリを (name, instance) で指すため、§13.1）。
  host は保存した組を list から解決し、見つからなければ未提供として扱う。fn は同じ boot_id の間の呼び出し先で、firmware 更新後の保存識別には使わない。
  instance は接続先 target や配線の識別ではない。複数の revision を提供するときは各 revision の組を明示的に選ぶ。設定は revision によらず（name, instance）のカテゴリに属する（§13.1）。
- list の応答（どのインターフェースがあるか、その fn、instance、revision、名前）は、同じ boot_id の間変わらない。インターフェースが増えたり減ったりする probe は再起動する（新しい boot_id）。host は boot_id が同じ間、名前から fn への対応を覚えてよい。
- first が total 以上なら、応答は total と count 0。

### 7.3 describe

```text
要求: fn(u16)、first(u16)
応答: more(u8)、TLV の並び
```

fn の宣言を、first 番目の TLV から 1 フレームに入る分だけ返す。more = 1 なら続きがあり、host は first に受け取った TLV の数を
足してもう一度聞く。probe は各 TLV を、応答の見出し 5 byte と more 1 byte を足しても自分のどの経路の max_frame にも収まる大きさにする（TLV の値は、いちばん小さい max_frame − 9 byte まで。describe は経路によらない）。fn 0 は probe 全体の宣言。

**describe は宣言だけを返す**: 同じ boot_id の間、TLV の並びと値は変わらない（host は boot_id が同じ間 cache してよく、ページングは
途中で設定が変わっても崩れない）。変わるもの（接続、保存の有無、空き容量）は、インターフェースが状態を返す op
（ロック不要）で出す。
- **ページングの終わり**（firstでページを指す一覧に共通）: first が数以上なら、要素を 0 個、more 0 で
  返す（要素の数の欄を持つ応答では、その欄は 0）。host は more = 0 で止める。list は more を持たず、total で終わりが分かる（§7.2）。
  first ではなく通し番号で指す一覧（記録や区画など）の規則は、それを使うインターフェースの文書が決める。

### 7.4 describe の共通タグ（0x01〜0x3F）

| tag | 名前 | 値 |
|---:|---|---|
| 0x01 | role_channels | role(u8)、base(u16)、bitmap。bit i が立っていれば channel base+i をその role に使える。同じ role を複数書いてよい（和集合） |
| 0x02 | max_clock_hz | u32 |
| 0x03 | max_length | u16。機能が1回に扱える長さの上限（describeは経路によらない。単位はインターフェースの文書が決める）。超えた要求は rejected unsupported。要求と応答は、さらにその経路のmax_frameへ収める（§4.4）。外部から受けた結果を分割できない操作は、その操作の定義に従い全経路で結果を運べる値を宣言する |
| 0x04 | min_clock_hz | u32 |
| 0x05 | features | u32。op でない任意機能のビット: モード、format など（意味はインターフェースが決める）。任意の op は ops で宣言し、決して features では宣言しない |
| 0x06 | channel_group | group(u8)、n(u8)、n × (role(u8)、channel(u16))。group が 1 つ以上ある機能では、どれか 1 つの group に挙げられた role について、選んだ channel の組が完全に一致しなければならない。group に無い role は下の role_channels の規則に従う |
| 0x07 | ops | base(u8)、bitmap。bit i が立っていれば op base + i を持つ（§1.2）。fn 0 を含むすべての fn の describe が付ける |
| 0x08 | setting | form(u8)、key_kind(u8)、keys(u16)、max_len(u8)、flags(u8)、name（text）。その fn が持ち主の設定の項目ごとに 1 つ（§13.2） |
| 0x09 | setting_choice | number(u8)、value(u8)、name（text）。form enum の項目の選択肢ごとに 1 つ（§13.2） |

role の番号はインターフェースが定める。これらの値は固定の形で、足す情報は新しい tag にする（§2.3）。

- **ops の値**: base(u8) と、1 byte 以上の bitmap。`base + 8 × bitmap の byte 数 ≤ 256`（bitmap は op 0xFF を越えない）。
- **ops** の例: op 0x10〜0x17 をすべて持つ riscv-dm の fn は `07 02 00 10 FF` を送る。dmi、halt、resume だけ（0x10〜0x12）を持つものは `07 02 00 10 07` を送る。
  `F9 01`（op 0xFF を越える）は正しくない。host は op があるかを知るのに、features ではなく bitmap を読む。

- どのピンにも割り当てられる機能は role_channels に候補を並べ、ピンの組が決まっている機能は channel_group を組の数だけ書く。
  両方を書いた場合、選んだピンの組は channel_group のどれかに一致し、かつ role_channels の候補にも入っていなければならない。
  role_channels が縛るのは、それが挙げる role だけである（role_channels に無い role は channel_group だけで決まり、channel_group に
  無い role は role_channels だけで決まる）。
  例えばgroupがrole 1/2を固定し、role_channelsがrole 3だけを挙げる場合、role 1/2の一致とrole 3の候補を別々に確かめる。
- role_channels と channel_group は、インターフェースがピンを選ぶどのやり方（ほかのインターフェースによる割り当て、要求の引数）でも、
  選べるピンの宣言である。role の番号と、どのやり方でピンを選ぶかは、インターフェースの文書が定める。

### 7.5 probe 全体の宣言（fn 0 の describe、0x40〜）

| tag | 名前 | 値 |
|---:|---|---|
| 0x40 | firmware | text。任意の版・診断情報 |
| 0x41 | model | text。probe の種類の名前（任意。個体では変わらない） |
| 0x42 | unit_id | 個体の ID。**必須**。text で 1〜32 byte、使える文字は `a-z 0-9 -` だけ（チップの固有の番号を小文字の 16 進にしたもの、など）。同じ probe の経路を host がまとめるのに使うので、どの経路の describe でも同じ値を返す。USB の serial number と同じ（[経路](oep-transports.ja.md) §3）。host が probe を名指す値 |
| 0x43 | channels | u16。channel の数。channel の番号は 0〜channels − 1。channel を持つ probe は必ず付け、無ければ channel は 0 個 |
| 0x44 | channel_name | channel(u16)、text。channel の名前。channel ごとに 1 つ。channels を付ける probe は必ず付ける（下） |
| 0x45 | netif | text。ネットワークの口の名前（§7.7 の名前の並び）。口ごとに 1 つ。意味は[経路](oep-transports.ja.md)が定める |
| 0x49 | transport | index(u8)、kind(u8)、interface(u8): USB CDC（kind 2）は CDC の通信の interface の bInterfaceNumber（その機能の最初の interface）。内蔵の USB シリアル（kind 3）は、ハードウェアが見せるその同じ番号、probe が知れなければ 0xFF。vendor bulk と HID はその interface の番号。UART bridge（kind 1）と TCP は 0xFF。probe の経路ごとに 1 つ。**必須** |
| 0x4C | chip | text。probe の MCU の型番とリビジョン（任意） |
| 0x4D | max_op_ms | u32。probe が1つの要求自身の検証を始め、内部の再試行・実行・後始末を終えて応答を生成するまでの最長の処理時間。同じ経路・別経路の先行要求を待つ時間と経路の転送時間は含まない。**必須**。1〜600000（`max_op_ms_max`、10 分）。明示的な待ちの引数がこれを超える要求は rejected unsupported（どの op かはインターフェースの文書が定める）。所有者の新規要求の処理中だけleaseを数えない（§6.1）。値は probe が決める。host は §4.4 のとおり待つ |

- transport の kind: 1 UART bridge、2 USB CDC、3 内蔵の USB シリアル（MCU のハードウェアが持つ USB のシリアルの口で、serial number を含む USB の記述子を probe が選べないもの）、4 vendor bulk、5 HID、6 TCP（registry の `transport_kind`）。
  1〜3 がシリアルの口（[経路](oep-transports.ja.md) §4）。index は probe の中で経路を指す番号（0 から）で、設定がシリアルの口を指すときも wire ではこの番号を
  使う。番号は同じ boot_id の間だけ変わらない。保存と書き出しでは経路の名前（§13.3）で指す。
- **channel の名前**: チップのデータシートがそのピンに使う名前（ESP32 の `GPIO14`、CH32 の `PA5` など）。`A-Z a-z 0-9 _ -` の 1〜16 byte で、
  probe の中で重ねない。番号は同じ boot_id の間だけのもので、保存と書き出しでは名前で指す（§13.3）。ピンの呼び名（`NRST` など）は名前ではなく、
  設定の `channel.{}.label`（§13.8）である。
- **unit_id の一意性**: unit_id は個体ごとに違う値にする（チップの固有の番号、など）。`any` は使わない（host のアドレスで「どれでも」を表す、[hostガイド](host-development-guide.ja.md) §5.3）。保存はあるが固有の番号の無い probe は、最初の起動で乱数から unit_id を作って保存する。
  どちらも無い probe は `x-` で始まる unit_id を使う（一意ではない）。host は `x-` で始まる unit_id で経路をまとめず、それで probe を名指さず、セッションを越えて持つもの（たとえば口のリンクの速さの記録）のキーにしない。同じ口のほかの個体が何も引き継がないためである。
- **unit_id の不変性**: unit_id は個体の値（チップの固有の番号、保存した乱数。`x-` の unit_id だけは例外）だけから作り、firmware の版、profile、ビルド、経路の種類で
  変えない。接尾辞を足さない。host と OS は unit_id（= USB の serial number、[経路](oep-transports.ja.md) §3）で probe を覚える。

### 7.6 clock

```text
要求: —
応答: boot_id(u32)、uptime_ns(u64)、[TLV]
```

- clock は probe の今の時刻を返す。boot_id は §6.5 の値（confirm と open の応答と同じ）、uptime_ns は §2.7 の時計の値。
- clock はロックの要らない読むだけの op（§6.3）である。セッションが無くても送れる: session_id 0 の clock は、セッションの確かめなしに処理し、
  どのセッション、ロック、lease にも触れない（§4.1）。
- uptime_ns は、probe がこの clock の要求を受けてから応答を送るまでの間に読んだ、自分の時計の値である（前に読んだ値や推定した値は入れない）。

### 7.7 名前の並び

probe が持つ選択肢を host が要求で選ぶもので、標準のほかにほかの者が足しうるもの（コンソールの方式、ネットワークの口など）は、
番号を registry で振らず、名前で宣言する（fn と list の関係と同じ形）。

- インターフェースは、describe に名前を持つ TLV を 1 つずつ繰り返して並べる。要求と応答では、その並びの位置（1 から）を番号として使う。0 は番号に使わない（「無い」を表し、unsupported の payload の印 0x00 と重ならない）。
- 標準の名前は registry が持つ（`a-z 0-9 -`、`.` を含まない）。ほかの者の名前は §12 規則 1 の逆 DNS の名前（`.` を含む）。
  同じ名前は、どの probe でも同じ意味と同じ値の形を表す。1 つの並びに同じ名前を 2 回置かない。
- 番号は同じ boot_id の間変わらない。host は名前から番号を引き、boot_id が変わったら引き直す。番号を名前の代わりに覚えない。
- 並びに無い番号は、その要求の定義に従って断る（ふつうは unsupported）。

## 8. channel の空きの状態

channel（probe のピン、§1）は、インターフェースがそれを取っていないとき、**空きの状態**にある。ピンを取るのは、インターフェースの文書が
定める操作（ピンの割り当て、線の接続、設定など）である。

- **空きの状態**: 設定の `channel.{}.idle`（§13.8）がそのピンの空きの状態を決めていればその状態（出力 low / high ならその level を
  設定の定義に従って駆動し、Hi-Z にしない）、決めていなければ **Hi-Z（入力、プルなし）**。
- 解いたピンは、どの道で解いても（インターフェースが定める解く操作、§9 の lease の期限切れと force での後始末）、空きの状態にする。
  インターフェースは、解いた後もピンを自分の駆動のまま残してはならない（空きの状態が出力なら、その駆動は設定の idle のもの）。
  例外は、インターフェースの定義が解いた後の**保持**を定めた場合だけである（debug の線、[線とデバッグ](../interfaces/oep-if-debug.ja.md) §2）。
  保持は空きの状態の一種で、設定の idle の無いピンを、そのインターフェースが休みの状態で駆動したまま残す。取得は空きのピンと同じに
  扱い（保持を理由に断らない）、取ったものが引き継ぐ。保持を定める定義は、それを設定で OFF にでき、保持中であることを読めるようにする。
- **起動時**、probe は最初の要求に答える前に、自分で使う channel と、設定の `channel.{}.disable`（§13.8）が真の channel を除くすべての channel を空きの状態にする。それまでピンは MCU のリセットの
  状態である（参考: 誤った水準が害になる線には外付けのプルが要る）。
- **ピンを取ってもピンの電気の状態は変わらない。** ピンは、それを取ったインターフェースが使い始めるまで空きの状態を保つ。どの操作で使い始めるかは、
  各インターフェースの文書が定める。ピンを読むだけのインターフェースは決して変えない: 出力を止めず、ほかの機能や出力の idle が駆動するピンのプルや
  向きも変えない。
- idle が出力の channel を取る要求は、そのインターフェースが取得を明記している場合を除き、unavailable（cause 5）で断る。
  取得を認めるインターフェースも、取得時には空きの状態を保つ。読むだけの取得では駆動を変えない。

### 8.1 資源の取り合い

- probe の資源（ピン、ペリフェラル、DMA、タイマーなど）を取るものはすべて、取る前に、今あるピンの割り当て、実行時の資源、設定の使用制限、上の規則で取得を認めない出力のidle とぶつからないか確かめる。ぶつかれば rejected unavailable で断り、**今ある機能の状態は何も変えない**。
  取るもの: インターフェースが定める、ピンや資源を取る操作（ピンの割り当て、線の接続、設定、資源を作る操作）。
- configure / attach / start などで資源の使用量を増やす場合も、既存の機能と新しい機能の宣言・受理済みの時間条件を同時に守れるか確かめる。
  同時使用の資源・処理能力が足りなければ、副作用前に unavailable（cause 2）で断る。すべての fn を同時に動かす能力は要求しない。
  ピンの取り合いは cause 1、設定による禁止は cause 5、操作できない状態は cause 6 のままである。

## 9. 資源の寿命（一般の規則）

**実行時の資源はすべて、作ったセッションの所有物である。** end、lease の期限切れ、force でロックを失ったとき、
そのセッションの資源と購読をすべて解放する。依存する資源を先に解放し、最後にピンを空きの状態へ戻す。
新しいセッションへ資源を引き継がない。永続設定は実行時の資源を所有しない。
セッションと独立して効く設定の有無と作用は、その項目の持ち主が定める（§13）。

| 出来事 | 実行時の資源 | 購読 | 再送状態 |
|---|---|---|---|
| end / lease の期限切れ | すべて解放 | 終了 | 最後のセッションの順序状態と、保持中のbyte記録を残す（§5.1） |
| 別の ID の force open | 前の資源をすべて解放 | 終了 | 新規 open の成功時に置き換える |
| 同じ ID の新しい open（保持中） | 残す | 残す | 残す |
| 同一 open の再送 | 変えない | 変えない | 保持した応答を返す。保持していなければ result_lost |
| 再起動 | 無効（boot_id が変わる） | 無効 | 無効 |

- 資源の番号は u32、probe 全体で 1 つの空間。0 は割り当てず、1 から増やす。
  **同じ boot_id の間は、閉じた番号も再利用しない。** 0xFFFFFFFF を使い切ったら、新しい資源の作成を rejected unavailable（cause 2）で断る。
  既存の資源はそのまま使える。番号を再び 1 に戻すには再起動して boot_id を変える。
  古い番号が別の資源を指さないことを、セッションなしの読み取りにも保証する。閉じた番号の履歴表は不要で、次の番号と使用中の資源だけを保持すればよい。
- 閉じた資源の番号、存在しない番号は rejected no_resource。その操作が使うと定めていない種類・作成元の資源は rejected unavailable（cause 6）。
  定義が別fnの作った資源を使うと明記する場合は、その対応に従う（作成元と利用先が別fnの接続など）。別fnというだけでは断らず、対応しない資源を暗黙に共有しない。
- 作成に失敗した要求は使用可能な番号や資源を返さない。予約だけで失敗した番号を欠番にしてよい。
- 接続先は常に要求の fn と資源の番号で指定する。「現在の target」や最後に attach した target を暗黙に使わない。
  1 つのセッションで複数の connection と fixture を使ってよい。依存する接続とピンの組は、各インターフェースの要求で明示する。

## 10. 通知

probe から送る通知の仕組み。通知を送り出すかはインターフェースが決める: 送り出すインターフェースは、その fn の ops に subscribe と
unsubscribe（§10.3）を立てる。何が届くか（出来事の kind、データの意味）はそのインターフェースの文書が決める。host は購読しなければ
何も受け取らない。§10.1 はすべての host に、§10.3 と §10.4 は通知を送り出すインターフェースを持つ probe に掛かる。

### 10.1 host の義務（全 host）

- 受け取ったフレームを role で振り分ける。corr で照合するのは role 0x02 だけ（0x03 / 0x04 のバイト 1〜2 は fn）。
- 知らない role のフレームと、待っていない corr の応答は捨てる。
- 通知が届き続けても、応答を待つ処理と受信を読む処理が締め切りどおりに終わるようにする。

### 10.2 形

```text
データ   role=0x04 | fn(u16) | seq(u16) | position(u64) | len(u16) | data | [TLV]      見出し 5 byte
出来事   role=0x03 | fn(u16) | seq(u16) | kind(u8) | 固定部分 | [TLV]                   見出し 6 byte
```

- データの payload の形は全インターフェース共通: `position` はこのフレームの先頭のストリームの位置（インターフェースが決める）、
  `len` は data の長さ、後ろは TLV（§2.3）。出来事の固定部分は kind ごとにインターフェースが決め、後ろは TLV。

- `seq` は fn ごとのフレームの通し番号（u16、一周する。データと出来事で共通）。subscribe のたびに 0 から数える。抜けがあれば
  フレームが失われた。probe は、生まれた出来事すべてに番号を振り、probe の中で捨てたものも番号を消費する。
- fn 0 は通知を送らない。

### 10.3 購読

subscribe と unsubscribe は、通知を送り出すインターフェース自身の op である。**op の番号はどのインターフェースでも同じで、すべての
インターフェースの op の空間で予約する**: 0x01 subscribe、0x02 unsubscribe。インターフェースはこの 2 つの番号をほかの op に使わない。
要求は購読する相手の fn を持たない（その fn 自身への要求で、見出しの fn が相手である）。

| op | 名前 | 要求 | 応答 | ロック |
|---:|---|---|---|---|
| 0x01 | subscribe | min_bytes(u16)、max_delay_ms(u32)、[TLV] | — | 必要 |
| 0x02 | unsubscribe | [TLV] | — | 必要 |

- 通知を提供する場合は、subscribe と unsubscribe を両方とも持ち、ops に立てる。通知機能そのものが必須か任意かは、そのインターフェースの文書が決める。
  （参考）中継のブローカーは、どの fn への要求でも、この番号で購読を見分けて断れる。
- **購読はロックの持ち主だけができ、ロックと一緒に終わる**（end、期限切れ、force で奪われたとき）。読むだけの監視は、ロック不要の read を使う。
- 購読の無い fn の unsubscribe は何もせず成功。
- 同じ fn をもう一度 subscribe したら、前の購読を原子的に置き換える（送る条件、送り先の経路、seq を 0 から）。1 つの fn の購読は
  1 つだけ。
  置き換えや解除では旧購読の未送信通知を捨てる。既に送り始めたフレームは、同じ経路へ返す操作の応答より先に完了する（§10.4）。
  別の経路への応答は旧経路のフレーム完了を待たない。閉じた経路の送信残りは捨て、新しい経路へ持ち越さない（[経路](oep-transports.ja.md) §3）。
- probe は購読用の保持量に上限を置いてよい。要求したデータの送信条件を満たすための保持量が足りない場合は、何も変えずに rejected unavailable（cause 2）で断る。
  成功した購読の条件を黙って丸めない。既存の購読を置き換える要求を断った場合も、以前の条件、送り先、seq を保つ。
- **まとめて送る条件はデータ（role 0x04）だけに掛かる**: min_bytes バイトたまるか、最初のバイトから max_delay_ms 経ったら送る。0 は
  その条件を使わない。両方 0 ならあるだけすぐ送る: 送り出せるようになった時点で、あるだけ送る。前の送信で経路が塞がっているあいだに
  溜まった分は、まとめて 1 つのフレームにしてよい（遅れて届くことにはならない。まとめた結果も max_frame を超えない）。
  条件が成立した時点の未送信データは、max_frameに収めて複数のframeへ分けてよく、その残りにmin_bytesを再適用しない。
  min_bytesは1frameの最低データ長ではない。送信開始は§10.4の応答優先に従い、max_delay_msはその優先順を上書きしない。
- **出来事（role 0x03）はまとめない**: 生まれた出来事は、その前に送る応答（§10.4 の 1）を送り終えたらすぐ送る。min_bytes と max_delay_ms は
  出来事に掛からず、出来事の byte は min_bytes に数えない。

### 10.4 probe の義務（送り出す probe）

1. **応答を先に送る。** 届いている要求をすべて処理してから、新しい通知フレームを送り始める。
   同じ経路で既に送り始めたフレームには別の応答や通知を挟まず、そのフレームを完了してから次の応答を送る（[経路](oep-transports.ja.md) §2）。
2. **送りかけの通知を小さく保つ。** 経路の送信バッファに、送りかけの通知を max_frame × 2 byte を超えて
   ためず、書き込みで待たない。この値は上限であり、その量のqueueを確保する義務ではない。入らない通知は送り始める前に probe の中で捨てる（seq の抜けで分かる、§10.2）。
3. 通知は、その fn の subscribe が来た経路に送る。

## 12. 拡張の規則（インターフェースの書き方）

どのインターフェースも、次の規則で定義する。

これは標準 OEP と独自拡張のすべてに適用する共通契約である。
OEP の[共通部品](../interfaces/oep-if-common.ja.md)は、採用したときだけ追加で適用する。採用しない stream、connection、通知、ピンや plan を実装する義務はない。
最小の拡張は、名前/revisionと、1つの固有操作か1つの設定の項目（§13）だけでよい。list と fn 0 の describe/ops で発見でき、下の固定形・失敗・ロック・版の規則に従う。
ピンを使う拡張は、fnごとの割り当て（planなど）か、資源を作る要求の引数かを自分の定義で選び、取得・解放を明記する。
独自拡張へOEPのplan方式を一律に要求しない。

1. **名前**: インターフェースの名前は、定義する者の逆 DNS の名前（`io.github.<owner>.<name>` など）である。OEP を伸ばす者は誰でもこれを使う。
   例外は project 自身のインターフェースだけで、逆 DNS の名前の代わりに、予約した短い接頭辞 `oep.` を使う: `oep.<層>.<名前>`、層は `probe`（probe 自身）、
   `wire`（線と connection）、`target`（connection の上の target の操作）、`fixture`（治具の機能）。この短い名前のほかに、それらに特別なものは無い。
   `oep.` で始まる名前は project だけが付ける。名前は host が何に使うかで切る（probe のペリフェラルの名前にしない）。汎用か 1 つの系統のためのものかは
   名前に入れない（規則 8）。**1〜48 byte、使える文字は `a-z 0-9 - .`**（registry の `limits`。list の項目が 1 フレームに収まる長さ、§7.2）。
   名前の label はそれぞれ `a-z 0-9 -` の 1 文字以上で、`-` で始まらず `-` で終わらない。名前は label を 2 つ以上持つ。
2. **定義が決めるもの**: インターフェースの文書はどれも、次のチェックリストを埋める。
   - 名前と revision。
   - op の表: 番号、要求、応答、ロックの要否、どの op が必須でどれが任意か（任意の op は ops で宣言する、§1.2）。
   - 各 op の要求と応答の TLV（その op の文脈の tag の空間）。
   - 各 op の completed success、completed failed、completed partial の payload（§4.2）。
   - インターフェース自身のstatus、reject reason、unavailableのcause（各0x40〜0x7F）。
   - describe のインターフェース固有のタグ（0x40〜0x7E）と、ピンの role の番号。
     必須宣言が全経路へ収まる条件と、要求/固定結果が要求経路のframeへ収まる条件（§4.4/§7.3）。
     describeのページングはTLVの値を分割しない。外部受信の非分割結果は個別定義に従う。
   - どの target の系統のためのものか（規則 8。どの系統にも使うものはそう書く）。
   - インターフェースが作る資源とその寿命（§9 の上で）。
   - 通知を送り出すか。送り出すなら subscribe / unsubscribe（§10.3）を宣言して実装し、出来事の kind（0x01〜0x7F）とその payload、
     通知のデータの payload の形。
     データ生成が終了する機能では、送信条件未満の残りをどう扱うかと、欠落を含む終了判定も定める。
   - 読む側が、応答の enum の知らない値と知らない flags をどう扱うか（§2.4、§12.1）。
   - 設定の項目を持つなら、その名前、form、key、flags、固定と既定の値、意味の検証、効く時（§13）。
   - 頼る外部の仕様と、その版と、使う部分（「参照する仕様」の節）。
3. **形の規則**: §2.3 のとおり（固定の形、足すものは TLV だけ、可変の並びの前に数を置き要素に長さを置かない、省略できるフィールドを置かない、安全の引数は critical）。
4. **失敗**: 受け付けなかったものは rejected、受け付けて失敗したものは completed failed / partial（§4.2）。
5. **ロックなしの op は状態を変えない**（§6.3）。
6. **版**: §2.8。
7. **ほかの者の名前のインターフェースに、番号（op、tag、enum の値）を足さない。** 番号を振るのはその名前を持つ者だけである（`oep.` の名前なら project、§2.5）。
   ほかの者が足せるのは、名前で識別する所だけ:
   - 名前つきの拡張 TLV（§2.2、tag 0x7F）: 要求、応答、出来事、データ、describe に、自分の名前で情報を足す（例: 標準の出力に probe の固有の強さを足す）。
   - 名前の並び（§7.7）: インターフェースが名前で宣言する選択肢に、自分の名前の選択肢を足す（例: コンソールの独自の方式）。
   設定の項目は名前で識別するが、ほかの者の名前のカテゴリには足さない（§13.1）。自分の設定は自分の名前のインターフェースに置く。
   - 自分の名前のインターフェース: 新しい機能（別の fn として出す）。
   どれも、その名前を知らない host には読み飛ばされるか（非 critical）、断られる（critical）だけで、標準の動作を変えない。
   標準の動作を変える必要があるものは、ここではなく、その名前の持ち主が定義を伸ばす。
8. **特定のチップ向けの手順は、汎用のインターフェースに入れない。** チップや系統に特化した手順（flash の書き方、リセットのタイミングなど。
   probe がやらないとタイミングが間に合わないもの）は、そのための別のインターフェースに置く。
   どの系統のためのものかは名前に入れず、インターフェースの文書の冒頭と、名前が `oep.` で始まるものでは registry（インターフェースの `target`）に書く
   （名前は永続する識別子で、どれだけ広く使われるかは時とともに変わるため）。**どの系統にも使うインターフェースには、特定のチップ向けの処理を
   入れない。** 特化したものは移植性が下がる（それを使う host はその機能を持つ probe に縛られ、新しいチップへの対応に probe の firmware の
   更新が要る）。汎用の手順（生の転送と host の知識）で済むものは、そちらで組む。
   **判定は host が持つのが基本である。** ただし host から接続先を確かめて直すのでは間に合わないもの（タイミングに関わるものなど）は、
   その系統のための定義の中に probe の自動の判定を置ける。自動の判定を置く定義は、(a) 何を選んだかを応答や一覧で host に返し（自動の判定を
   したことが分かるように）、(b) host の明示の指定を優先し、(c) probe の設定でその判定を OFF にできるようにし、(d) 判定に使う target の表を
   registry に置く（例: debug §3.1 の rvswd の線の休ませ方）。

### 12.1 伸び方

凍結の後、OEP はこれらだけで伸ばす:

1. **新しい TLV**: 要求、応答、出来事、データ、describe の中に。名前の並び（§7.7）の新しい標準の名前。
2. **新しい任意の op**（ops で宣言する、§1.2）か**新しい出来事の kind**。
3. **予約の空間の新しい値**: 古い probe が unsupported で断る要求の値（§2.5）、または下の条件のもとでの
   応答の値。
4. 新しい意味には**新しいインターフェースの名前**、変わった固定の形には**新しい revision**（§2.8）。

本体は、共通操作専用の範囲（§2.5）へ新しい任意の共通操作を定義でき、新しい経路の種類とそのフレームも定義できる（§3）。
既存の契約や本体の形を変える場合はプロトコルのrevisionを上げる（§2.8）。旧revisionも提供する場合はその契約を保つ（§7.1）。

並びの要素へ情報を足す場合は、繰り返せる応答TLVに要素のindexを持たせる。

**値の幅**: 定義する値の範囲、単位、予約値が収まる幅を選ぶ。ハードウェアに由来する値でも、上限を定義できれば u8 / u16 を使ってよい。
狭い幅へ切り捨てたり、上限を超えた値を一周させたりしない。単位と範囲はインターフェースの文書に明記する。
例: ページの要素数はu8で表し、UARTのbaudはu32で表す。対応しない範囲の断り方はそのopの定義に従う。
すでに定義した固定部分の幅や単位を変える場合は新しいrevisionにする。広い範囲が必要なら、初めから広い幅を選ぶか、後で新しいTLV/操作を追加する。
ビットの集合は、既存の定義が選ぶ幅か `base + bitmap` を使い、新しい定義は必要なbit数と拡張方法を決める。

**応答に足す値。** 応答、出来事、データが運ぶ enum の値やビットの集合のビットは、次の 3 つがすべて成り立つときだけ、revision を変えずに足してよい:

1. どのフィールドの有無、長さ、位置も、その値によらない。
2. §2.4 の扱いが安全である（知らない outcome、status、reason は失敗、ほかは「知らない値」、予約のビットは無視）。
3. 意味がその値によるフィールドはどれも、その値を知らない読む側が無視するか、生のまま見せると定めてある。

そうでなければ、足すものは新しい TLV、新しい revision、新しいインターフェースにする。revision 1 の応答の enum とビットの集合は、どれも 3 つの条件を満たす。

## 13. 設定（任意）

設定は、probe が起動を越えて保つ値である（ピンの呼び名と空きの状態、ネットワークのつなぎ先、インターフェースの休ませ方など）。
本体が一括して取りまとめ、保存する。項目を決め、値の意味を確かめて使うのは、その項目の持ち主である。
設定の仕組みも保存も任意である。設定の仕組みを持たない probe は、すべての channel を Hi-Z の空きの状態で扱う（§8）。

実行時の状態（plan、接続、UART の configure など）は設定ではない。それらはインターフェースの op で明示し、設定に置かない。

### 13.1 カテゴリと項目

- **カテゴリ**: 設定は持ち主ごとのカテゴリに分かれる。カテゴリは本体（fn 0、名前なし）か、インターフェース（名前と instance、§7.2）の
  2 種類だけである。probe の作り手の設定（ホスト名など）は、その作り手の名前のインターフェースに置く（設定だけのインターフェースでよい、§12）。
  同じ（名前、instance）を複数の revision で出す probe では、そのうち 1 つの fn だけが項目を宣言する（カテゴリは revision によらない）。
- **項目**: 持ち主は自分のカテゴリにだけ項目を定め、名前を付ける。ほかの者は他人のカテゴリに項目を足さない。
  項目の持ち主はカテゴリで決まるので、項目の名前に「標準か、ほかの者か」の区別は無い。
- **項目の名前**: `a-z 0-9 -` の label を `.` でつないだもの（label は §12 規則 1 と同じ形）。key を持つ項目は、key の入る所に label の代わりに
  `{}` を 1 つだけ置く（`channel.{}.label`）。1〜48 byte。
- **値**: 値は（カテゴリ、項目、key）ごとに 0 か 1 つ。1 つの値は 1 つの形（§13.3）を持つ。組の値（アドレスとプレフィックスなど）は、欄ごとに別の項目にする。
- **名前の意味は変えない**: 同じカテゴリの同じ名前の項目は、firmware の版とインターフェースの revision を越えて同じ意味、同じ形、同じ key の使い方を表す。
  意味を変えるときは新しい名前の項目にする。保存と書き出しは項目を名前で持つ（§13.7、[設定のファイル](oep-settings-file.ja.md)）。
- **持ち主が決めるもの**: 項目の名前、形、key の種類と範囲、flags、固定と既定の値（§13.4）、値の意味の検証（定義が除く値は malformed、probe が扱えない値は unsupported、§4.3）、値が効く時、変更の可否（§13.6）。
  **本体が決めるもの**: 形の検証（§13.3）、読み書きの操作（§13.5）、世代、保存（§13.7）。
- 持ち主は値をメモリに持って使う。持ち主は §13.5 の操作によらずに値を変えない。値を使うのは設定の読み書きではなく、§13.6 の可否を通らない。

### 13.2 宣言

項目は、持ち主の fn の describe に並べる（本体の項目は fn 0 の describe）。describe は何があるかだけを示し、値は §13.5 の get で読む。

| tag | 名前 | 値 |
|---:|---|---|
| 0x08 | setting（共通） | form(u8)、key_kind(u8)、keys(u16)、max_len(u8)、flags(u8)、name（text）。項目ごとに 1 つ。k 番目の setting を項目番号 k（1 から）とする |
| 0x09 | setting_choice（共通） | number(u8)、value(u8)、name（text）。form enum の項目の選択肢ごとに 1 つ |

- 1 つの fn に同じ名前の setting を 2 回置かない。項目番号は同じ boot_id の間変わらない。host は名前から番号を引き、boot_id が変わったら引き直す。
- form、key_kind は §13.3。keys は key_kind index の key の数（1 以上）で、ほかの key_kind では 0。max_len は form bytes と text の最大の長さで、
  ほかの form では 0。flags: bit 0 **secret**（§13.5）、bit 1 **restart**（新しい値は再起動の後に効く。get は新しい値を返す）。ほかの bit は 0。
  restart の無い項目の値が効く時は、項目の定義が決める。
- max_len は、その項目の値 1 つの get の応答と set の要求が、probe のどの経路の max_frame にも収まる値にする（いちばん小さい max_frame − 19 以下。§13.5）。
- setting の値は 6 + 名前の長さで、名前が 48 byte でも 54 byte となり、64 byte の max_frame の describe に収まる（§7.3）。
- setting_choice: number はその fn の項目番号、value はその選択肢の wire の値、name は `a-z 0-9 -` の 1〜16 byte。同じ項目の中で value も name も重ねない。
  setting_choice の無い value は、その項目では使えない（unsupported）。

### 13.3 形と key

| form | 名前 | wire の data | 書き出し（JSON） |
|---:|---|---|---|
| 1 | bytes | 0〜max_len byte | 小文字の 16 進の文字列 |
| 2 | text | §2.1 の text、1〜max_len byte | 文字列 |
| 3 | u32 | u32 | 数 |
| 4 | ipv4 | 4 byte、`a.b.c.d` を a から | `"a.b.c.d"` |
| 5 | bool | u8（0 か 1） | 真偽 |
| 6 | enum | u8。setting_choice の value のどれか | 選択肢の name |
| 7 | channel | u16。channel の番号 | channel の名前（§7.5） |
| 8 | transport | u8。経路の index | 経路の名前（下） |
| 9 | fn | u16。list に載る fn | `"名前/instance"` |

| key_kind | 名前 | wire の key（u16） | 書き出しの名前 |
|---:|---|---|---|
| 0 | none | 0 | — （名前に `{}` を置かない） |
| 1 | channel | channel の番号 | channel の名前 |
| 2 | index | 0〜keys − 1 | 10 進の数（`0`、`1`） |
| 3 | transport | 経路の index | 経路の名前 |
| 4 | netif | fn 0 の describe の netif の並びの位置（1 から、§7.7） | netif の名前 |

- **wire は起動の間だけの番号、保存と書き出しは名前**: channel、経路、fn、netif、選択肢は、wire では番号で運び、保存（§13.7）と書き出しでは名前で持つ。
  本体が両者を引き換える。起動時に名前から今の番号へ引けない値は使わない。
- **経路の名前**: kind の短い名前（1 `bridge`、2 `cdc`、3 `usj`、4 `bulk`、5 `hid`、6 `tcp`）と、同じ kind の経路の中での index の小さい順の位置
  （0 から）をつないだもの（`cdc0`、`bridge1`）。
- **形の検証**: data の長さが form と合わなければ malformed。bool の 2 以上も malformed。text は長さだけを確かめる（中身は確かめない。host が見せるときに §2.1 のとおり置き換える）。
  enum の setting_choice に無い値、channels 以上の channel、無い経路、list に無い fn は unsupported。key が key_kind の範囲に無ければ unsupported。
  範囲の中でも、持ち主がその key に項目を置かない（その channel では使えない、など）なら unsupported。

### 13.4 出どころ

値は出どころを持ち、get が値と一緒に返す。

| 値 | 出どころ | 意味 | set | unset | 書き出し |
|---:|---|---|---|---|---|
| 1 | fixed | firmware が決めた値。変えられない（ピンが固定の probe のピンの呼び名など） | unsupported | unsupported | しない |
| 2 | default | firmware が用意した初めの値 | 利用者の値になる | 値はそのまま（何もしない） | しない |
| 3 | user | 利用者が set した値 | 置き換える | default があれば default に、無ければ値の無い状態に戻る | する |

- 持ち主は、項目を宣言するときに、key ごとに fixed か default の値を持たせてよい。fixed の key には user の値を置かない。
- 保存の無い間と unset の後は default が効く。default も無ければ値は無く、項目の定義が「値の無いとき」を決める。

### 13.5 操作

設定の操作は fn 0 の任意の op である（§11）。

| op | 名前 | 要求 | 応答 | ロック | 要否 |
|---:|---|---|---|---|---|
| 0x20 | get | first(u16)、[TLV] | more(u8)、generation(u32)、count(u8)、count × 値、[TLV] | 不要 | 設定を持つなら必須 |
| 0x21 | set | count(u8)、count × 書く値、[TLV] | generation(u32)、[TLV] | 必要 | 設定を持つなら必須 |
| 0x22 | unset | count(u8)、count × (fn(u16)、number(u8)、key(u16))、[TLV] | generation(u32)、[TLV] | 必要 | 設定を持つなら必須 |
| 0x23 | save | [TLV] | generation(u32)、[TLV] | 必要 | 任意（state と組） |
| 0x24 | state | [TLV] | storage_state(u8)、saved_generation(u32)、reason(u8)、[TLV] | 不要 | save があれば必須 |

```text
値:     fn(u16)、number(u8)、key(u16)、origin(u8)、len(u16)、data（len byte）
書く値: fn(u16)、number(u8)、key(u16)、len(u16)、data（len byte）
```

- fn は項目の持ち主の fn（本体は 0）、number はその fn の項目番号（§13.2）。list に無い fn は unknown_function。number 0 は malformed。
  その fn の setting に無い番号は unsupported。
- **get** は、値を持つ（fixed、default、user の）すべての（fn、number、key）を、fn、number、key の小さい順に並べ、first 番目から 1 フレームに入る分だけ返す。
  値を分割しない。first が数以上なら more 0、count 0。more 1 なら host は受け取った count を first に足して続ける。
  同じ generation のページは同じ内容を表す。途中で generation が変われば host は初めから読む。
- **set** は（fn、number、key）ごとに値を置き換え、送らない値は保つ。**unset** は指定した値を §13.4 のとおり戻す。値の無い所の unset は何もしない。
  1 つの要求の中の同じ（fn、number、key）の重なりは malformed。count 0 は何もしない。
- **まとめて受けるか、何もしない**: probe は、set と unset の要求の全部の値について、形（§13.3）、出どころ（§13.4）、可否（§13.6）、持ち主の意味の検証、
  変更の後の設定全体の矛盾、保持できる量、実行中の資源とのぶつかりを、何も変える前に確かめる。1 つでも通らなければ、設定、generation、ピン、
  実行中の資源を何も変えずに断る。通れば全部を持ち主に渡し、generation を 1 進める。断りの payload の TLV の item（u8、要求の中の値の位置。0 から）で、
  どの値かを示してよい。保持できない変更は unavailable（cause 2、または 3）で断る。
- **generation** は内容の digest ではなく、同じ boot の中の変更の数である。起動時は 1（保存を読んでも 1）。内容が実際に変わる set と unset ごとに
  1 進める。0 は使わない。0xFFFFFFFF での変更は unavailable（cause 2）で断り、再起動まで戻さない。内容を変えない set と unset は、generation を変えず、
  ピンも設定し直さずに成功する。host は等しいかどうかだけを比べる。
- **secret**: flags の secret の値は書くだけである。get はその値の data を返さない（len 0）。値があるかは、その値が get に並ぶことで分かる。
  set の len 0 は、その値を今のまま保つ（値が無ければ malformed）。だから get の値をそのまま set に送り返しても何も変わらない。secret の項目の値は
  0 byte にできない（無くすには unset）。probe は secret の値を、どの応答、出来事、ログにも出さず、どの権限でも読ませない。host も secret の値を表示せず、
  ログに書かない。OEP は値を暗号化しないので、secret の値は信頼できる経路（USB など、[経路](oep-transports.ja.md) §1）で送る。
- **フレームの大きさ**: 値 1 つの get の応答は 19 + len byte（見出し 5、more 1、generation 4、count 1、値の固定部分 8）、set の要求は 18 + len byte
  （見出し 10、count 1、書く値の固定部分 7）。§13.2 の max_len の規則で、どの値も 1 つの要求と 1 つの応答で運べる。
- 要求の末尾の [TLV] は §2.3 のとおりで、値の data には掛からない。

### 13.6 変更の可否

- 本体は、set と unset のそれぞれの値について、その持ち主に変更の可否を問う。持ち主は要求の状況（経路など）を見て断ってよい。
  断るときは rejected unavailable に cause 7 を付ける（§4.3）。本体の項目の可否は probe が決める。
- 本体は認証を定めない（§0）。設定の可否も §4.3 の任意の方針判定と同じく、経路または拡張が定める方針に従う。方針を持たない probe は、ロックを持つ
  セッションのどの変更も受ける。
- get と state は §4.3 の方針判定のほかでは断らない。secret（§13.5）はどの方針でも読ませない。

### 13.7 保存と起動

保存を持つ probe は save と state を ops に立てる。保存の内部の形式、CRC、置き場所は probe が選ぶ。ただし次の性質を持つ。

- **名前で持つ**: 保存は値を、カテゴリ（本体か、インターフェースの名前と instance）、項目の名前、key の名前（§13.3）、値（参照は名前）で持つ。
  起動の間だけの番号を保存しない。firmware の版が変わっても読める形にする。
- **save** は明示の操作で、今の user の値をすべて書く（fixed と default は書かない）。同じ内容が保存済みなら書き直さない。保存済みかの判定を
  generation だけに頼らない。save は成功しても失敗しても、今の設定、generation、ピンを変えない。保存の全部の処理を max_op_ms（§7.5）の中で終える。
  保存の量に入らない save は、何も変える前に unavailable（cause 3）で断る。
- **電源断**: 書き込みのどの時点で電源が落ちても、更新の前の完全な保存か、新しい完全な保存のどちらかが残る（保存が無かったなら、無いままか新しい完全な保存）。
  途中まで書いたものを完全な保存として扱わない。
- **起動**: 持ち主が項目を宣言した後、本体は保存を読み、宣言された項目に当てはまる値だけを、名前を今の番号へ引いて、持ち主の検証を通して使う。
  宣言されていない項目、引けない名前、検証を通らない値は使わない（ほかの値は値ごとに使う）。使わなかった値は次の save で消える
  （save は今の user の値だけを書くため）。消してよいのは、host が設定を書き出して入れ直せるからである（[設定のファイル](oep-settings-file.ja.md)）。
- **起動の順**: 本体の channel の項目（§13.8）を、どのインターフェースの値より先に、disable、idle の順に効かせ、それから §8 の空きの状態を作る。
  保持できる量が保存より小さいときは、disable、idle、そのほかの本体の項目、インターフェースの項目の順に、同じ項目の中では key の順に使えるだけ使う。
  不正な値を別の channel や別の値に読み替えない。
- **消す**: 保存を消す op は無い。host は全部の user の値を unset して save する（save は今の値だけを書くので、使わなかった古い値もここで消える）。
  物理的な手段（ボタン、firmware の書き直し）での初期化は OEP の外である。
- 保存を持たない probe も、get、set、unset をメモリの上で持ってよい。値は再起動で消える。host は書き出したファイルから入れ直す。

**state** の答え:

| フィールド | 意味 |
|---|---|
| storage_state | 0 保存が無い、1 保存をすべて使えた、または save した、2 保存を読めない（形や完全性を確かめられない。何も使わない）、3 保存の一部だけを使えた |
| saved_generation | storage_state 1 なら、保存と同じ内容だった generation（起動時は 1、save の成功で今の generation）。ほかは 0 |
| reason | 0 なし、1 保存の形か完全性、2 使えない値（宣言の無い項目、引けない名前、検証を通らない値）、3 保持できる量の不足 |

- save が成功したら（内容が同じで書き直さなかったときも）storage_state 1、saved_generation は今の generation、reason 0。その後の set と unset で内容が変わっても
  saved_generation は変えない。
- 受けた save で書き込みか検証を終えられなければ completed failed（partial は返さない）。応答の固定部分は成功でも失敗でも同じ。state は、失敗の後に
  確かめられた保存の様子を示す: 更新の前の保存がそのまま残れば操作の前の値、保存が無いと確かめられれば 0、完全性を確かめられなければ storage_state 2、reason 1。
  媒体の故障を電源断の規則と取り違えず、読めない保存を黙って使わない。

### 13.8 本体の項目

本体のカテゴリ（fn 0）の項目。channel を持ち、設定を持つ probe は、channel の項目を宣言する。

| 名前 | form | key_kind | 意味 |
|---|---|---|---|
| `channel.{}.label` | text（1〜32） | channel | ピンの呼び名（`NRST` など）。probe はこの名前で線を動かさない |
| `channel.{}.idle` | enum | channel | 空きの状態（§8）。選択肢: 0 `hi-z`、1 `pull-up`、2 `pull-down`、3 `low`（出力 low）、4 `high`（出力 high） |
| `channel.{}.disable` | bool | channel | 真なら、probe はそのピンを駆動も設定もしない |

- probe が自分で使う channel は、label の fixed の値だけを持ってよく、idle と disable を unsupported で断る。
- **disable** は、起動時と解いたときの空きの状態より先に効く。宣言を広げない。disable の channel を使う要求は unavailable（cause 5）。
  使用中の channel を disable にする set は unavailable（cause 1）。変更の後の設定で同じ channel に idle と disable（真）が両方あれば unavailable（cause 5）で断る
  （先にぶつかる値を unset する）。disable を unset した、または偽にした channel は、ただちに空きの状態に戻す。
- **idle** の変更は、空きの channel ではただちに、使用中の channel では次に空いたときに効く。値の無い channel は Hi-Z。出力の強さは probe が決める。
  probe が作れない状態の選択肢は setting_choice に並べない。出力の idle の channel を取れるかは、取る側のインターフェースの定義に従う（§8）。
- ネットワークの経路の項目（Wi-Fi のつなぎ先、IPv4 の決め方）と、その様子を読む op network（0x25）は、[経路](oep-transports.ja.md) §7 が定める。
- インターフェースの項目は、それぞれの文書が定める。
