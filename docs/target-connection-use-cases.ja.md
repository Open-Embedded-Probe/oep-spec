# Open Embedded Probe — target の発見と接続

状態: **仮置き**（2026-09-24 の議論の合意）。実験してから調整する。wire format は決めない。
セッション、ロック、長い操作は [セッションと排他](session-and-exclusivity.ja.md)、コンソールは
[コンソールのストリーム](console-stream.ja.md) に分けた。

## 前提

- **probe は target を知らない。** 起動時に分かるのは probe 自身と、どのピンでどの線（RVSWD、SWIO、SWD、JTAG）を
  出せるか、fixture 側の I/O だけである。
- **target の知識は host が持つ。** 返ってきた ID から「CH32X035 だ」と判断するのも、flash の形や書き込み方を知って
  いるのも host（ch32rv の DB など）である。
- **probe は自発的に target に触らない。** スキャン、attach、識別、detach はすべて host の指示で行う。

## attach と detach の副作用（実測）

| 事象 | 内容 |
|---|---|
| attach が target を書き換える | WCH-LinkE は attach のたびに、動いている target の RCC_CFGR0 と FLASH ACTLR を書き換えた（CH32V307 / V203 / L103） |
| 接続中は target の動きが変わる | debug module が有効な間は低消費電力のスリープが効かないことがあり、停止中は DBGMCU の設定次第でタイマなどが止まる。dmseq のコンソールは接続中しか使えない |
| 放置すると線が落ちる | CH32L103 の RVSWD は 1 ms 程度の無通信で落ちる。probe が次の転送の前に立て直す |
| 立て直しが target を乱す | RVSWD の立て直しは debug module をリセットし（止めていた hart が走り出す）、起こしの系列で target のアプリケーションも再起動する |
| 線のレベルに要件がある | RVSWD のアイドル時、L103 は SWCLK を low、X035 は両方 high に保つ必要がある |

このため、attach の回数を減らし、probe が線の状態を保ち続けることを基本にする（probe の状態は transport を閉じても
残る）。

## 接続の寿命

1. **attach / detach は host が明示的に指示する。** probe はタイムアウトで detach しない。線の維持（RVSWD の
   立て直しなど）は probe の中で行う。
2. **ロックの期限切れや transport の切断では、attach を解かない。** 次の host（one-shot CLI の次のコマンドを含む）は
   接続をそのまま使える。
3. **2 回目以降の attach は、最初に ID を読んで記録と照合する。** 機材は入れ替わる（このベンチでは日常的に）。
   違えばはっきり失敗させ、host がスキャンからやり直す。
4. 前回から状態が続いているかは、session_id の再開（間に誰も操作していない）と boot_id（probe が再起動していない）で
   判断する。

## ピンの指定

- **ピンは probe が振る channel 番号で指定する。** 同じファームとプロファイルなら起動ごとに同じ番号になる。
  ESP32 なら GPIO 番号と同じにするのが自然。宣言した順のインデックスにはしない。
- **人が読む名前（ラベル）は別に宣言する。** `GPIO5`、`D5`、`PA13`、fixture の端子名などを channel ごとに probe 全体の
  describe で任意に宣言する。利用者はラベルで指定し、host が channel に直す。

## スキャン

### 候補の一覧（許可リスト）

wire ごとの describe で、スキャンの候補を宣言する。

| probe | 宣言 | 無指定のスキャン |
|---|---|---|
| 汎用（Pico のばら配線、P4） | role_channels に SWDIO 候補・SWCLK 候補を並べる | 候補の全組み合わせを試す |
| ピン固定（LinkE 型、治具） | channel_group を 1 組だけ書く | その 1 組だけを試す |

- **候補の一覧は「スキャンで駆動してよいピン」の許可リストでもある。** スキャンは候補のピンにクロックやデータを出す。
  target の出力や fixture の出力につながったピンを駆動すると、ぶつかって壊しかねない。配線を知っているプロファイルが
  宣言したものだけを候補にする。
- **host からは足せない。** 変えるのはファームかプロファイルである。
- **host はスキャンの要求で候補の部分集合を指定できる**（その回だけ絞る。probe に状態を持たせない）。1 組の指定は
  その特別な形で、前回の記録の確認や 2 回目以降の接続に使う。許可リストに無いピンの指定は reject する。

### 結果

共通化できるなら共通の外枠にする。

```text
scan(wire の fn, 候補の部分集合（任意）, クロック) → 見つかったものの列
  found : kind(u8), channel の組, TLV（生の値）
```

| kind | 返す生の値 |
|---|---|
| riscv-dm（RVSWD / SWIO） | DMSTATUS、DM の版、hartinfo |
| arm-dp（SWD） | DPIDR、TARGETID（DPv2 以上）、AP の IDR の列 |
| jtag-tap | IDCODE の並び |

- probe は値を解釈しない。
- CH32 のチップ ID は ESIG（メモリ）にあり、DM 経由でメモリを読まないと取れない。**スキャンで分かるのは
  「RISC-V の DM が答えた」まで**で、識別には attach が要る。

### 時間

| 実測（Pro Micro RP2350 → CH32L103、2026-09-24） | 組数 | 所要時間 |
|---|---|---|
| ARM SWD（1 組あたり起動系列 4 通り） | 380 | 約 0.5 秒 |
| CH32 RVSWD（1 組あたりクロック 2 通り） | 420 | 0.4 秒以下 |

- P4 の 40 本（1,560 組）なら、1 つの線の種類で数秒の見込み（未測定）。数秒なら host に待ってもらえばよい。
- **眠っている CH32 は最初の起こしを無視することがある**（冷えた L103 は 5 回目で答えた）。1 組 1 回の試行では
  見落とすおそれがある。全組で 8 回ずつ試すと 10〜20 秒になる。対策の候補: 1 周目は 1 回ずつ速く回し、見つからなければ
  回数を増やしてもう 1 周。プルの様子（CH32 の SWDIO はプルアップ、SWCLK はプルダウン）で試す順番を決める
  （除外には使わない。RP2350 のエラッタ E9 やボードのプルアップで外れる）。
- 長くかかる場合は PENDING と status で扱う（[セッションと排他](session-and-exclusivity.ja.md)）。

## attach

```text
attach(wire の fn, channel の組, クロック, 方法) → 結果（成功・失敗は必須）, connection, 詳細
  方法 : 止めずに / 止めてから / リセットしながら（NRST の配線が要る）
```

- 成功・失敗は必ず返す。詳細（実際のクロック、止めたか、リセットしたか、target のレジスタを書いたか）をどこまで
  返すかは実験で決める。
- connection は、1 つの probe が線ごとに複数の target を同時に持てるようにするための番号。target を扱う操作は
  これを伴う。

## 能力の見え方

**target を扱うインターフェースの名前は、最初から list に出す。** 「この線で RISC-V の DM を扱える」という能力として
載せ、操作には attach が返した connection を付ける。未 attach で呼ぶとエラーになる。

- 操作できない probe に接続まで進まずに済む。
- list と fn は起動ごとに固定になり、状態を保つ方針や one-shot CLI と相性がよい（attach のたびに list が変わると、
  host が記録を持ち越しにくい）。
- どの名前（`oep.target.riscv-dm`、ARM 用など）を載せるかは、probe が話せる線で決まる。target を知らないという
  前提と矛盾しない。

## flash の書き込み（実験してから決める）

v0 は probe の中に CH32 の flash コントローラの扱い（geometry / erase_page / program_page / verify_crc32）を
持っていた。これは「target の知識は host が持つ」と食い違う。**v0 は移植しない。** v1 の標準は汎用の部品だけにし、
CH32 の書き込み手順は host（ch32rv の DB など）に置く方向で実験する。

| 部品の候補 | 使い道 |
|---|---|
| メモリのまとめ読み・まとめ書き | データの転送 |
| 短い手順を 1 回の要求で送る（書く、読む、条件を満たすまで待つ） | flash コントローラのレジスタ操作。往復を減らす |
| 実行して停止を待つ（PC と引数を設定して走らせ、ebreak で止まるまで待つ） | target の RAM に置いた書き込みプログラム（probe-rs / CMSIS の flash algorithm と同じ考え方） |

手順の表現は「条件を満たすまで待つ」までに留める候補（分岐やループを入れると小さな言語になる）。v0 は OEP を
書き込みの検証にだけ使っていたので、v1 ができるまで一時的に無くなってよい。

実測（[experiments/flash-primitives](../experiments/flash-primitives/README.ja.md)、2026-09-24、基準は WCH-LinkE +
ch32rv）: CH32X035 62 KB は、host の RAM ローダー + ブロック書き込み + 実行して停止を待つ（F4）で消去 + 書き込み
1.7〜2.2 秒、LinkE が約 2.1 秒で同等。CH32V003 16 KB は F4 で 3.6 秒、LinkE が 1.6 秒（OEP 側は 115200 bps の UART
経由で、転送が主な差）。host の手順のリストだけ（F3）は X035 で 15.2 秒で、DM アクセスが多すぎる。どの部品を標準に
するかは未決。

## 使い方ごとのユースケース

| 使い方 | host のプロセス | 求めるもの |
|---|---|---|
| Arduino の書き込み | 1 回ごとに起動・終了 | 記録からの attach、ID の照合、書き込み手順は host |
| Arduino の Monitor | 長く動く | コンソール専用の口、または OEP の中のストリーム。書き込みの間は閉じる（口が 1 本の場合） |
| デバッグ（gdb） | 長く動く | halt、レジスタ、ブレークポイント。止まるまで走らせる操作は PENDING |
| ch32rv 型（テストなど） | 1 プロセスですべて | 最も単純 |
| 対話型の CLI | 1 セッション、人の速さ | 長い放置の間も線を保つ（probe の中）。keepalive でロックを保つ |
| one-shot CLI（`probe-rs read` 型） | 1 コマンドごとに開閉 | 状態の保持。session_id を保存して、コマンドの間に誰も触っていないことを確かめる |

### UC-T1: 初めてのベンチで、何がつながっているかを調べる

1. host がつながっている probe を列挙する（USB など。OEP の外）。
2. 各 probe について list で能力を読む。
3. 各線について、無指定でスキャンを指示する（候補の全組み合わせ）。
4. probe は応答を生で返す。host が ID を DB と照合し、target の候補を絞る。
5. host が attach を指示し、target の識別レジスタ（CH32 なら ESIG のチップ ID と UID）を読んで確定する。
6. host が「probe の個体、線、channel の組、target の ID」を記録する。

### UC-T2: 2 回目以降に、書き込んで走らせる

1. host が記録を読み、記録した 1 組だけでスキャン（または直接 attach）する。
2. attach したら最初に ID を照合する（違えば UC-T5）。
3. 書き込み、verify、リセットして走らせる（コンソールに reset マークが付く）。

### UC-T3: 走らせながらコンソールを読む

1. Monitor は「最後の reset マークから」読み始める。
2. 書き込みのために Monitor が閉じても、probe はためておく。戻ったら続きの位置から読む。

### UC-T4: host が落ちた・ケーブルが抜けた

1. probe は何も戻さない（attach、ピン、線の状態を保つ）。長い操作は最後まで進める。
2. ロックは期限で下りる。同じ host が同じ session_id で戻れば、最後の結果を取り出して続けられる。
3. 別の host が来たら、新しい session_id で open する。状態は残っているので、ID の照合から始める。

### UC-T5: 機材が入れ替わっていた

1. ID の照合で、記録と違う target が見える（または何も見えない）。
2. host は操作を中止し、その線について UC-T1 のスキャンからやり直す。

### UC-T6: target のリセットや電源断で接続が切れた

1. probe はコンソールに restart / link-lost のマークを付け、次の操作の失敗で host に伝える。
2. host が方針に従って attach し直すか止める。probe が黙って attach し直すことはしない。

### UC-T7: debug の影響なしに target を観測する

1. 書き込みのあと detach し、debug module の影響（スリープ、停止中のタイマ）を外す。
2. fixture 側の I/O だけで target の振る舞いを観測する。
