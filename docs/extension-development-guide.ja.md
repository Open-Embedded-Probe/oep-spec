# 独自インターフェースを定義して検査する

状態: **ガイド**（規範ではない）。定義の要件は [core §12](oep-core.ja.md#12-拡張の規則インターフェースの書き方)、適合の要件は [適合検査](conformance.ja.md) に従う。
OEPを使うプロジェクトが、独自機能の仕様と検査を作るための書式と進め方を示す。

## 最初に決める範囲

機能の仕様は、その名前を所有するプロジェクトで管理する。独自の逆DNS名を付け、Probeが提供する機能をlistへ出す。
Hostは(name, instance, revision)を選び、今回のbootのfnへ解決して呼び出す。
instanceは欠番を許す固定識別子で、保存した組が見つからなければ未提供として扱う。

定義を小さく始めるため、最初の機能に必要な操作と共通部品を選ぶ。
pin割当が必要ならその取得・解放を、資源を作るなら種類・所有者・寿命を定義する。
位置つきストリームを採用するなら [共通部品](../interfaces/oep-if-common.ja.md) のreadなど、採用する操作を定義する。
通知を提供する場合はsubscribe/unsubscribeと出来事を定義する。OEPの標準機能をすべて採用する義務はない。

自己更新、権限付きの製品操作、共有機材の接続の保護は、[利用場面ごとの拡張例](extension-use-cases.ja.md)で示す。
新しい名前の機能に条件を定義する例と、OEPへ到達する前の接続を保護する例を扱う。
既存coreのopen/forceや標準機能の読み出しの条件を変えることは、任意の拡張追加だけからは導けない。

## 定義の書式と小さい例

以下は、状態を持たず受け取ったbyte列を返す`io.example.echo`という説明用の独自機能の例である。
実際の名前は所有するドメインから選ぶ。製品の端点や実装済みサンプルを提供するものではない。

| 定義する項目 | この例の選択 |
|---|---|
| 名前・revision | io.example.echo、revision 1 |
| target系統・外部仕様 | targetに依存しない。外部仕様なし |
| 操作表 | op 0x10 echo、必須、ロック不要 |
| 要求 | n(u16)、n個のbyte、末尾のTLV |
| completed success | n(u16)、要求と同じn個のbyte、末尾のTLV |
| failed / partial | この操作は生成しない |
| describe | opsで0x10、max_lengthでnの上限を宣言。例として48byte |
| 独自TLV・reason・status・event | 追加の定義なし。未知TLVと共通拒否はcoreに従う |
| 状態・資源・pin・通知 | いずれも作らず、操作による状態変化なし |
| 範囲外 | nが宣言した上限を超えればunsupported。構造と拒否の順序はcore §4.3に従う |
| 未知値の扱い | 独自enum/flagsなし。共通の応答はcore §2.4に従う |

max_frame=64の場合、この例の最大データ要求は10+2+48=60byte、成功応答は5+2+48=55byteとなる。
末尾のTLVもframeの上限に含める。上限は宣言した48を保ち、余ったframe量からHostが独自に引き上げない。
coreが要求するfn 0の操作・宣言は別に実装する。fn 0のmax_op_msは、この機能も含めて決める。
固定部・TLV値・配列要素は末尾を伸ばさず、追加情報は新しいTLVで運ぶ。

## 仕様から3層の検査へ

| 層 | 対象と代表的な確認 |
|---|---|
| コア | 全端点のconfirm、発見、見出し/TLV、session、再送、時刻。提供するtransportと資源に適用される契約 |
| 拡張共通 | 名前/revision/instanceの一意性、ops、describeの固定形と同じboot内の不変性、未提供opの拒否。採用した資源・通知・共通部品の契約 |
| 個別拡張 | その機能の操作と観測可能な作用。この例なら空と上限のecho、上限超過の拒否、返却byte列、状態を変えないこと |

個別検査のcaseは「仕様の参照 → 初期状態 → 要求 → 期待応答 → 独立に観測する作用 → 後始末」で書く。
標準OEPのGPIO/UART/wire/targetの検査もこの書式を使い、独自機能では個別操作のadapterを入れ替える。
実装から期待応答を作らず、仕様で定義した意味を期待値とする。拒否の応答だけでなく、拒否前後の作用も比較する。
特定の構成が無い場合の適用外と、用意すべき観測や前提が不足した未実行を区別する。

最初は代表ケースで小さい構成・拒否時不変・寿命を確認し、結果を仕様の見直しに戻す。
選択したケースのPASSには検査範囲を付け、全適合を主張する場合は [適合要件](conformance.ja.md) の適用される全契約を検査する。
機器の選択、配線、刺激、観測は呼び出すプロジェクトが明示的に渡す。共通検査器に特定の設備の場所や台帳を埋め込まない。
結果にはSPEC commit/tag、Probe firmware、使用した能力、検査器と構成の識別、要求/応答、観測を記録する。

## 拡張するとき

既存の形と振る舞いを保つ任意TLV/op/eventは同じrevisionへ追加できる。任意opはops、op以外の能力はそのdescribeで宣言する。
必須化、固定形、状態遷移、資源寿命など既存の契約を壊す変更は、凍結後にはrevisionを上げる。
別の意味の機能は別の名前で定義する。他の所有者のインターフェースへ独自のopやtagを足さない。
チップ固有の手順はHostで処理できるかを先に考え、Probe側の時間条件が必要なら専用の名前の機能で定義する。
