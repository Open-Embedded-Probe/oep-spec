# Open Embedded Probe — Project要求

状態: **検討中の要求案**。この文書は、[プロジェクトの目的と範囲](project-concept.ja.md)および[相互運用ユースケース](use-cases.ja.md)から、OEPが満たすべき性質を技術方式に依存しない要求として抽出する。

protocol構造、message model、encoding、識別子、接続方法または実装技術は、この文書では決めない。

## 要求の読み方

各要求は次の要素を持つ。

- **要求** — OEPが満たすべき性質
- **理由** — その要求が必要な理由
- **由来** — 要求の根拠となるユースケース
- **成立の確認** — 将来、要求を満たしたと判断するために観測すべき結果

`OEP-REQ-*`の番号は議論と追跡のための仮番号であり、protocol上の識別子ではない。要求が確定するまで番号の変更を許容する。

## OEP-REQ-001: 組合せ固有の対応を必要としない

### 要求

共通に定義された機能について、独立して開発されたprobe実装とhost実装は、その組合せ専用の変更を追加せずに相互利用できなければならない。

hostは、product名、board名、firmware名等だけを根拠とする組合せ固有の処理を、共通機能の利用に必須としてはならない。

### 理由

個々のprobeとhostの組合せごとに専用対応が必要であれば、実装間の分断を解消できないため。

### 由来

- UC-1: 個別対応のない組合せで共通機能を利用する

### 成立の確認

- 一つのhost実装が、組合せ専用の変更なしに複数のprobe実装で同じ共通機能を利用できる
- 一つのprobe実装が、組合せ専用の変更なしに複数のhost実装へ同じ共通機能を提供できる

## OEP-REQ-002: 機能の意味を実装間で共有できる

### 要求

OEPは、機能、操作、入力、結果および外部から観測できる振る舞いについて、独立したprobe実装とhost実装が同じ意味を共有するために必要な定義を提供できなければならない。

同じ機能として扱うものは、特定実装の内部構造に依存せず、利用側から見た意味が一致しなければならない。

### 理由

dataを交換できるだけでは、その解釈が一致せず、機能を相互利用できないため。

### 由来

- UC-1: 個別対応のない組合せで共通機能を利用する
- UC-3: 実装ごとの違いと制限を扱う

### 成立の確認

- 同じ操作と結果を、複数の独立実装が同じ意味として解釈できる
- 実装内部の違いが、共通に定義された外部の意味を変更しない

## OEP-REQ-003: OEP機能の通信経路を明示する

### 要求

OEP機能の利用に必要なhost–probe間通信は、次のいずれかとして扱われなければならない。

- 操作、data、状態、結果および失敗をOEP protocolで運ぶOEP native path
- OEP機能と外部interfaceまたは外部protocolの関係をOEP上で明示するexternal binding

external bindingは、USB CDC、USB Audio等の標準interfaceでも、独自protocolまたは非公開protocolでもよい。機能に必要な通信を、OEPから認識できない未宣言の外部経路へ暗黙に切り替え、または依存させてはならない。

external bindingは、対応する提供機能と外部経路の関係、およびhostが対応可否を判断するために必要な情報を示せなければならない。OEP側と外部側の設定、開始、停止、状態、失敗およびresource管理の責任は、bindingごとに曖昧でないよう定義されなければならない。外部protocol自身が定義する制御を、OEPが重複して定義することは要求しない。

一つの提供機能が複数の通信経路を持つ場合、それらが代替、併用可能または排他的であるかを誤解なく扱えなければならない。

OEPを運ぶ下位通信、接続を成立させるための接続固有手続き、およびprobeとtargetの間の通信は、host–probe間の機能通信経路には含めない。

### 理由

OEP native pathだけに限定すると、USB標準class等の既存interfaceを直接利用する実用的な構成を表現できない。一方、外部経路を明示しなければ、hostが必要な対応を判断できず、組合せ固有の隠れた依存になるため。

### 由来

- UC-5: 新しい機能または実装固有の機能と共存する
- UC-6: 独自機能に対応する専用hostとprobeを実装する
- UC-7: 異なる接続環境で同じ機能を利用する
- UC-10: OEP機能のdataを外部interfaceで直接利用する

### 成立の確認

- OEP native pathだけで完了する機能を実装できる
- UARTからUSB CDC、I2SからUSB Audio等のdata経路をexternal bindingとして表現できる
- 独自protocolを使う外部経路も、一般的なhostが誤認しない形でexternal bindingとして表現できる
- hostが、必要なexternal bindingへの対応有無を判断できる
- hostが、OEP機能に対応する外部interfaceまたは外部protocolを特定できる
- external bindingが利用できない場合に、同じ機能の別経路や無関係な機能を不必要に利用不能にしない
- 未宣言の外部経路がなければ動作しない機能を、成立するOEP機能として扱わない

## OEP-REQ-004: 接続interfaceと機能の意味を分離する

### 要求

OEPは、異なる接続interface上で、機能の意味を接続方法ごとに再定義せずに利用できなければならない。

接続interface固有の性質や制限は、機能そのものの意味と混同されてはならない。

### 理由

接続方法ごとに機能を別仕様として定義すると、同じ機能を再利用できず、interfaceごとの専用実装へ戻るため。

### 由来

- UC-7: 異なる接続環境で同じ機能を利用する

### 成立の確認

- 同じ機能定義を、少なくとも二つの異なる接続環境で利用できる
- 接続環境の変更だけを理由に、操作や結果の意味が変化しない
- 接続固有の制限を、機能全体の非互換として扱わない

## OEP-REQ-005: 対応範囲の共通部分を利用できる

### 要求

probeとhostの対応範囲が一致しない場合でも、双方が共通に理解する機能は利用できなければならない。

一方だけが理解する機能は、共通機能の利用を妨げたり、別の既知機能として解釈されたりしてはならない。

### 理由

すべての実装に同じ機能集合を要求せず、規模や目的の異なる実装を相互運用可能にするため。

### 由来

- UC-2: 対応範囲が部分的に異なる実装を組み合わせる
- UC-5: 新しい機能または実装固有の機能と共存する

### 成立の確認

- 対応機能の異なる実装間で、共通機能だけを利用できる
- 未知の機能を含む実装と接続しても、既知の共通機能を利用できる
- 共通部分がない場合に、相互利用が成功したように扱われない

## OEP-REQ-006: 実装ごとの制限を正しく扱える

### 要求

OEPは、同じ機能を提供する実装間に存在する性能、規模、選択可能な条件、同時利用条件その他の制限を扱えなければならない。

実装が満たせない条件を、別の操作として実行したり、満たしたものとして成功扱いしたりしてはならない。

### 理由

機能の意味が同じでも、hardwareやfirmwareによって実行可能な範囲は異なるため。

### 由来

- UC-3: 実装ごとの違いと制限を扱う
- UC-4: 一つのprobeが複数の機能を提供する

### 成立の確認

- 同じ機能を異なる制限で提供する複数実装を、意味を変えずに利用できる
- 満たせない条件が、成功または意味の異なる処理として扱われない
- 機能間に制約がある場合、実際には成立しない同時利用を成功扱いしない

## OEP-REQ-007: 複数機能を独立して扱える

### 要求

一つのprobeは複数の機能を提供でき、hostは理解または必要とする機能だけを利用できなければならない。

一つの機能を利用するために、関係のない機能への対応を必須としてはならない。

### 理由

異なる規模や目的のprobeとhostが、必要な範囲だけで相互運用できるようにするため。

### 由来

- UC-2: 対応範囲が部分的に異なる実装を組み合わせる
- UC-4: 一つのprobeが複数の機能を提供する

### 成立の確認

- 複数機能を持つprobeから、一つの機能だけを利用できる
- 一部の機能を理解しないhostも、理解する機能を利用できる
- 一つの機能だけを持つprobeもOEPへ参加できる

## OEP-REQ-008: 独自機能をOEP内で定義できる

### 要求

OEPは、共通に標準化された機能に加えて、独自機能、実験的な機能および特定用途の機能を、既存機能と取り違えずに定義できなければならない。

独自機能を理解しない実装も、共有する既存機能を引き続き利用できなければならない。

### 理由

中央での標準化を待たずに新しい用途を実装可能にしながら、既存の相互運用を維持するため。

### 由来

- UC-5: 新しい機能または実装固有の機能と共存する

### 成立の確認

- 二つの主体が追加した異なる独自機能を取り違えない
- 独自機能を理解するhostはOEP上でその機能を利用できる
- 独自機能を理解しないhostも、既知の共通機能を利用できる

## OEP-REQ-009: 独自機能の仕様公開を必須としない

### 要求

OEPは、独自機能の意味またはdata形式をOEPの共通部分や一般的なhostが理解することを要求してはならない。独自機能の仕様公開や、第三者による再実装の許可を、OEP利用の必須条件としてはならない。

専用hostとprobeは、両者だけが理解するdataをOEP native pathまたは明示的なexternal bindingで交換できなければならない。これには、別protocolで定義されたpacketまたはbyte列をOEP native pathの独自dataとして運ぶ場合と、独自protocol自体をexternal bindingとして利用する場合を含む。

### 理由

独自機能の開発、製品固有機能および非公開機能を許容しながら、接続interfaceの違いはOEPによって吸収するため。

### 由来

- UC-6: 独自機能に対応する専用hostとprobeを実装する

### 成立の確認

- OEPの共通部分が内容を理解しない独自dataを、専用hostとprobeの間でOEP native pathにより交換できる
- 非公開の外部protocolをexternal bindingとして使用できる
- 独自機能の仕様を公開しなくても、その機能をOEP上で提供できる
- 独自機能を理解しないhostが、そのdataを既知の機能として誤解しない
- OEP native pathかexternal bindingかをhostが区別できる

## OEP-REQ-010: 互換な範囲で改訂を共存させる

### 要求

機能の定義または実装が改訂された場合、probeとhostは、意味に互換性がある範囲を利用できなければならない。

意味に互換性がない操作は、名称等の一部が同じであることだけを理由に実行してはならない。

### 理由

機能を発展させながら既存実装との相互運用を維持し、意味の異なる操作を誤実行しないため。

### 由来

- UC-8: 機能を改訂しながら既存の相互運用を維持する

### 成立の確認

- 改訂の異なる実装間で、互換な範囲を利用できる
- 意味が互換でない範囲は、成功した操作として扱われない
- 新しい機能の追加だけを理由に、既存の互換な範囲が利用不能にならない

## OEP-REQ-011: 非対応と失敗を誤った成功にしない

### 要求

OEPは、少なくとも次の状況を、hostが誤った成功または誤った意味として扱わないために必要な範囲で区別できなければならない。

- 共通に理解する機能がない
- 機能の意味または改訂に互換性がない
- 要求した条件が実装の制限を超える
- 現在の構成または状態では利用できない
- 操作を開始できない
- 開始した操作を継続できない
- 結果の全部または一部を信頼できない
- 受け取った情報を理解できない

### 理由

利用不能、非対応または失敗を成功と誤認すると、targetへの誤操作や誤った観測結果につながるため。

### 由来

- 相互運用ユースケースの「失敗および非対応の場面」

### 成立の確認

- 各状況が成功として報告されない
- hostが、継続、条件変更、中止または利用者への通知を選ぶために必要な違いを判断できる
- 不完全または信頼できない結果が、完全で有効な結果として扱われない

## OEP-REQ-012: 相互運用を実装から独立して検証できる

### 要求

OEPへの適合と相互運用は、特定のreference implementationを使用していることではなく、外部から観測できる振る舞いによって検証できなければならない。

protocolへの対応、個別機能への対応、接続環境固有の対応およびその他の適合主張は、必要に応じて区別できなければならない。

### 理由

特定のcodebaseへの依存を避け、独立した実装間で相互運用を確認できるようにするため。

### 由来

- UC-1: 個別対応のない組合せで共通機能を利用する
- UC-6: 独自機能に対応する専用hostとprobeを実装する
- UC-7: 異なる接続環境で同じ機能を利用する

### 成立の確認

- 少なくとも二つの独立したprobe実装と二つの独立したhost実装の組合せで、共通機能を検証できる
- 同じ観測可能な要件を、異なる内部実装へ適用できる
- 一つの適合主張を、別の種類の適合または品質保証として扱わない

## OEP-REQ-013: 非互換な派生をOEPとして識別しない

### 要求

OEPの必須要求を満たさないprotocolまたは実装は、OEPへの適合または互換性を主張してはならず、OEP protocolと誤認されるprotocol名またはprotocol identityを使用してはならない。

将来OEP projectへUSB VID:PIDその他の共通identityが割り当てられた場合、非互換な派生はそれを使用してはならない。非互換な派生は独自のidentityを使用し、OEP実装と機械的に区別できなければならない。

OEP endpoint、適合するexternal binding、およびOEPから独立した別機能または別protocolを、同じ物理deviceへ併設できる。hostはそれぞれの関係を区別できなければならず、独立した別protocolをOEP endpoint、OEP機能またはexternal bindingとして誤認してはならない。

適合するexternal bindingは、登録済みまたは許容されたprofileの範囲でOEP endpointと同じUSB VID:PIDその他のdevice identityを共有できる。外部通信を使用することだけを理由に非互換な派生としてはならない。

source codeまたは仕様を変更、forkまたは移植した事実だけでは、OEPへの適合性を決定しない。変更後も必須要求を満たす実装はOEP実装になり得る。

### 理由

相互運用できない実装がOEPと同じidentityで混在すると、hostが誤って接続または操作し、OEP ecosystem全体の互換性を判断できなくなるため。

### 由来

- UC-9: 非互換な派生をOEP実装と区別する

### 成立の確認

- hostが、非互換な派生をOEP endpointとして選択しない
- OEPの共通identityを持つ実装に、OEP endpointや適合するprofileを持たないものが混在しない
- 同じ物理deviceにOEP endpoint、external bindingおよび独立した別protocolが併設されても、それぞれの関係を誤認せず選択できる
- 登録済みまたは許容されたexternal bindingが、同じdevice identity内でOEP endpointと関連付けられる
- 異なるhardwareまたは接続interfaceへの適合実装は、forkやportであることだけを理由に排除されない

この要求案は、次の事項をまだ決定しない。

- 「機能」を構成する情報と定義の単位
- 標準機能と独自機能の識別方法
- 独自機能が公開仕様か非公開仕様かを示す必要性と、その表現方法
- 対応範囲や実装制限を伝える方法
- 操作、data、状態、結果および失敗の表現方法
- 接続interfaceとOEP protocolの境界
- OEP native pathとexternal bindingの識別、関連付けおよびlifecycle
- external bindingにおける設定責任、状態同期、失敗およびresource関係
- versionと互換性の表現および判断方法
- 適合性のlevel、test方法および管理主体
- OEPの名称、protocol identity、project PIDおよびその他の共通identityの具体的な利用条件
- OEP endpoint、external bindingおよび独立した別protocolを同じ物理deviceへ併設する場合の識別およびUSB profile規則
