# 拡張例: 自己更新、権限付き操作、共有機材

状態: **ガイド**（規範ではない）。[拡張開発ガイド](extension-development-guide.ja.md)の定義方法を、利用場面に当てはめる。
以下の`io.example.*`は説明用の名前であり、標準OEPの追加や実装済みの機能を表さない。
実際の名前、revision、op、固定形、認証方式は、その名前を所有するプロジェクトで定義する。OEPのregistryへ番号を追加する必要はない。

これらの例は、既存coreの契約を使って機能を追加する。coreの`open/force`や、標準インターフェースの読み出しの条件は変えない。
core操作まで認可で拒否する機能を同じrevisionへ追加できる、という約束をこのガイドから導かない。

## 1. 利用場面から拡張する場所を選ぶ

| 利用場面 | 拡張する場所 | Hostの流れ |
|---|---|---|
| app自身を、既存のUSB/UARTローダーで更新する | 更新モードへ移る新しいインターフェース（§2） | 発見、セッション、入口操作、別protocolで転送、appを再発見 |
| 自分のローダーへOEPでimageを送る | imageを扱う新しいインターフェース（§3） | ローダーを発見、分割転送、検証・確定、appを再発見 |
| 製品の強い操作を保守者だけに許す | 認可条件を最初から定義した新しいインターフェース（§4） | 発見、セッション、認証、許可された操作、状態確認 |
| 共有機材を未許可の利用者から守る | OEP接続へのアクセスを管理する経路/サービス（§5） | 接続の認証・許可を得てから、通常のOEPを使う |

能力はlistとdescribeで見つける。名前付き機能を使わないHostには、その実装や認証UIを要求しない。
機能の追加は新しいfnで表し、同じboot内で認証状態に合わせてlistやopsを増減しない（core §7.2/§7.3）。

## 2. appから別のローダーへ移る

OEPを話すappが、自分自身の更新対象でもある場面を考える。OEPの役割ではその装置がProbeである。
例えば`io.example.boot`で、更新の入口を表す。外部target用のwireやconnectionを作る必要はない。

| 操作の例 | 入力/結果 | ロック | 設計する意味 |
|---|---|---|---|
| status | 今のmode、最後に受け付けた移行の状態 | 不要 | 現在の状態を読み、移行を起こさない |
| enter | 移る先の識別子 → 移行要求の受付結果 | 必要 | 指定したローダーへ移る。応答を送ってから移行する |

describeには、選べる移行先と次のprotocolを宣言する。例えばvendor USB ISP、UART ISP、OEPを話す自前ローダーである。
Hostの待つ期限、USB再列挙やbaud変更、個体の照合方法は、その移行先の定義とHost adapterで扱う。
chip固有のBOOT切替やFlashの配置は、その機能を所有する実装の仕様へ置く。

Hostの手順の例:

1. confirm/list/describeで機能を見つけ、保存した(name, instance, revision)を今回のfnへ解決する。
2. openし、必要ならその新しい機能の認可条件を満たす。指定先と移行条件をProbeが副作用前に検証する。
3. enterの応答を読んだらOEP接続を閉じ、宣言されたローダーのprotocolへ切り替える。
4. 同じ装置を照合してimageを転送する。OEPを話さないローダーにもOEPのframingや起動baudを要求しない。
5. appへ戻ったらconfirmからやり直す。前のsession、fn、資源を引き継がず、新しいbootの宣言を読む。

応答を失った場合は、app/ローダーのどちらが動いているかを確かめて回復する。新しいcorrでenterを盲目的に再実行しない。
別protocolのローダーが同じUSB serialを持たない場合もあるため、unit_idだけで常に照合できるとはしない。
入口を認証しても、移行先のローダーへの書き込み権限やimageの真正性まで自動で保証されるわけではない。移行先の更新方針も合わせる。

標準の`oep.probe.restart`は、元の経路でOEPを受けられる内部状態へrestart_max_ms以内に戻る契約である。
OEPに戻らないローダーへ移る意味を、その既存操作へ独自TLVで足さない。上の例のように自分の名前の機能として定義する。

## 3. ローダーがOEPで自分のimageを受け取る

ローダー自身をOEP Probeとして起動し、例えば`io.example.update`をlistへ出す。
appとローダーは、異なるboot_idと機能一覧で表せる。同じ個体のunit_idと、同じmodelのtransport indexの契約は保つ（core §7.5）。
標準OEPはimage形式、Flash layout、署名方式を定めないので、この拡張の所有者が定義する。

| 操作の例 | 設計する意味 |
|---|---|
| begin | imageの対象・識別子・長さを検証し、更新を開始する。消去を始める時点も定義する |
| write | offset/count/dataで分割して送る。応答は、どこまで書き込みを確認したかを示す |
| status | 更新中のimage、確認済み範囲、未確定/起動可能などの状態を読む |
| finish | image全体を検証して確定する。appへ移る場合は、応答と移行の順を定義する |

begin/write/finishはロックを要する。statusは状態を変えず、公開してよい情報だけを返す。
describeには、image領域の上限、writeの機能上限、対応する検証方式を宣言する。現時点の進行はstatusで返す。

固定形を定めるときは、writeの要求にcountを置き、その後ろにdataと拡張TLVを置く。
例えばoffset(u32)/count(u16)/dataという固定部分なら、frame64でdataに使えるのは最大48byte（64−要求見出し10−offset4−count2）である。
追加の識別子や証明を置く場合は、そのbyte数も引く。Hostは、機能上限と経路のmax_frameの両方に収めて分割する。
全処理の時間はfn 0のmax_op_msへ含め、長い消去などは各操作の上限または分割した手順で扱う。

この機能の定義で決める点:

- 書いてよい範囲。loader自身、鍵、起動設定をimageの書き込みで壊さない境界を明示する。
- writeの進捗の計測点。failedや応答喪失だけでは、Flashが変わっていないとは判断しない。
- 同一要求の再送はcore §5.1に従う。result_lostではstatus等で状態を読み、新しいcorrで同じ消去/書き込みを自動再実行しない。
- セッションが終わった場合の更新状態。操作権と一時bufferは解放し、書き込み済みFlashや永続した進行記録の扱いは別に定義する。
  次のセッションで再開できるなら、そのimageの照合・認可を改めて行う。前の資源番号を引き継がない。
- imageの検証と、起動可能とする確定点。転送のchecksum、署名/MAC、利用者が自由に書き換える開発modeは、必要な信頼条件に合わせて選ぶ。

小さい装置では、単一app領域と独立したloaderを選べる。更新失敗後にloaderで再試行することと、旧appを保持することは別である。
旧appへ戻す必要があるなら、A/Bや退避・swapをその実装の要件として追加する。
appだけが実行する更新入口ではapp破損後の復旧を保証できないため、独立したloaderの起動条件と通信経路を用意する。
loaderにOEPのcoreが入らない場合は、§2の「入口だけOEP」の構成を選べる。

## 4. 新しい機能だけに権限を設ける

例えば`io.example.control`は、公開状態の照会と、保守者だけが実行できる製品固有の操作を持つ。
必要な証明と権限不足時の拒否を、その名前/revisionの最初から定義する。標準GPIOやraw debugを認証で上書きする例ではない。
同じ強い作用を公開の別機能でも実行できる構成では、その別機能も含めて公開範囲を設計する。

| 操作の例 | ロック | 設計する意味 |
|---|---|---|
| status | 不要 | 公開の状態を返す。認可済みのふりをしたり、権限を変更したりしない |
| authorize | 必要 | 証明を検証し、このセッションから使える操作の許可を設定する |
| service | 必要 | 本人・許可・対象・引数を確かめてから、製品固有の操作を実行する |

Hostは通常のopenの後にauthorizeを行い、serviceを使う。権限を変えるauthorizeを、ロック不要の読み出しとして定義しない（core §6.3）。
方式や対応する操作集合はdescribe、現在の許可は状態照会で表す。認可によって同じbootのlist/describeを変更しない。
権限は単一のlevelに限定せず、対象と操作の集合でも表せる。方式やbit数を全Probe共通の要件にしない。

session_idは本人認証ではない。平文で知った同じIDを使えるため、この機能の許可を、認証した接続/本人や操作ごとの証明へ結び付ける。
操作ごとの証明を使うなら、改ざんと別要求への流用を防ぐ対象に、boot/session、corr、fn/op、引数を含める方式を定義する。
必要な証明を省いた要求の拒否は、その新しいインターフェースの契約にする。
要求の証明だけではProbe本人や応答の真正性は保証されない。必要な応答/通知の完全性と秘匿も、経路またはその方式で扱う。

許可はセッションの終了・別IDのforce・再起動で引き継がない。期限や明示的な失効も、その機能の定義へ置く。
過去のauthorize/serviceの成功を再送で受け取っても、今の許可や資源が復活したとは扱わない。現在の状態は新しいcorrで照会する。

coreの再送判定は個別操作より先にあり、保持した過去の応答を返す。
秘密を返す拡張では、その古い応答も含めて認証・暗号化した経路で守るか、該当要求のbyte記録を保持しない構成（core §5.1）を選ぶ。
後段のserviceだけで認可を確かめても、cached応答の返却まで拒否できるわけではない。
認可後に秘密を平文で返す方式は、経路を読める相手からの秘匿を保証しない。

この例のcoreは公開のままであり、未許可の利用者のforceでもセッションは終わる。
作業の継続も守る必要がある場合は、§5の接続全体の保護を組み合わせる。

## 5. 共有機材のcore操作も守りたい場合

共有ベンチでは、forceで接続やGPIO等が解放されること自体が作業を妨げうる。
ここでは、認証したトンネルや接続を管理するサービスを前段に置き、許可した利用者だけを制御用OEP端点へ到達させる構成を使える。
認証が済んだ接続の内側では、既存coreのopen/force/再送を通常どおり扱う。

観測専用の利用者へ、制御用OEP接続をそのまま渡さない。必要なら別の公開APIから観測を提供する。
保護していない別のUSB/UART/TCP経路から同じ制御用端点へ到達できると、その保護を迂回できる。入口の公開範囲を揃える。
Hostの画面でforceボタンを隠すだけでは、端点へのアクセス制御にならない。

brokerが自分でOEP要求へ応答するなら、それ自身がProbeであり、通常のcore契約を実装する。
有効なcore要求を独自に拒否し、既存の成功条件や拒否順を変えた端点を、この構成だけを根拠に同じrevisionの準拠端点とはしない。
同じOEP端点の中で、既存core操作や標準インターフェースの読み出しへ新しい認可条件を強制したい場合は、core/該当revisionの契約を別に検討する。

## 6. 拡張例の確認方法

[適合要件](conformance.ja.md)と拡張開発ガイドの3層に加え、各例の作用を観測する。

| 例 | 個別に確かめる境界 |
|---|---|
| 更新モードへの入口 | 非対応先の拒否時不変、応答前に切断しないこと、応答喪失時の移行先の確認、appへの復帰と新しいboot |
| OEPによるimage転送 | 領域外/上限超過を副作用前に拒否、frameに収まる分割、応答喪失後の進行確認、電源断後にloaderへ戻れること |
| 権限付き操作 | 証明なし/別人/対象違いの拒否時不変、失効、end/force後の許可消去、古い成功で許可を復活させないこと、cached応答の保護 |
| 接続全体の保護 | 未許可の接続から制御用端点へ到達できないこと、保護外経路の有無、許可した接続のcore動作 |

各プロジェクトは、採用した例の具体的な固定形・失敗・寿命と、観測方法を自分の仕様へ落として検査する。
このガイドの操作名や表だけを、実装間のwire仕様として使わない。
