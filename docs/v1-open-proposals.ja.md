# OEP v1 — 未合意の案

状態: **案（未合意）**（2026-09-24 起草）。実装の前に決める必要があるものを、現状、案、推奨の順に書く。
合意したら該当する文書へ移し、ここから消す。

## 1. 線の組み合わせのスキャンと、長い操作（PENDING）の最初の実装

### 現状

- `oep.wire.<線>` の scan は、probe のビルドで決めた 1 組（ESP32-P4 なら GPIO2 / GPIO54）に DM が答えるかを見るだけで、
  すぐ終わる（P4 で 0.00 秒）。
- 2026-09-24 の議論で合意したこと: 無指定なら probe の候補の全組み合わせを、ピン固定の probe は 1 組だけを、host が
  ピンを指定したら許可リストにあるか確かめてその組を、スキャンする。数秒なら待たせてよい。長い操作は PENDING と
  ポーリング（[セッションと排他](session-and-exclusivity.ja.md)「長くかかる操作」、[v1 の差分](v1-core-wire-delta.ja.md) §4）。
- 長い操作は仕様だけあり、実装はない（status と cancel は unavailable を返す）。今ある操作はどれも数百 ms 以内に終わるので、
  PENDING を必要とする操作がまだ無い。

### 決めること

1. **スキャンで見つけた組で attach する方法。** 今の attach は、ビルドで決めた組にしかつながらない。候補の全組み合わせを
   探す意味があるのは、見つけた組にそのままつなげられるときだけである。
2. PENDING を、全組み合わせのスキャンから入れるか。

### 案

- scan の要求: `count(u8)` と `swdio(u16) swclk(u16)` の並び。count 0 は、probe が許可した組をすべて試す。応答は今と同じ
  （見つかった組と DMSTATUS の並び）。
- attach の要求に、組（`swdio(u16) swclk(u16)`）を任意で付ける。付いていて今の組と違えば、probe は PHY をその組に
  つなぎ直す。許可リストにない組は rejected。
- 全組み合わせのスキャンは PENDING を返し、進捗は（試した組の数、全部の組の数）。PENDING の仕組み（activity は probe
  全体で 1 つ、ぶつかる要求には BUSY、最後の結果は同じ session_id の間だけ取り出せる）は、core の endpoint に一般の形で
  実装する。
- 時間の見積もり: P4 は候補が 51 本で、順序つきの組が 2550 通り。1 組の確認（wake + dmactive + 1 回の読み出し）が
  100 µs なら 0.3 秒、1 ms なら 2.6 秒（未測定）。

### 推奨

- attach に組を付ける形で進める。P4 の利点（どんな配線でもつながる）を活かせるのは、この形だけである。
- PENDING は、全組み合わせのスキャンが実測で 1 秒を超えたときに入れる（必要が出てから足す）。1 秒以内なら、完了まで
  応答しない形のままでよい。

## 2. fixture の payload を v1 の形にするか

### 現状

- `oep.fixture.gpio` / `uart` / `capture` は、v1 の名前の下で v0 の payload をそのまま使っている。
- v1 側で足したのは plan の役割（fn、role、channel）と、ロックなしで使える操作の宣言だけ。
- 使っていて困ったことは、次の 3 つ。
  - UART の読み出しはデータを消費するので、ロックが要る。Monitor のようにロックなしで読みたい用途に合わない。
  - capture は 1 サンプル 1 byte に展開して返すので、2 本の観察では 4 倍の量を転送している（P4 の 250k サンプルの
    読み出しで数秒）。
  - gpio の configure の mode 番号（open drain の low = 6、解放 = 7 など）は v0 の表を見ないと分からない。

### 案

- A. v0 の payload を v1 の payload として固定し、v1 の文書に書き写す。困ったところだけ、あとで個別に足す。
- B. v1 の形に作り直す（UART はコンソールと同じ位置つきのストリームにして、ロックなしで読めるようにする。capture は
  詰めた形で返す）。

### 決定（2026-09-25）

- **B**（v1 の形に作り直す）。固めた後に v0 の形と v1 の形の 2 つの流儀を host が持ち続けないため（ch32rv セッションの意見）。
  形は [v1 wire](v1-core-wire-delta.ja.md) §5.8（gpio / uart、revision 1）と §5.9（capture、revision 1）。

### 推奨（決定前の記録）

- A。いま実際に困っているのは capture の転送量と UART の読み出しのロックだけで、どちらも既存の payload に操作を
  1 つ足せば済む（capture の詰めた読み出し、UART の位置つき読み出し）。作り直すのは、必要が出てから。

## 3. 資源の寿命を 1 つの表にする（2026-09-26 のレビュー 2.2 / 3.1）

### 現状

- connection: host の attach と、config の bind が「使っているもの」。host の detach は host の分だけを外し、force か、使うものが
  無くなったときに閉じる。lease の期限切れで host の分が外れる（2026-09-26 に実装）。
- console の stream: 「session や lease の終了では終わらない」と書いてある一方、connection が閉じれば閉じる（読み出しは残る）。
  lease が切れて host の分が外れ、bind も無いと、connection も stream も閉じる。文書どうしが食い違っている（レビューの指摘）。
- plan: session の終わりでも lease の期限切れでも残る（one-shot の CLI のため）。host が落ちると、出力のピンが出力のまま残る。
- `connection(u8)` と `stream(u8)` は、今の probe では常に 1。閉じた後に同じ番号を使い回す。

### 案（1 つの規則）

**「session が作った資源（attach の分、plan）は、明示の end では残して次の session に渡し、lease の期限切れで外す」**。

| 出来事 | connection の host の分 | bind の分 | stream | plan |
|---|---|---|---|---|
| host の attach | 加わる | — | — | — |
| host の detach | 外れる（使うものが無くなれば閉じる） | — | connection と一緒に閉じる | — |
| detach（force） | 閉じる | 閉じる | 閉じる | — |
| 明示の end | **残る**（次の session の attach がそのまま加わる） | — | 残る | **残る** |
| lease の期限切れ | **外れる** | — | connection が閉じれば閉じる | **外す**（ピンは安全な状態へ） |
| force で奪われる | 外れる（期限切れと同じ） | — | 同上 | 外す |
| target の reset | 残る | 残る | 残る | 残る |
| 線が切れる（1000 ms） | 閉じる | 閉じる | 閉じる | 残る |
| probe の再起動 | 無くなる | 保存から結び直す | 無くなる | 保存から戻す（§5.10） |

- stream は connection の利用者に数えない（connection の上に載るもの）。閉じた stream も、次に開くまで read / marks で読める。
- bind のコンソールは bind の分で connection を保つ（host がいなくても集め続ける）。
- 残したい plan は `oep.probe.config` に保存する（保存した plan は期限切れでも外さない）。「一時的な plan を明示的に残す」
  TLV は作らない（要るものは保存で足りる）。
- 「安全な状態」はピンの解放（入力）。チャネルごとの安全な状態の宣言は、要るものが出てから。
- **ハンドルの使い回し**: connection の番号は、新しい connection を作るたびに 1〜255 を順に進める（閉じた番号をすぐには
  使わない）。古い番号の要求は rejected no_connection になる。stream も同じ。同じ boot_id の間だけ有効。

### 決めること

1. 上の表（特に、end で残す / 期限切れで外す、の分け方）でよいか。ch32rv の要望「Ctrl-C で落ちた host の分は残らない」と、
   one-shot の CLI（end して終わる）が次のプロセスに渡す流れの両方を満たす。
2. plan を期限切れで外す（今は残す）に変えてよいか。

## 4. 状態を変える要求の重複排除（2026-09-26 のレビュー 2.4）

### 現状

- 応答が壊れたか来なかったとき、host は session_id の無い要求（読むだけ、open）だけを送り直し、状態を変える要求は送り直さない。
  応答だけが失われると、実行したかどうかが分からない（reset、write_block、config の set / save で困る）。

### 案（見出しを変えない）

- **再送は同じ corr で送る**。corr は host が要求ごとに進める u16 で、見出しに既にある。
- probe は、ロックを持つ session の要求（role 0x81）について、直近の **max_inflight 個以上**の (corr, 結果) を覚えておく。同じ
  session で同じ corr の要求が来たら、実行せずに覚えている結果を返す。
- 覚えておく結果の大きさには上限を置く（例: 64 byte。状態を変える要求の結果は小さい）。上限を超えた結果の要求を送り直された
  ときは、実行せずに新しい reject reason（例: `result_lost`）で断る（host は読み直して確かめる）。
- session が変わったときの exactly-once は約束しない。
- レビューの案（見出しに `request_seq` を足す）と比べて、見出しも host の番号の付け方も変わらない。corr は今も host が要求ごとに
  一意に振っている（2026-09-25 の立て直しの規則）。

### 決めること

1. corr を重複排除の鍵にしてよいか（見出しに新しい番号を足さない）。
2. 覚えておく数と、結果の大きさの上限。

## 5. プロトコル本体と標準インターフェースの線引き（2026-09-26、ユーザーの方針）

### ユーザーの方針

- OEP のプロトコル本体と、ロジアナなどの仕様を分ける。どこまでが本体で、どこからが拡張かを分かるようにする。
- ロジアナなどは OEP の**標準的な実装例**。自由に拡張できる領域の標準例である。
- ただし「すでに OEP に含まれている」という考え方もあるので、線引きのルールを明確にする。

### 案: 3 つの層

| 層 | 中身 | 名前 | 版 |
|---|---|---|---|
| **本体（OEP core）** | どの probe と host も、機能に関係なく実装するもの: 経路とフレーム、メッセージの見出しと role、corr、セッション・ロック・lease・force、confirm / list / describe / ping、結果のモデル（resolution、reject reason、outcome、status）、TLV と番号の規則、revision と名前の規則、通知の仕組み（push / event のフレーム、subscribe、ハートビート）、長い操作のポーリング、plan（ピンの割り当て）、describe の共通タグ、registry の形 | `oep.core` | プロトコルの revision（confirm） |
| **標準インターフェース** | 本体の仕組みだけを使って定義した、名前つきの機能: `oep.wire.*`、`oep.target.*`（riscv-dm、arm-adi、console と dmseq）、`oep.fixture.*`（gpio、uart、capture、analog）、`oep.probe.config` | `oep.` で始まる名前（project が管理） | インターフェースごとの revision |
| **拡張** | (a) 標準インターフェースの中の任意機能（features のビット、任意の TLV / op）と、別の定義（ミックスドシグナル、多段トリガなど。logic-capture §0.1）。(b) 独自のインターフェース（逆 DNS の名前） | `oep.` の別の定義、または独自の名前 | それぞれ |

OEP の外: probe 自身の更新（DFU、Mass Storage）、コンソール専用の CDC の口、USB の記述子の細部。

### 線引きの規則

1. **本体に入れるのは、host がインターフェースの名前を知る前に要るもの、またはすべてのインターフェースにまたがり、どれか 1 つの
   インターフェースでは定義できないものだけ**（例: セッションのロック、インターフェースをまたぐピンの割り当て、通知のフレーム）。
2. **本体の仕組みだけで名前つきのインターフェースとして定義できるものは、どの probe も持つとしても本体に入れない。**
   判定の問い: 「第三者が、本体を変えずに、独自の名前で同じものを定義できたか」。できたなら標準インターフェース（または拡張）。
3. **本体は、特定のインターフェースの名前にも意味にも触れない**（`oep.core` 自身を除く）。たとえば push のデータのフレームの
   見出しは fn と seq までを本体が決め、その後ろ（ストリームの位置など）はインターフェースが決める。
4. **標準インターフェースに、本体の上での特別扱いは無い。** 独自のインターフェースと同じ仕組み（名前、fn、revision、describe、
   plan の role、通知）だけを使う。違いは、名前が `oep.` で、番号が project の registry にあり、project が適合試験を持つことだけ。
5. **インターフェースどうしの関係**（riscv-dm は wire の connection を使う、console は connection か plan の上に開く、など）は、
   関係するインターフェースの文書が決める。本体は関係の仕組みを持たない（connection は wire のインターフェースが定義する資源）。
6. **版は層ごとに独立**: 本体を変えたらプロトコルの revision、インターフェースを変えたらそのインターフェースの revision
   （§0 の revision の規則）。

### この規則で決まる、境目にあったもの

| もの | 層 | 理由 |
|---|---|---|
| plan（ピンの割り当て） | 本体 | ピンは probe の資源で、複数のインターフェースにまたがる（規則 1） |
| describe の共通タグ（role_channels、max_clock_hz など） | 本体 | どのインターフェースを知らなくても、宣言を読むのに使う |
| connection と、その利用者・寿命 | 標準インターフェース（`oep.wire.*`） | wire が定義する資源。本体は「session が作った資源は end で残し、期限切れで外す」という一般の規則だけを持つ（§3） |
| 位置つきのストリーム（console、uart、capture の read と marks） | 標準インターフェースの共通部品 | 3 つのインターフェースが同じ形を使うが、本体の仕組みではない。「標準インターフェースの共通部品」の文書に置く |
| push のデータのフレームの position | 本体からは外す | 規則 3。本体の見出しは role、fn、seq まで。position はインターフェースの payload の先頭に置く（capture は u64） |
| dmseq | 標準インターフェース（`oep.target.console` の方式 2） | target 側の framing。本体とは無関係 |
| `oep.probe.config`（設定、起動モード、bind） | 標準インターフェース（任意） | 本体の仕組みだけで定義できる（規則 2） |
| 複数の経路（vendor、HID、CDC）とセッションの共有 | 本体 | インターフェースを知る前に要る |

### 文書の形（レビュー 2.1 と合わせて）

- `oep-core.ja.md`: 本体の規範を 1 つにまとめる（今の v1-core-wire-delta の §0〜§5 の core の部分と、v0 に委ねている見出しの形）。
- 標準インターフェースは、まとまりごとに 1 文書: 線と target（wire、riscv-dm、arm-adi）、コンソール（console、dmseq）、
  fixture（gpio、uart）、キャプチャ（capture、analog）、probe の設定。
- 「標準インターフェースの共通部品」: 位置つきのストリーム、connection の利用者など、複数の標準インターフェースが使う形。
- 「インターフェースの書き方」: 独自のインターフェースを定義する人への規則（名前、番号の空間、revision、TLV、describe、通知）。
  本体の文書の 1 章でもよい。
- 比較、実験、採用の理由は、規範ではない文書として分ける。

### 決めること

1. 3 つの層と、線引きの規則 1〜6 でよいか。
2. 境目の表の割り振り（特に plan を本体、connection を wire 側、push の position を本体から外す）でよいか。
3. 文書をこの形に分けてよいか（大きな書き直しになる。中身の決定（§3、§4、u64）を先に済ませてから分けるのがよい）。
