## 8. ボード上の LED（2026-10-01、ユーザーのメモ）

状態: **保留・記録だけ**。今の作業（凍結前の仕様の反映と UART の速さ）が終わってから仕様にする。**標準（BASIC の `oep.` の

## 6. IP の経路（Wi-Fi、Ethernet）（2026-09-26、ユーザーのメモ。**v1 では扱わない**: 凍結前の決定 11。TCP は経路の種類としてはあるが、設定と発見は v1 の外）

### 現状

- core §3.1 は TCP のフレームの形（`length(u16) message`）と、「TCP は信頼できるローカルの接続か、認証したトンネルの内側でだけ
  使う」という注意だけを持つ。
- どうやって IP につなぐか（Wi-Fi の SSID と鍵、Ethernet の DHCP / 固定 IP）、host がどうやって probe を見つけるか（アドレス、
  ポート）、TCP で開いた経路が USB の経路とどう並ぶか、の規定が無い。

### ユーザーの方針（メモ）

- Wi-Fi の接続先（AP）は firmware に焼き込まない。host が設定し、probe が永続化する。

### 案

1. **設定の項目として足す**（`oep.probe.config`、USB の項目と同じく任意の群）:

   | 項目 | 値 | 備考 |
   |---|---|---|
   | wifi | ssid（text）、secret（バイト列）、ほか（hidden など、TLV で足す） | **get は secret を返さない**（長さ 0 か「設定済み」の印だけ）。hash の正規形からも secret を外し、代わりに secret の有無だけを入れる |
   | ip | method（u8: 0 DHCP、1 固定）、固定なら address / mask / gateway（u32 ×3） | Wi-Fi と Ethernet で 1 つずつ（キー: interface の番号） |
   | tcp | port（u16）、flags（bit0 待ち受ける） | 待ち受けない限り、TCP の経路は開かない（既定を持たない） |

2. **見つけ方**: probe は describe（fn 0 か probe.config）で今の IP のアドレスとポートを出す（USB でつないだ host が読める）。
   ネットワークの上での発見（mDNS など）は任意で、名前は後で決める（最小から）。
3. **経路の扱い**: TCP の経路も core §3.3 の複数の経路の 1 つで、セッションとロックを共有する。host は、同じ probe に USB と TCP の
   両方があるとき USB を先に試す（§3.3 の順に TCP を足す）。
4. **信頼**: core §3.1 のまま（認証は持たない。信頼できる LAN か、認証したトンネルの中だけ）。Wi-Fi の LAN を「信頼できる」と
   みなすかは使う人が決める、と注記する。

### ユーザーの意見（2026-09-26、追記）

- IP には、OS やシステムに統合されているもの（Wi-Fi、Ethernet）と、client としてだけ出てくるもの（LTE など）がある。どこまで
  対応するかは要検討。
- probe の実装例の話なので、プロトコルとしては扱わない（ノンケア）でもよいかもしれない。

### 決めること

- IP の経路をプロトコル（設定の項目、アドレスの出し方）で扱うか、probe の実装に任せてプロトコルは扱わないか。扱うなら、
  どの種類（Wi-Fi、Ethernet、LTE のような client だけのもの）まで。
- 設定の項目の形と、secret を読み出せない扱い（get と hash）。
- アドレスの出し方（describe のどこに置くか）と、発見の仕組みを v1 に入れるか。
- IP だけで使う probe（USB を持たない）の、最初の設定の入れ方（下の §7 の回復のモードと合わせて考える）。

## 7. 回復（リカバリ）の方法（2026-09-26、ユーザーのメモ。**v1 では扱わない**: 凍結前の決定 11。案 1 は「すべてのシリアルの口がいつでも OEP を受ける」の規範で前提が変わった）

### 問題

- 設定で CDC の口を UART の素通しなどに割り当て、Wi-Fi などの設定を誤ると、host が OEP の経路に入れなくなり、設定を戻せない
  おそれがある（今の試作は、保存の boot_mode が組めないときだけ `forgetBootMode` で戻る）。

### ユーザーの方針（メモ）

- 回復の方法を探す。**仕様の外のガイド**として扱う（probe の作りに依る）。例: ボタンを押しながら起動、リセットを 2 回続けると
  回復のモードで起動する。

### 案

1. **仕様（規範）に入れる最小のもの**:
   - probe は、保存した設定で **OEP を運ぶ経路が 1 つも無くなる**ようなら、その設定を適用しない（set は rejected unavailable、
     起動時は保存を読めないものとして扱う）。
   - probe は、回復のモードを持つなら、describe でその入り方を名前（text）で知らせてよい（ガイドへの手がかり）。
2. **ガイド（規範ではない。probe 開発ガイドに書く）**: 回復のモードは、保存した設定を無視して、firmware の既定の経路（USB の
   OEP の口）で起動し、設定の erase を受け付ける。入り方の例:
   - ボタンを押しながら起動する（ESP32 の BOOT は ROM のダウンロードと取り合うので、別のボタンか、起動後の一定時間の押下）。
   - リセットを短い間隔で 2 回（RTC のメモリや NVS に印を残し、次の起動で見る。いわゆる double reset detect）。
   - 起動から一定時間だけ、既定の経路も開いておく。
3. 試作で、P4 と classic ESP32 でどれが使えるかを確かめてから、ガイドに書く。

### ユーザーの意見（2026-09-26、追記）

- 回復のモードは推奨で、必須ではない。firmware を焼き直して設定し直す、でもよい。

### 決めること

- 規範に入れる最小のもの（OEP の経路が無くなる設定を断る）でよいか。回復のモードは推奨（必須にしない）として書く。
- 回復のモードの入り方を、どの probe でどれにするか（試作で確かめる）。
